# AI-Ready Docs

## 目标与范围

从目标 AI 实际读到的文本出发，审阅它能否理解任务、依据和边界，并按需改写同一份权威内容。文本也应便于人维护；已有契约要求的机器字段或消费视图，应能追溯到权威内容。

本 skill 处理文档侧的语义和组织。获取、解析、索引、召回与上下文组装属于交付链路；所需信息未进入 AI 上下文时，明确指出缺口及其影响。纯措辞润色和视觉美化不触发本流程。

## 读取策略

1. 普通审阅和编辑直接使用下方清单。用户只说“复看一下”时，在指定范围内依次检查五个阶段，无需用户点名症状；定向审阅或局部修改只核对与请求有关的项及受影响的边界。
2. 遇到原理争议、复杂取舍、不熟悉的文档用途或需要解释理由时，按标题读取 [principles.md](references/principles.md) 的相关章节；校准例只帮助判断边界。
3. 整体审阅本 skill、检查引用一致性或多个原则相互影响时，读取完整原则文件。

## 五阶段检查清单

### 1. 确定消费场景与处理范围

- [ ] **用途与结果**：哪类 AI 会读到哪些文本，要据此做什么？什么结果表示用对了？
- [ ] **范围与前提**：按用户指定的文件或目录处理；只给出项目时，从当前任务定位直接相关文档。标出必需但不可获得的信息及其影响。
- [ ] **受保护的边界**：识别安全、隐私、机密性、权限、合规、真实性、不可逆操作和明确契约，标出会影响本次处理的冲突。

### 2. 恢复主承诺与内容 owner

- [ ] **重心偏移**：从标题、开头、触发条件和输入输出看，文档承诺解决什么？用正文的篇幅、层级、结论与验收核对重心；入口过宽就收窄承诺，正文偏题就调整内容。混合用途以最容易误用的一项组织主线。
- [ ] **owner 错乱、重复与冲突**：规则变更时应改哪一处？在负责定义它的位置保留完整判断，其他位置保留够用的摘要、触发条件或引用；口径不同时核对适用条件与权威来源。
- [ ] **内容过长**：读者是否必须读完另一项任务的细节，才能找回当前步骤？把当前任务必需的判断留在主线，有独立用途的细节归入相应 owner，按需展开。

### 3. 核对语义并收敛内容

- [ ] **规则的条件与效力**：读者能否区分事实、建议、要求和示例？写清完成任务所需的定义、输入输出、依赖、因果、优先级与例外；用目标状态、必要约束、推荐路径和验收规格说明该怎么做。保留能区分正确用法与相近错误的反例。
- [ ] **泛化特例**：核对正文声称的范围和依据实际覆盖的范围。
  - 局部观察是否被写成通则？专用办法要作为通用要求，需确认其成立前提也覆盖其他对象；只在局部成立的办法写明条件。
  - 区分规则的来源与举例：上位契约已明定范围时，举一个例子不缩小其效力；只有个例、无法确认规则来源时，指出依据缺口，保留原要求待核。
- [ ] **负向描述**：点名排除对象，读者多知道了什么？能消除真实歧义或定义独立约束的禁止项应保留；没有新增信息的排除项只增加核对成本，删去。
- [ ] **迁移残留**：旧名称、退场方案或一次性故障，今天还有谁需要据此行动？仍生效的兼容义务写明条件，只有复核价值的材料归入历史参考，其余退出主线。
- [ ] **语义保真**：区分澄清表达、补充事实和改变要求。不同解释会改变结果且原意无法确认时，标出歧义，交由相应 owner 决定。

### 4. 形成可恢复的阅读路径

- [ ] **阅读路径**：标题能否指到所需内容？局部阅读时术语、指代、条件和例外是否清楚？将必要的口头或视觉语境写进文本。引用不可访问时，补足最小语境或指出缺口。
- [ ] **结构与格式**：遵循交付格式契约。用有序列表表达顺序，用每行自足的表格表达简单对照，用适合消费方的结构表达复杂输入输出；图示按关系类型与目标环境选择，关键语义须能从文本或可读取的图源恢复。
- [ ] **Markdown 层级与渲染**：文档使用 Markdown 时，分别核对：
  - 标题、编号和嵌套是否把步骤、条件与例外挂在正确位置？
  - 默认用可移植的 Markdown 表达正文；只有用户或交付契约明确要求 HTML 时，才嵌入 HTML。
  - 行内强调能否在相邻文字与标点之间正确闭合？表头与分隔／对齐行的列数是否一致，数据是否落在对应列？
- [ ] **语言**：保持原文主要语言，用户要求翻译或文档确需统一时再切换。

### 5. 从目标读者角度复核文本

- [ ] **代表任务**：选一个与文本用途相符的问题，只读目标 AI 能获得的文本，能否判断任务、依据、约束和预期结果？
  - 读说明或规则时，能否据此回答问题或作出选择？有适用边界时，再看一个相邻但不适用的情形是否被误纳。
  - 读提示词时，模型要对什么做什么、交付什么？附有参考材料时，能否分清待处理的内容与样例，判断要借用样例的哪些特征？
- [ ] **验证依据**：编辑后核对精确约束、有效例外和人的可维护性，运行已有的格式、链接、schema 或文档检查。分别说明文本走查的判断和机械检查的结果；实际运行过模型时，再报告观察到的输出。

## 边界与交付

编辑任务按授权范围写入；审阅只报告有文本依据、会影响理解或行动的发现，指出位置、影响与建议；未发现时直接说明结果。

高风险目标的优先级不明且会改变结果，或高风险边界、更高优先级指令、明确契约之间发生冲突时，先确认可行路径。缺少关键信息时说明它如何改变结果，只问一个具体问题；其余可逆取舍按用户目标处理并说明。交付区分文档侧改动、外部交付链路状态、已验证结果和残余风险。

## 自更新

本 skill 的指令使用不需要安装依赖。仅在本 skill 目录运行自更新入口 `node scripts/update-skill.ts` 时，需满足随包 `package.json` 的 Node 版本与兼容依赖。
已有兼容宿主依赖即可复用；普通运行、导入与检查不自动安装。依赖不可用时，使用随包 manifest 固定的 pnpm 显式执行：

```bash
pnpm --dir "<skill-directory>" install --ignore-workspace --prod --frozen-lockfile --config.node-linker=isolated
```

运行时文件或 manifest/锁文件损坏时，重新获取完整 skill 后再安装并重试。更新覆盖正式包中的同路径文件、保留其余本地文件。源码更新成功不证明依赖兼容；需要时按新包锁文件显式安装。
