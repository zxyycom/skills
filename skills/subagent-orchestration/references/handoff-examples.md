# 派发与回报示例

下面是两种接手情形。文件名、版本和回报均为示例；实际派发时用接手者能定位的材料，不要求复用句式。

## 看不到父对话：只读核对，回报与产物语言不同

主代理需要决定是否修改英文安装说明。子代理只负责核对，不负责改文件。

**可直接发送的消息**：

> 在目标仓库根目录，对照 `README.md` 的安装要求和 `package.json` 的 `engines.node`。用中文说明两者是否一致，并给出各自的位置和原文；若明确冲突，附一句可替换 README 原文的英文建议。任一处没写版本就说明缺口，不推测，也不改文件。

**若确实查到了冲突，回报可以很短**：

> 不一致。`README.md` 的 Installation 节写的是 “Requires Node.js 20 or later.”；`package.json` 的 `engines.node` 为 `">=22"`。若以 manifest 为准，建议改成 “Requires Node.js 22 or later.”

两处原文支持“不一致”的结论，不足以证明哪一处该改；后者仍是主代理要做的判断。

## 文档可见，用户的选择不可见：补决定，不补整段对话

假设用户已确认以 manifest 为准，并授权修改英文说明。只发“按刚才定的版本修一下”会让接手者猜测版本来源和写入范围。

> 用户已确认以仓库根目录 `package.json` 的 `engines.node` 为准。只修改根目录 `README.md` 的英文安装要求，不动 manifest。改后用中文回报 README 的新句子、对应的版本字段和实际核对结果。

如果接手者只能看到 README，它可以明确回报：“能定位安装段落，但无法读取用作依据的 manifest；请提供目标版本字段或可访问的位置。尚未修改。”这比凭上一轮示例中的版本动手更可靠。
