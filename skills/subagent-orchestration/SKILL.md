# Subagent Orchestration

主代理对用户目标、跨任务取舍和最终交付负责；子代理在约定范围内自主完成一项可独立验收的结果。日常委派按下文执行；派发示例和独立审查方法在相应步骤按需读取。

## 决定谁做什么

1. 确认用户要的结果、验收条件，以及用户和运行环境对委派的要求或限制。工具可用不等于已获授权。分工可自行决定时，只有并行、隔离上下文或获得独立证据的收益值得交接成本，才委派；否则由主代理直接做。
2. 给每个子代理一个能独立验收的结果，而不是一个角色名或一串零散步骤。必须一起修改同一状态、或合起来才有可验收结果的工作，由同一负责人连续完成。主代理推进不依赖子任务结果的工作，不与子代理重复实现。
3. 并行前划清写入范围：同一交付物、共享配置、生成物或外部状态同时只有一个写入方。临时脚本等辅助写入也须明确授权并隔离。为取得互补或独立证据可以读取同一材料；依赖前序改动的工作，等前序停止写入、输入稳定后再开始。

## 写一条接手者能执行的消息

发送前，从接手者的角度读一遍：只看消息和其中明确指向、自己能读取的材料，能否知道要解决什么问题、可以改什么、要带什么结果和证据回来？简单任务一句话即可；多个输入或写入限制再分项。不要让“按刚才说的做”或“按本 skill 回报”代替具体要求。

- **上下文**：共享工作区不意味着共享对话，继承对话也不意味着继承父任务权限。写明影响做法的用户要求和已确认取舍。稳定材料给路径、章节或版本；接手者看不到的必要信息，只在获准共享的范围内摘录或转述。
- **历史**：可配置时默认使用干净上下文。必要原意无法准确转述时，选工具支持的最小充分片段；只有完整对话本身不可替代时才主动选全量。继承范围不明时，不依赖可能已传入的内容。仍缺材料时，子代理指出具体缺口，主代理补齐输入或调整任务。
- **语言**：派发和回报默认沿用当前协作语言；产物按用户要求或目标文件的语言约定编写。两者不同时分别交代。命令、标识符和待核对的原文保留原样。需要措辞参照时，见[派发与回报示例](references/handoff-examples.md)。
- **运行配置**：允许选择时，先按任务所需的理解、工具使用和综合能力选模型，再按推理难度和消解证据冲突所需的预算选思考强度。不按角色固定组合，也不用更高强度弥补能力缺口。工具不支持所需配置时，调整任务范围、输入或验证方式。

## 处理进行中的变化

- **目标或输入改变**：主代理通知受影响的子代理；若已有下游结论依赖旧输入，只重做或复核受影响部分。子代理遇到其他来源的改动，报告影响，保留对方的工作，只在自己的授权范围内继续。需要澄清用户意图或扩大授权时，由主代理询问用户。
- **继续还是换人**：同一交付的实现、自验证和定向修复由原代理继续。目标或主要职责改变，或需要独立验证、审查时，交给新的代理。原代理不可继续时，先确认它已停止写入，再把当前成果、未决问题和写入范围交给接手者。

## 接回结果并验收

1. 子代理自验证后回报完成程度、核心结论和依据；若受阻，说明缺口，不把未验证的事写成结论。有正式改动、影响共享工作区的辅助物、范围偏差或影响交付的假设和风险时，一并说明。高风险、涉及多个关键验收条件或用户要求可追踪时，逐项给证据；其他情况不必填表。
2. 主代理对照用户目标检查实际结果、权限范围和集成情况。自验证足以支持验收时就不加一轮审查。用户要求独立判断、关键结论不确定或失败影响较高时，按[独立验证与审查](references/independent-checks.md)选择补证方式。
3. 只把阻断本次验收的问题交回修复，并复核受影响的部分。主代理自己的工作与委派结果合起来覆盖用户目标、证据充分、没有未解决的阻断，且影响交付的限制和残余风险已说明时，完成交付。

## 自更新

本 skill 的指令使用不需要安装依赖。仅在本 skill 目录运行自更新入口 `node scripts/update-skill.ts` 时，需满足随包 `package.json` 的 Node 版本与兼容依赖。
已有兼容宿主依赖即可复用；普通运行、导入与检查不自动安装。依赖不可用时，使用随包 manifest 固定的 pnpm 显式执行：

```bash
pnpm --dir "<skill-directory>" install --ignore-workspace --prod --frozen-lockfile --config.node-linker=isolated
```

运行时文件或 manifest/锁文件损坏时，重新获取完整 skill 后再安装并重试。更新覆盖正式包中的同路径文件、保留其余本地文件。源码更新成功不证明依赖兼容；需要时按新包锁文件显式安装。
