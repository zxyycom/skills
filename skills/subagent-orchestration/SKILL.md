# Subagent Orchestration

## 目标

把复杂任务拆成可独立交付的任务切面, 由子代理承担主要调查、实现、验证和审查。主代理负责整体目标与验收、切面编排、依赖与所有权协调、结果审计和最终交付; 子代理在明确边界内自主产出结果和证据。

## 主流程

1. 定义整体目标、最终验收和必须由主代理处理的跨切面取舍。
2. 将工作拆成可独立交付和验收的任务切面, 为每个切面指定一个主要职责和明确边界。
3. 为每个切面配置历史范围、模型、思考强度、权限、写入所有权和依赖关系。
4. 派发结果导向的任务, 让子代理在切面内自主完成主要职责, 并为结论或改动提供必要证据。
5. 子代理运行期间保持其切面所有权, 主代理继续调度依赖已经满足的其他切面; 范围或验证负担显著偏大时再调整切面。
6. 根据交付物、证据和依赖状态推进任务; 结果不足或阻塞原因不清时, 缩小切面或补充调查, 主要职责变化时建立新的子代理。
7. 按证据缺口和交付风险选择自验证、独立交叉验证和独立审查, 将修复范围限定为实质阻断问题。
8. 审计目标、范围、证据和重大例外; 验收满足后完成最终交付, 需要新增授权、目标解释或跨切面取舍时由主代理请求用户决定。

## 任务切面与代理生命周期

1. 任务切面以能够独立产出和验收的结果为边界; 必须共同写入同一状态, 或只有合并后才能形成稳定、可验收中间结果的工作保留在同一切面。
2. 每个子代理承担一个主要切面。目标、主要职责或独立验证与审查角色变化时, 建立新的子代理并提供最小必要上下文。
3. 同一切面的继续实现、自验证和定向修复延续原子代理, 保留局部上下文与写入所有权。原代理不可用或工具不支持延续时, 由替代代理在前序写入停止后接收上下文和所有权。
4. 每个切面负责人完成自身结果的自验证; 需要独立证据或判断时, 在稳定结果形成后由不同代理执行交叉验证或审查。
5. 切面拆分以隔离上下文、写入所有权和独立验收的实际收益为准; 交接成本更高的相邻工作由一个代理连续完成。

## 派发配置

每个切面显式确定历史范围、运行能力、权限和依赖; 具体字段与合法值由当前工具接口承接。

### 历史与上下文

1. 新代理使用当前工具支持的最小充分历史范围。可控时使用干净上下文, 通过任务消息和可访问的稳定材料提供必要信息。
2. 最近对话包含无法安全压缩的必要用户意图或已确认取舍时, 使用最小有限历史; 完整对话本身是不可替代输入时, 使用全量历史。
3. 工具无法控制历史时沿用其实际行为, 并让任务消息补足缺失信息、减少对已继承内容的重复。

### 模型与思考强度

1. 模型决定子代理可用于切面的能力, 包括目标理解、知识与上下文利用、工具使用、跨范围综合和约束遵守。根据这些能力要求选择模型; 大工作量优先通过任务切面控制。
2. 思考强度决定所选模型可用于当前问题的思考预算上限, 并在该模型的能力边界内生效。根据多步推理、约束交互、证据消歧、方案探索和自检难度选择思考强度。
3. 先选择具备所需能力的模型, 再为问题难度配置思考强度。配置依据是切面的能力要求和问题难度, 相同职责的不同切面可以使用不同组合。
4. 工具不支持独立配置或所需组合时, 将实际配置作为当前约束, 通过调整切面、上下文和验证降低误判风险。

### 权限与依赖

1. 改变交付物、项目配置、共享生成产物或外部状态的写入所有权保持互斥; 输入稳定且写入所有权不重叠的切面可以并行, 读取范围可以为独立结论或互补证据重叠。
2. 调查、验证和审查可以在明确、隔离的范围内创建临时脚本、测试 fixture、分析输出、局部缓存或其他辅助物。
3. 独立验证和审查保持被评估对象不变, 以不同代理形成的证据支撑独立结论; 辅助写入仍遵守已声明范围。
4. 依赖前序结果或改动的切面串行执行, 并在前序写入结束后读取稳定输入。前序结果发生变化时, 主代理重新判定依赖旧输入的下游交付物和证据, 并定向重做或复核受影响切面。
5. 子代理发现其他来源的改动时报告其影响, 在自身所有权范围内继续推进; 主代理据此调整依赖或切面。

## 子代理任务模板

先在派发工具中配置历史范围、模型和思考强度, 再发送以下工具无关的任务消息:

```text
目标与验收: <需要达成的结果和完成条件>
职责与范围: <唯一主要职责及文件、模块、问题或决策边界>
上下文: <最小必要背景、可访问的稳定材料和已确认取舍>
权限与依赖: <交付与辅助写入范围、被评估对象、外部状态权限及前置输入>
约束: <必须遵守的具体限制、用户偏好或项目规则>
结果交接: <按“子代理结果交接”返回结果和关键证据>
```

## 验证与收敛

1. 产出代理根据切面验收条件完成自验证, 返回足够证据, 并在自身范围内处理未通过项。
2. 交叉验证由不同代理独立重做关键检查或采用另一证据路径, 用于补足事实或行为证据的独立性; 失败影响较高、错误难以观察、证据冲突或用户明确要求独立验证时按需使用。
3. 独立审查由不同代理判断目标一致性、范围、假设、重要取舍和风险, 用于补足判断的独立性; 需要实现与审查分离或相关判断风险较高时按需使用。
4. 主代理选择足以支撑当前交付的最小充分验证组合; 两类独立性都需要时才组合交叉验证和审查。阻塞原因不清时派发更小的调查切面, 结果冲突时派发独立审计切面。
5. 主代理从结果和证据审计目标覆盖、范围、假设、验证和重大风险; 细节补充服务于目标判断、风险判断、验证或下一步切分。
6. 实质阻断问题包括影响用户目标、正确性、安全与权限边界、范围一致性、集成结果或必要验证的问题。风格偏好、可选优化和范围外设想作为非阻断建议随结果报告。
7. 实质阻断问题由原实现代理定向修复; 替代代理按生命周期规则接收上下文和所有权。复核聚焦受影响边界, 阻断清除且证据充分后结束修复循环。

## 与 task-graph 协作的 Git 集成

本节只在当前工作已经由 `task-graph` 领取, 且 task goal 包含目标主线集成时适用。调用前读取可用的 `task-graph` 行为入口; result、lease、`complete` 和 task index 版本锚点由该 owner 定义。本 skill 只决定代理交接、集成所有权和任务切分。

`task-graph` 不可用时, 使用项目已有的任务与版本管理流程, 不自行假设 lease、`complete` 或 task index。无论采用哪种流程, 分支提交都只是待集成输入。

按集成时序和所有权选择路径:

| 条件 | 路径 |
| --- | --- |
| 主代理会立即继续同一 task 的集成 | 保持一个 task 和当前 lease, 使用“即时集成”。 |
| 集成需要等待, 或由另一个长期所有者负责 | 在派发前或重新调度时建立显式依赖的实现 task 与集成 task, 使用“异步集成”。 |

### 即时集成

1. 子代理在自身分支完成实现、自验证和提交, 在 lease 有效期内续租, 再交付 task ID、分支、当前提交、lease ID、到期时间和验证结果。子代理不在分支提交后执行 `complete`。
2. 主代理以当前主线为基线 rebase 子代理分支, 处理冲突并执行与风险匹配的验证。只有目标主线能够 `ff-only` 接纳该分支时才合并。
3. 集成成功后, 主代理按 `task-graph` 的 result 契约使用匹配 lease 完成 task。合并或验证失败时 task 保持运行, 由当前 lease 继续续租、修复或按实际状态释放。

### 异步集成

1. 实现 task 的 goal 止于产物可交接; 集成 task 显式依赖实现 task, goal 止于目标主线完成集成。
2. 子代理完成实现 task, 并把分支、当前提交和验证结果交给主代理。需要跨上下文恢复时, 主代理在领取前把这些输入写入集成 task 的上下文。
3. 集成执行者独立 claim 集成 task, 完成 rebase、验证、`ff-only` 合并和 task 收敛。

多个 worktree 共用中央 task graph 时, 所有 task mutation 只写中央索引; 子代理不修改或提交自身 worktree 中的索引副本。本节只约束已经获得授权的 Git 与 task 操作顺序, 不自行授予这些操作。

## 子代理结果交接

使用自然文本、列表或当前工具支持的结构, 交接足以让主代理判断继续、修复或交付的最小信息:

```text
结果: <完成程度与核心结论>
证据: <支撑结论和验收的关键检查或依据>
改动: <正式交付改动, 以及仍保留或影响共享工作区的辅助写入; 没有则省略>
例外: <会影响当前交付的假设、范围偏差、风险或阻塞; 没有则省略>
```

`结果` 和 `证据` 始终提供; `改动` 和 `例外` 按实际情况提供。高风险任务、多个关键验收条件或用户明确要求可追踪性时, 将证据按验收条件展开; 其他任务保持简洁。

进入上述 Git 集成流程时, 按所选路径补充 task ID、lease 信息、分支、当前提交和已运行验证; 只有确有偏差或风险时才写入 `例外`。主代理据此继续同一 lease 或领取独立集成 task。

## 完成标准

同时满足以下条件时, 主代理可以交付:

1. 子代理结果和跨切面集成结果覆盖用户目标与最终验收; 使用 task graph 的 Git 集成已经按明确路径完成 `ff-only` 合并和对应 task 收敛。
2. 每个切面的职责、上下文、权限、写入所有权和依赖足以支持稳定交付, 并行任务之间没有写入冲突。
3. 自验证、独立交叉验证和独立审查的组合与当前证据缺口和风险匹配, 现有证据足以支撑交付。
4. 实质阻断问题已经清除, 会影响交付的改动、假设、范围偏差和残余风险已经说明。
5. 主代理能够依据交付物和证据完成目标一致性审计与最终交付。
