# Git Commit Organizer

## 目标

在保持其他来源的工作区和索引内容不变的前提下，把当前任务范围内的 Git 改动整理成语义单一、类型准确、信息可追踪且已经复核实际快照的提交。

## 风格定位

1. 本 skill 是一套可跨项目复用、带明确偏好的提交风格；触发后按本文定义的提交粒度、类型和消息格式组织提交。
2. 安装或显式调用表示使用者希望采用这套默认风格；用户或项目对当前任务给出更具体的提交要求时，按该要求调整。
3. 没有更具体要求时，稳定使用本文定义的类型、中文全角冒号、中文标题和中文 bullet。

## 提交范围

用户只说“提交”“提交 Git”或同类泛化指令时，只授权提交可可靠归因于当前任务的改动，不授权提交整个工作区。用户明确指定路径、change 或全部改动时，可以按该范围扩大候选集合；扩大授权不跳过实际 diff、提交粒度和生成物来源检查。

### 判断改动归属

先用当前任务的用户要求、已知写入记录和任务开始时观察到的工作区状态判断归属，再用 diff 理解改动内容。Diff 说明“改了什么”，不能单独证明“由谁或哪个任务改动”。

| 可用证据 | 归类 | 处理 |
| --- | --- | --- |
| 当前任务的已知写入记录，包括明确委派给当前任务的写入，并且与实际 diff 一致 | 当前任务改动 | 进入默认候选集合 |
| 用户明确指定路径、change 或全部改动 | 用户明确纳入 | 进入扩展候选集合，继续检查内容和粒度 |
| 任务开始时已经存在，且用户没有明确纳入 | 其他来源 | 保留不提交 |
| 执行期间新出现，但没有当前任务写入证据 | 归属不明 | 保留不提交 |
| 只有 staged、unstaged、untracked 状态，或只有路径、时间与内容相关性 | 证据不足 | 不据此扩大候选集合 |

归属证据必须覆盖准备提交的实际内容。同一路径混有当前任务与其他来源的 hunk 时，只把能够精确识别和隔离的当前任务 hunk 纳入候选。当前对话没有已知写入且用户也没有指定范围时，不从工作区代选内容；说明没有可可靠归因的候选并请求用户给出范围。

### 隔离提交快照

Staged 状态只表示索引快照，不表示当前任务获得了提交授权。先按下表选择快照方式，再创建提交：

| 当前状态 | 使用方式 | 提交前必须证明 |
| --- | --- | --- |
| 索引为空或只包含当前语义单元，且目标文件全部内容都应提交 | 用 `git add -- <path...>` 显式 stage，再普通提交 | 完整 cached diff 只包含当前语义单元 |
| 索引为空或只包含当前语义单元，但目标文件只提交部分 hunk | 使用可精确复核的局部暂存方式，再普通提交 | 完整 cached diff 只包含选中的 hunk |
| 索引含本次提交范围外的内容，目标路径与其完全分离，而且目标路径当前工作区的完整内容都应提交 | 对已经由 Git 跟踪或加入索引的目标路径使用 `git commit --only -- <path...>` | `git diff HEAD -- <path...>` 与 `git commit --dry-run --only -- <path...>` 都符合目标；范围外 staged diff 已单独复核并保留对照 |
| 范围外 staged 内容与目标路径重叠、目标路径只应提交部分内容，或无法构造精确快照 | 不创建提交 | 向用户说明最小冲突范围并请求选择 |

使用 path-limited commit 时，提交的是所选路径当前工作区的完整内容，而不是这些路径现有的 staged 快照。不得用它提交混合归属路径，也不得为隔离本次提交而 reset、取消暂存或覆盖范围外内容。提交后再次检查原有 staged 内容仍存在且未改变。

## 提交粒度

1. 一个提交只表达一个可独立理解、审查和回滚的语义单元。
2. 工作区包含多个互不依赖的语义单元时，按单元拆分提交；每个提交分别选择类型、标题和正文。
3. 同一功能、修复或规格调整所必需的代码、测试、文档和示例可以放在同一提交中，不为了文件类型机械拆分。
4. 若同一批改动同时包含用户可见行为、规格契约、AI 配置、CI 或构建流程等不同影响面，优先拆成多个提交；无法判断拆分边界时先向用户确认。
5. 若用户明确要求一次性提交全部改动，仍需在提交前说明存在的多语义单元风险。

## 提交类型

类型只表达本次提交的主语义，不承接提交粒度、stage 范围或正文写法。

本风格使用以下类型：

1. `feat`：新增用户可见能力、正式行为、产品能力或对外可感知流程。
2. `fix`：修复错误、冲突、不一致、回归、兼容性问题或错误的既有行为。
3. `plan`：整理规划、方案、OpenSpec change、proposal、design、tasks、实现路线或审计结论。
4. `spec`：调整协议、schema、契约、示例语义、验收标准或其他可验证规格。
5. `test`：新增或调整测试、fixture、测试数据、验证脚本或测试策略本身。
6. `docs`：只调整说明性文档，且不改变产品契约、规格能力、实现行为或验证规则。
7. `ai`：只调整 AI/agent 配置，例如模型、工具、MCP/app 连接、权限、运行参数或配置化 prompt。
8. `refactor`：调整代码结构、命名、拆分或内部组织方式，且不改变外部行为。
9. `chore`：通用维护、依赖、元数据、仓库整理或非 AI 专属配置。
10. `build`：调整构建、打包、发布产物生成或发行流程。
11. `ci`：调整持续集成、workflow、自动化门禁或检查任务。

选择规则：

1. 当多个类型都可能适用时，选择后续阅读提交历史时最需要追踪的语义影响。
2. 只影响 AI/agent 配置时，使用 `ai`，不归入 `chore`。
3. Skill 说明、agent 协作规则、OpenSpec、schema、示例和测试策略不因服务 AI 而使用 `ai`；按实际语义选择 `plan`、`spec`、`docs` 或 `test`。
4. 在 AI 主导或规格先行项目中，`docs/`、OpenSpec、schema、示例和测试策略可能是项目计划或产品契约本身；优先使用 `plan` 或 `spec` 表达语义，不默认使用 `docs`。

## 提交信息传递

1. 优先使用 `git commit -m "type：标题" -m "正文"` 通过命令参数传入提交信息。
2. 正文包含多条 bullet 时，在第二个 `-m` 的正文参数中保留换行。
3. 只有命令参数无法可靠表达多行正文时，才使用临时提交信息文件配合 `git commit -F <file>`。
4. 不默认用 stdin 传入提交信息。

## 工作流

1. 恢复范围：
   - 运行 `git status --short`。
   - 用 `git diff --stat`、`git diff --cached --stat` 和必要的局部 diff 理解 staged 与 unstaged 改动。
   - 对准备纳入的 untracked 文件单独查看内容和来源，因为常规 `git diff` 不展示其内容。
   - 按“判断改动归属”把实际内容归为当前任务、用户明确纳入、其他来源或归属不明；只保留前两类作为候选。

2. 形成语义单元：
   - 按“提交粒度”把候选改动拆成一个或多个可独立理解、审查和回滚的单元。
   - 分别按“提交类型”选择每个单元的类型。

3. 隔离快照：
   - 对当前语义单元按“隔离提交快照”选择普通提交、局部暂存、path-limited commit 或停止请求选择。
   - 不让后续语义单元或其他来源内容提前进入本次快照。

4. 编写提交信息：
   - 使用中文全角冒号：`type：标题`。
   - 标题用简洁中文，说明本次提交的核心目的，不加句号。
   - 正文使用 2-5 条中文 bullet，每条以 `- ` 开头。
   - 每条 bullet 描述实际 diff 中可观察的改动。
   - 只在实际运行验证后写“验证通过”或命令名称；未运行验证时在最终回复中说明未运行。

5. 提交前复核：
   - 再次运行 `git status --short`，确认没有新的范围变化。
   - 普通提交运行 `git diff --cached --stat`、`git diff --cached --check` 和必要的 `git diff --cached`；path-limited commit 运行表中规定的工作区 diff、dry-run 和保留 staged diff 检查。
   - 对新出现或发生变化的内容重新执行归属判断与快照选择；不能证明属于候选集合时保留不提交，无法隔离时停止提交。
   - 确认存在实际改动，并且将提交的文件、hunk、标题和正文一致。

6. 创建提交：
   - 按选定的快照方式和“提交信息传递”创建提交。
   - 提交成功后运行 `git show --stat --format=fuller HEAD`，核对实际提交的 hash、标题、正文和文件范围。
   - 再运行 `git status --short`，确认剩余改动；使用 path-limited commit 时同时核对原有无关 staged 内容未被消费或改变。
   - 提交失败时保留现有 staged 内容，重新检查状态并报告失败原因。
   - 最终回复提交 hash、提交标题、验证情况和是否有未提交残留。

7. 处理后续提交：
   - 工作区仍有本次范围内的其他语义单元时，从“检查工作区”重新执行完整流程。
   - 每个提交独立完成范围、类型、消息、staged diff 和提交结果复核。

## 提交信息模板

```text
plan：整理 CLI 参数兼容 change 说明

- 优化 standardize-cli-unknown-argument-compatibility 的目标、范围和影响说明
- 明确 warning 在 readable-json 与 protocol-json 等输出层的承载边界
- 同步核心 CLI change 的未知参数兼容和 protocol-json schema 边界
```

## 边界

- 整仓操作：只有用户明确要求提交全部改动且实际 diff 已确认时，才使用 `git add .`、`git add -A` 或等价整仓 stage。
- 生成物处理：提交前查看生成物、缓存或日志来源；与请求无关时保留不提交。
- 历史操作：默认创建新提交；只有用户明确要求 amend、rebase 或 reset 时，才执行历史改写类操作。
- 验证表述：最终回复和提交正文只陈述实际运行过的验证。
