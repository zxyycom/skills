# Decision Records

## 目标

在长期判断形成或拟议方向与既有判断冲突时，帮助 agent 恢复当前决定、识别必须遵守的约束、区分一次性例外与长期修订，并把已经确认且值得回放的判断维护为可继续使用的决策记录。

决策记录保存“项目决定往哪里走、为何这样选择、是否已经完整执行、后续必须保持什么”。`alignment` 只标记决策的完整目标是否已经执行并通过事实核对，不保存任务进度、执行日志或当前实现快照；代码、配置、规范和项目文档仍是当前事实来源。

## 内容 owner

1. 本文件面向 agent，承接触发后的读取路径、决策判断、动作选择和交付验收。
2. [decision-record-rules.md](references/decision-record-rules.md) 面向需要写入或结构维护的 agent，承接决策模型、内容边界、领域与身份语义、生命周期、关系、版本快照和维护不变量。
3. [decision-index.schema.json](references/decision-index.schema.json) 承接索引的精确机器结构；本文件和领域契约不复制字段顺序、版本、派生键或序列化细节。
4. `scripts/decision-records.mjs --help` 承接当前 CLI 参数；CLI 实现和校验承接精确输出、退出状态和索引操作细节。
5. [maintenance-recovery.md](references/maintenance-recovery.md) 只在 CLI 不可用、索引故障、写入中断或普通诊断不足时读取。

## 主动读取

1. 先读目标工作区指令和与当前任务直接相关的事实来源。
2. 按 `--root` 和可选的 `--decisions-dir` 定位决策集合；集合整体不存在时视为尚未初始化，不从 Git 状态推断决策是否存在或生效。
3. 日常恢复先运行 `list` 读取最近一次成功维护或同步后的索引快照。需要选择责任领域时运行 `domains`，需要完整理由时运行 `show`，需要理解演进关系时运行 `trace`。
4. 摘要足以完成当前判断时停止扩大读取；只有任务需要历史时才查询归档记录或完整关系图。
5. 相关活动决策尚未建立为当前基线时，完整读取决策并与当前事实来源比较，再决定本次差距和动作。
6. 只读恢复、冲突判断和未确认候选不加载领域契约；任何记录写入、状态变化、关系变化、领域变化、`pending` 决策快照构造或结构审阅前完整读取领域契约。
7. 只有工具、索引或中断写入不能通过普通 CLI 诊断处理时才读取恢复手册。

## 执行流程

### 1. 确定任务出口

1. 恢复、解释、检查或审阅已有决策时，只交付查询或审阅结果；没有维护授权时不扩大为写入。
2. 当前指令已经明确长期判断、维护对象和影响范围时，视为已经确认；新增记录或改变状态前告知将写入的判断和集合变化，然后直接维护。
3. 普通工作中形成重要取舍时，在自然更新或交付阶段提出候选；只有继续任务必须先确定该取舍时才即时提出。
4. 长期含义、适用范围或被改变的责任边界仍不清楚时，只确认会改变记录结果的最小问题。

### 2. 恢复当前判断

1. 从 `list` 的领域、路径、生命周期、对齐状态和摘要定位相关记录。
2. 从完整记录的目的恢复长期结果，从背景恢复选择依据，从决策恢复采用方向及必须遵守的限制。
3. `active` 表示决策已经确认并且当前适用；`aligned` 表示完整目标已经执行、与当前事实核对并建立为持续基线，`unaligned` 表示尚未完整执行，但所有相关工作必须考虑其后续落地并避免继续固化冲突方向。
4. 将当前任务归为以下一种情况：
   - 已对齐继续：遵守活动已对齐基线。
   - 向目标推进：活动未对齐，当前工作按决策正文中的方向和明确约束推进。
   - 明确的一次性例外：按当前指令完成本次任务，说明例外范围，状态和历史不变。
   - 长期修订：形成新的完整候选和真实直接关系。
   - 一致性问题：活动记录互相冲突、已对齐记录与当前事实偏离，或当前动作违反活动决策中的明确约束。
5. 已对齐记录发生事实偏离时不改回 `unaligned`；报告一致性问题。新的未来目标通过新决策表达。
6. 常规查询读取持久索引快照，不逐次证明全部 Markdown 新鲜度。手工修改来源、怀疑快照陈旧或准备维护时先运行严格 `check`，需要接受来源变化时运行 `sync-index --write`；不得用尚未同步的查询结果断言来源中不存在记录。

### 3. 提出候选决策

候选判断需要同时具备长期影响和回放价值。依次确认：

1. 它是否持续影响后续行为、责任边界、兼容性、风险处理或验收？
2. 缺少记录时，未来是否难以恢复为何采用当前方案？
3. 它是否是判断或取舍，而不是事实、任务、进度或执行结果？
4. 它是否能够独立修订或替代？需要分别演进的判断分别记录。

当前指令已明确表达判断时复用该确认。否则只给出目的、背景、采用方向、必须长期遵守的限制和必要的直接关系，等待确认后再写入。当前实现差距留在当前事实来源，不作为决策正文中的专门结构保存。

### 4. 选择动作

1. 既有活动决策适用时，按其方向与约束继续任务，不为普通执行创建新记录。
2. 当前指令只形成一次性例外时，限定本次范围并保持决策集合不变。
3. 既有方向仍成立但尚未完整执行时，按决策约束推进；完整执行并核对后再把它建立为当前基线。
4. 长期方向、理由或责任边界发生变化时，形成能够独立使用的新决策，并保存与直接前序的真实关系。
5. 既有活动决策互相冲突或已对齐基线与事实偏离时，报告一致性问题；没有新的长期判断时不通过改写历史掩盖冲突。

### 5. 维护记录

1. 完整读取领域契约，确认领域、稳定身份、记录内容、生命周期、关系和维护顺序。
2. 写好完整候选后，根据当前事实决定以 `aligned` 或 `unaligned` 激活；尚未完整执行时必须使用 `unaligned`，它已经约束后续相关工作，但不虚构实施完成。
3. 已确认目标后来得到完整执行时，在核对当前事实后标记为已对齐。
4. 决策演进时使用演进命令，或在激活新候选时显式提供直接关系，让前序归档、关系写入和新记录建立作为一次维护事务完成。若待归档记录尚未进入 Git `HEAD`，命令会先暂停且不写入；判断其是否具有长期回放价值后，显式选择保留未提交历史，或使用 `evolve` 折叠一个中间前序并声明由零个或多个关系组成的完整最终关系集合。
5. 折叠不自动继承或合成上游关系。存在分叉、多层中间链、其他引用或最终直接关系不清楚时保留现场并请求判断；`discard` 仍只用于不再需要的未激活候选。
6. 内容或领域来源发生编辑性变化时同步索引；不得直接修改派生索引来制造决策状态。

### 6. 构造待提交决策快照

1. 只有调用方明确要让一个或多个 `filesystem` 决策变化进入下一版本时才运行独立的 `stage <decision-path...>`；路径必须逐项显式选择，并共同形成一个合法决策集合。重命名同时选择旧路径和新路径，不从关系、差异或命令历史推断选择集。
2. `stage` 以当前 `revision` 决策集合为基线，只叠加所选路径在 `filesystem` 中的状态：新增或修改读取磁盘内容，删除由路径仍在 `revision` 但已不在磁盘表达。既有 `pending` 决策变化和未选择的其他磁盘变化都不参与目标构造。
3. 命令从同一目标来源重建并验证完整索引后，整体替换 `pending` 决策范围。最后一次成功调用决定该范围的完整内容；范围外既有 `pending` 内容和整个 `filesystem` 保持不变。生命周期命令仍直接读写磁盘决策文件，不读取、判断或写入 `pending`。
4. 指定路径、候选、领域或关系不能形成合法目标，版本管理环境不可用，或目标构造期间 `revision` 或受控 `pending` 前提发生变化时，按诊断修正选择或重新读取后重试；这些失败不接受部分结果。若工具报告 `pending` 范围恢复不完整，停止后续维护并保留诊断，不继续猜测或覆盖。
5. 当前分发实现只在可用的 Git 工作区中提供 `stage`。调用方只依赖 CLI 暴露的 `revision`、`filesystem`、`pending` 和项目路径语义，不解析或透传 Git 内部值。

### 7. 验证与交付

1. 确认记录只包含已经确认且值得长期回放的判断，目的、背景、采用方向和长期约束互相一致。
2. 标记已对齐前，将完整决策与当前事实来源逐项核对；保持未对齐时，从同一比较恢复实际差距。
3. 维护结束时运行严格 `check`，并清理全部未激活候选；中间命令的成功或 warning 不替代最终验收。
4. 写入时说明新增、修订、归档或对齐变化及验证结果；只读恢复时说明适用决策、当前分类和结果边界。

## CLI

从 skill 目录运行，或使用脚本绝对路径：

```text
node scripts/decision-records.mjs <command> [options] --root <resolution-root>
```

| 命令 | Agent 使用效果 |
| --- | --- |
| `domains` | 查看可选领域及其责任边界。 |
| `list` | 从持久索引按领域、生命周期或对齐状态恢复紧凑定位信息。 |
| `show` | 从索引定位并读取一条决策的完整 Markdown。 |
| `trace` | 查看一条决策的直接演进链路。 |
| `check` | 严格验证整个决策集合及派生索引。 |
| `sync-index --write` | 从当前领域定义和已建立记录重建查询索引。 |
| `stage` | 从当前 `revision` 与显式选择的 `filesystem` 决策构造完整、一致的 `pending` 决策快照，不修改磁盘决策集合。 |
| `activate` | 建立一个完整候选，或重新激活已归档记录并保留原建立时间和关系；只有新候选可以显式提供直接关系并同时完成演进事务，未进入 Git `HEAD` 的待归档前序会先触发预警。 |
| `evolve` | 在一次可恢复事务中归档活动前序、写入完整最终关系集合和激活新候选；也可以显式折叠一个未进入 Git `HEAD` 的中间前序。 |
| `mark-aligned` | 在完整执行并通过事实核对后建立当前基线。 |
| `archive` | 让活动决策退出当前依据并保留最后对齐状态与历史；目标尚未进入 Git `HEAD` 时先暂停，要求显式确认是否保留。 |
| `discard` | 删除尚未生效且可安全丢弃的完整候选。 |

`activate` 和 `evolve` 是面向不同 agent 意图的并行入口，可以产生相同的演进事务；`evolve` 额外提供显式折叠未记录中间前序的能力，不要求两者互斥。

`stage` 是独立的版本快照命令，不是生命周期选项；`activate`、`evolve`、`archive`、`mark-aligned` 和 `discard` 均不提供 `--stage`。

具体参数使用对应命令的 `--help`；索引的精确字段、版本和格式查看相邻 JSON Schema。写命令执行前读取领域契约；手工修改 Markdown 后先同步或严格检查，不从索引反向补造权威来源。

## 完成标准

1. 已恢复所有与当前任务直接相关的活动决策，并把任务归为遵守基线、向目标推进、一次性例外、长期修订或一致性问题。
2. 新记录只保存已经确认、具有长期影响和回放价值、能够独立演进的判断。
3. 决策与当前事实来源的关系已经核对；对齐状态准确表达是否完整执行，没有代替事实检查或放宽未对齐决策的约束。
4. 所有写入遵循领域契约，未激活候选已处理，派生索引没有被当作事实源。
5. 使用 `stage` 时，显式选择、目标领域目录表、全部目标 Markdown 与完整索引来自同一目标来源；`pending` 决策范围外内容和 `filesystem` 未被改变。
6. 严格 `check` 返回成功；无法运行时按恢复手册说明尚未证明的边界。
