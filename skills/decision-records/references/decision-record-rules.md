# 决策记录领域契约

本文面向需要创建、修订或维护决策记录的 agent，定义决策模型及写入时必须保持的语义和安全不变量。日常恢复与动作选择由 `SKILL.md` 承接；索引的精确机器结构由 [decision-index.schema.json](decision-index.schema.json) 承接；当前 CLI 参数、输出和退出状态以 `scripts/decision-records.mjs --help` 及实际诊断为准。

## 权威来源与职责

1. `SKILL.md` 决定 agent 何时恢复决策、如何判断当前任务以及何时进入维护。
2. 本契约决定什么是合法决策、领域和身份如何表达、生命周期与关系如何演进，以及写入必须满足什么条件。
3. `decision-domains.json` 是领域定义来源；每条决策 Markdown 是自身内容、生命周期、对齐状态和关系的来源。
4. `decision-index.json` 是从权威来源建立的持久查询快照，不拥有独立决策状态，也不作为领域或 Markdown 的反向修复来源。
5. 代码、配置、规范和项目文档是当前事实来源。决策记录保存长期方向和理由，不复制当前实现、任务进度或执行日志。
6. 本契约中的“内容 owner”只表示某项规则应由哪个文档完整承接；判断决策是否落实时以“当前事实来源”为准。

## 决策集合与稳定身份

未传 `--decisions-dir` 时，决策根目录是 `<root>/docs/decisions`；显式相对路径只相对 `--root` 解析，绝对路径直接作为决策根目录。决策集合不要求位于 Git 仓库。

```text
<decision-root>/
├── decision-domains.json
├── decision-index.json
└── <domain-id>/
    └── <semantic-slug>.md
```

1. 根目录只保存领域目录表、派生索引和已定义的一级领域目录；归档记录仍留在原领域，不建立物理归档目录。
2. 每条 Markdown 直接位于一个领域目录。未知目录、嵌套目录、领域目录中的非 Markdown 文件和已经存在但为空的领域目录均无效。
3. `<domain-id>/<semantic-slug>.md` 是稳定身份。文件名使用简短 kebab-case 语义名称，不包含日期、状态或一次性动作。
4. 路径第一段是唯一领域归属。领域纠正或结构迁移必须同时更新路径、全部关系目标、直接引用和派生索引。

## 受控领域

`decision-domains.json` 使用以下最小结构：

```json
{
  "schemaVersion": 1,
  "domains": [
    {
      "id": "workflow-governance",
      "description": "维护工作流中的批准、责任和长期治理边界。"
    }
  ]
}
```

1. `domains` 非空并按 `id` 升序排列；ID 是唯一 kebab-case 名称，描述用单行文本界定一个稳定责任或能力边界。
2. 一条决策选择拥有被改变契约的主要领域，不按正文中出现的名词、执行阶段或所有受影响对象归类。
3. 可以独立修订、替代或退役的跨领域判断分别记录；其他影响写入正文，不建立自由 tag 或 `impact` 字段。
4. CLI 的 `domains` 命令只读展示领域。新增领域或修改描述时直接编辑目录表；新增但尚无记录的领域不创建空目录。
5. 删除领域前必须确认没有决策路径继续使用该 ID。重命名、拆分或归并领域属于结构迁移，先处理全部路径、关系和直接引用，达到长期维护门槛时另行记录决策。
6. 领域变化后运行 `sync-index --write` 和严格 `check`；不得直接修改索引中的领域 metadata。

## 什么进入决策记录

只有同时满足以下条件的判断才进入记录：

1. 它会持续影响后续行为、责任边界、兼容性、风险处理或验收。
2. 缺少记录时，未来难以恢复为何采用当前方向。
3. 它是已经确认的判断或取舍，而不是事实、任务、进度或执行结果。
4. 它能够作为一个整体被独立修订、替代、判定无效或归并。

一条活动记录必须能够独立表达当前判断，不要求读者拼接前序。目的说明希望长期达成什么，背景说明为何需要选择，决策说明采用方向、核心理由以及必须长期遵守的限制、允许范围或例外。

## Markdown 记录

新候选和已建立记录使用同一结构，并保持所示 frontmatter 与正文顺序：

```markdown
---
title: <标题>
status: active
alignment: aligned
createdAt: null
purpose: <精简目的>
background: <精简背景>
decision: <精简采用方向>
relations: []
---

## 目的
- <希望长期达成或维护的结果>

## 背景
- <促成选择的事实、问题与关键约束>

## 决策
- 采用: <最终方向、核心理由和长期约束>
```

1. 标题和三项摘要是 4 至 100 个 Unicode 码点的单行文本；摘要不得引入对应正文没有表达的独立含义。
2. 正文只使用依次排列的 `目的`、`背景` 和 `决策` 二级章节，不重复一级标题、摘要或关系。
3. `决策` 至少包含一个非空 `采用`；关键备选确实有助于回放时可以增加 `不采用`。
4. 当前事实和实施差距不复制进正文。需要判断对齐时，将完整决策与当前事实来源比较。
5. 已建立记录只允许不改变目的、范围、关键背景、采用方向、核心理由或关系语义的编辑性修正；语义变化通过新记录和演进关系表达。

## 生命周期与对齐

| 状态 | 含义 |
| --- | --- |
| 候选：`createdAt: null` | 完整但尚未生效，不进入索引；可以继续收敛或安全丢弃。 |
| `active + aligned` | 决策已经确认且当前适用，完整目标已经执行并通过当前事实核对，后续相关工作必须遵守。 |
| `active + unaligned` | 决策已经确认且当前适用，但尚未完整执行；相关工作必须考虑后续落地并避免固化冲突方向。 |
| `archived + aligned/unaligned` | 不再作为当前依据，保留归档前最后执行状态以及理由和演进历史。 |
| 历史 `archived + alignment: null` | 不再作为当前依据，且归档前执行状态未知；只为兼容既有记录。 |

1. 首次 `activate` 写入不可变的建立时间，使候选成为已建立记录；Git 提交、暂存或历史不参与建立状态。
2. `active` 表示决策已经确认并且当前适用，必须结合 `alignment` 判断执行约束；`unaligned` 不表示可以忽略决策，也不自动增加或取消任何权限。
3. 对齐是从 `unaligned` 到 `aligned` 的单向执行基线；只有完整目标已经执行并通过当前事实核对后才能标记。已对齐记录后来与事实偏离时报告一致性问题，不把原记录改回未对齐。
4. 归档保留最后一个非空 `alignment`；新归档必须写入 `aligned` 或 `unaligned`，既有 `null` 只表示历史执行状态未知。已归档记录重新激活时保留原 `createdAt` 和既有关系，并由本次激活参数建立当前对齐状态。
5. 关系字段本身不隐式改变生命周期或对齐状态；激活、演进、对齐和归档都由显式维护动作完成。

## 演进关系

新判断改变已有决策时，在新记录中使用从新到旧的直接关系：

```yaml
relations:
  - type: 修订
    target: workflow-governance/direct-predecessor.md
```

1. `修订` 保留主体方向并改变一部分；`替代` 用完整新判断取代前序；`判定无效` 表明前序依据不成立；`归并` 把多个前序整合为一个可独立使用的当前判断。
2. 关系只指向直接前序；每个目标只出现一次并使用一个关系类型，不自环、不形成环。目标使用决策根目录相对 POSIX 路径，并在新记录建立事务完成时处于归档状态。
3. 关系只保存真实语义演进，不作为分类、引用列表或任务依赖。

## 维护不变量

1. 当前指令足以确认长期判断和维护范围时可以直接维护，但新增记录或改变状态前先告知用户将写入的判断和集合变化。
2. 写候选、编辑性修正和领域目录表维护可以直接修改权威来源；生命周期、对齐、归档和候选丢弃使用对应 CLI 命令。
3. 决策演进优先使用 `evolve`，也可以在 `activate` 新候选时显式提供直接关系。调用方给出的关系是该候选的完整关系集合；CLI 在一次事务中归档全部活动直接前序、写入关系、激活候选并重建索引，对可处理失败尽力恢复命令前的 Markdown 和索引组合。进程中断或恢复不完整时停止继续维护，并按恢复手册处理。
4. `activate` 和 `evolve` 是面向不同调用意图的并行入口，允许共享同一内部事务并产生等价演进结果；`evolve` 额外承接显式折叠未记录中间前序，不通过强制互斥制造额外状态语义。
5. Git `HEAD` 只用于归档前判断决策路径是否已经进入已提交基线，不参与候选、建立、生效、对齐或索引成员判断。当前 `HEAD` 中存在同一决策根相对路径即视为已经记录；文件内容、Git index 和工作区差异不改变该判断。尚无提交时，全部路径都视为未记录。
6. `evolve`、带关系的 `activate` 或 `archive` 即将归档未记录路径时，首次调用暂停、返回 warning 且不写入；调用方判断后显式确认保留未提交历史，或选择折叠。只有确认决策集合不在 Git 工作树内时才跳过预检；仓库发现或 `HEAD` 读取失败时停止且不写入。
7. `evolve` 只在显式提供 `--collapse-unrecorded` 时折叠一个活动、已建立且不在 Git `HEAD` 的中间前序。折叠目标不能仍被其他记录引用；零个或多个 `--relation` 参数共同构成后继的完整最终关系集合，已归档目标只能是折叠记录原有的直接前序，CLI 不自动继承或合成关系。非 Git 集合继续使用既有生命周期，不能在缺少版本证据时折叠。
8. 不使用复合演进命令时，先使用 `archive` 归档全部直接前序，再把关系写入候选并普通激活；不能只改变旧记录或只增加关系来表达新方向。归档预警仍需在动作前处理。
9. `activate` 建立候选或重新激活已归档记录，`evolve` 建立演进后的新候选，`mark-aligned` 在完整执行并核对后建立基线，`archive` 退出当前依据并保留最后执行状态，`discard` 只删除尚未生效且没有被引用的完整候选；不使用 `discard` 或通用删除动作重写已建立历史。
10. 状态命令完成后会更新查询投影；手工修改权威来源后运行 `sync-index --write`。任何情况下都不直接编辑派生索引。
11. 中间维护可以出现未激活候选 warning，但交付前必须激活或丢弃全部候选，并让严格 `check` 成功。
12. 无法确定的内容若会改变决策含义、生命周期、关系、建立时间或责任领域，保留现状并请求用户判断。

## 派生索引与查询

1. 索引从当前领域目录表和全部已建立 Markdown 完整生成，为 `list`、`show` 和 `trace` 提供持久查询快照；`domains` 直接读取领域目录表。
2. 索引 metadata 提供完整领域定义；每条记录的领域由路径确定，不在 Markdown 或索引 state 中重复维护另一份领域字段。
3. 常规查询直接读取结构有效的持久索引，不在每次查询前遍历全部 Markdown 或重算源 revision；`show` 只额外读取目标正文。索引表达最近一次成功生命周期事务或同步后的集合状态。
4. 生命周期事务负责同步 Markdown 与索引；手工修改领域定义、成员、路径或原文后，调用方必须运行 `sync-index --write`，并在维护或验收前运行严格 `check`。
5. 索引缺失、损坏或陈旧时可以从权威来源重建；不能从索引反向补造领域、生命周期、时间、正文或关系。
6. 精确字段、合法值、版本和结构以 [decision-index.schema.json](decision-index.schema.json) 为准；同步、规范化和 revision 等通用机制不在本契约重复说明。

## 验证

1. `check` 机械验证领域目录、路径、Markdown 结构与状态组合、关系、索引结构、新鲜度和成员一致性。
2. Agent 另外检查记录门槛、领域选择、目的与理由质量、摘要和正文语义一致性、关系是否为直接前序，以及标记已对齐前是否已有当前事实证据。
3. 工具或索引故障、写入中断或普通诊断不足时，停止猜测并读取 [maintenance-recovery.md](maintenance-recovery.md)。
