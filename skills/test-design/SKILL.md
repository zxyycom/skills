# Test Design

## 目标

设计和保留关键、必要、低成本的测试，识别值得防范的错误，并容忍保持契约的实现替换。范围限于当前请求的一条或一组测试。

- **关键**：按消费者依赖、失败影响和现实易错点选择保护目标。
- **必要**：相对其他保留证据提供值得其成本的新增证明；已有充分证明时复用。
- **低成本**：在证明足够的候选中，比较准备、运行、理解、变更与不稳定性成本。

## 任务与读取

先按请求区分设计、实施和只读审查：设计交付方案；实施在授权范围内改进测试、fixture 和必要入口；只读审查保持被评估材料不变，动态验证服从当前授权。

先读项目测试约定、行为 owner、相关实现与测试，有改动时读对应 diff；只补读会改变本次判断的职责链与邻近证据。产品契约由对应 owner 确定；生产重构、依赖安装和外部服务调用另需相应授权。

普通任务使用下方主流程；专门问题按[测试范式](references/test-patterns.md)标题定位：

- 对照已有实现补写或审查测试时，选读[已有实现下的常见误判](references/test-patterns.md#已有实现下的常见误判)。
- 细化阈值或条件组合时，选读[规则与边界矩阵](references/test-patterns.md#规则与边界矩阵)。
- 处理昂贵准备或进程复用时，选读[准备复用与独立执行](references/test-patterns.md#准备复用与独立执行)。

## 主流程

### 1. 选择值得保护的契约

从行为 owner、消费者要求或独立确认的缺陷恢复正确性依据，说明行为前提、应有结果及值得防范的错误。条款、分支或可构造错误的数量，不自动决定测试义务。

- 区分已确认契约、既有行为与假设；歧义会改变预期时向行为 owner 确认。只有当前输出依据时，可刻画行为或保护兼容性，但尚不证明行为正确。
- 源码用于理解职责、调用关系和可达场景；预期依据独立于当前实现，避免从现有分支反推正确答案。
- 重点保护项目自己的规则和消费责任；第三方通用机制仅在具体兼容风险或上游 Bug 需要保护时补测。

### 2. 按职责复用已有证据

按实际代码结构识别规则计算、变更计划、执行与结果消费等职责，核对相关测试实际承担的责任。一组测试的证据可以组合，单条只需证明限定范围。

- 规则、执行、副作用与失败保护各由所属职责层承担；上层聚焦选择、传递、结果映射和环境差异等具体衔接风险。
- 复用证据时，结合实现与已有测试核对前提、输入输出衔接和结果消费，仅为尚未被承接的责任补证。

### 3. 选择低成本边界与有效观察

选择证明充分、总成本较低的现有入口，层级作为默认参考。已有上层测试更简单、稳定且成本可接受时可保留；文件身份、Git 等目标语义仍由相应真实边界验证。

| 待证明的责任 | 默认边界 |
| --- | --- |
| 规则、状态计算、文本转换、解析与组合矩阵 | 纯函数或领域 API |
| 实际文件读写、路径身份、权限与恢复 | 必要的真实文件系统 |
| Git index、历史、锁或跨进程语义 | 隔离的真实 Git／进程 |
| 参数解析、输出、诊断与退出结果的接线 | CLI；参数矩阵可在等价入口下沉 |
| 制品启动、模块解析及安装位置 | 真实制品和目标运行时的代表性 smoke |

替身控制非目标依赖，目标行为仍实际执行；替身假设由真实边界证据或依赖契约支持。已有清楚入口时利用职责分离，所需生产结构调整另行提出。

以最少输入和明确动作组织场景。同一行为等价类先选代表，新增样例补足重要辨错缺口。

- 输入需能区分目标错误：排序有乱序，过滤有命中与干扰，消歧有冲突；数据规模只需跨过目标边界。
- 预期来自契约、独立算例、经审核的 fixture 或独立模型。
- 观察聚焦当前责任内的结果与必要保护，无关细节允许变化；数量、存在性或配置透传可以充分证明其各自限定责任。
- 负向场景从健康基线改变目标因素，观察对应失败原因及本层受保护状态。纯规则可直接构造值；来源、身份或真实环境属于目标时经过相应入口。

名称和断言准确表达本条范围；helper 保持场景和失败位置可追踪，一组断言可共同证明当前责任，独立意图按原生节点组织。

控制无关环境，共享只读材料，隔离可变资源；等待实际完成并回收资源。随机反例可复现且不泄露敏感数据。

### 4. 校准必要性与实现兼容性

结合本条职责和整组已有证据判断：

- **辨错**：值得防范的重要错误，是否已有有效观察使运行器报告失败？
- **替换**：保持契约而更换实现，是否仍应通过？内部顺序、调用次数、源码或私有形状的约束须有使用、兼容、安全或资源依据。
- **增量**：新增测试、场景、断言或真实边界，相比已有证据增加了什么，是否值得其成本？

据此选择保留、缩减、合并、下沉、移除或在责任所属层补齐；名称过宽时澄清范围。

移除或转移测试前，说明关键责任仍由哪些有效证据承担，避免互相引用待删除项。相同结果不等于相同责任；承接尚未就绪时保留原测试或明确缺口，接受保护减少时说明具体风险。

确保断言失败能传到运行器；被测对象会捕获或转换 callback、getter 或 hook 异常时，按[回调与失败传播](references/test-patterns.md#回调与失败传播)安排外层观察或精确结算。

### 5. 按任务验证并交付

- **设计或只读审查**：交付目标责任、可复用证据、推荐处置与实际缺口；区分静态推断、已有运行记录与本轮动态验证。未实现方案给出验收方法即可。
- **编写或改进**：运行目标测试，确认 runner 实际发现、选择并报告预期节点，没有意外 skip 或遗漏异步工作，并接入项目要求的聚合入口。移动、拆合、降层或去重后，运行受影响的邻近测试和项目要求的检查。
- 风险或辨错证据的不确定性值得额外成本时，在授权且可隔离的范围内补充[回归敏感性验证](references/test-patterns.md#针对性变异与回归敏感性)，确认目标错误导致断言失败。
- 并发、随机或环境相关改动按风险补充单独、组合或重复运行；报告首次失败及其原因，重试通过不能代替解释。
- 产品缺陷与测试缺陷分别处理；不得靠放宽断言、盲目刷新快照、提高超时或删除失败测试掩盖未解决的产品问题。

沿用当前任务的交付形式，说明方案或改动、保留与移除的关键责任、成本取舍、实际验证和未覆盖边界。测试数量、覆盖率和耗时是辅助信息，不单独作为质量结论。

测试账本、覆盖率政策与 Gate 由项目 owner 管理。项目采用 `test-evidence-review` 时，将最终入口和证明范围交给它；本 skill 可独立使用，不自行创建账本或新增管理流程。

## 自更新

本 skill 的指令使用不需要安装依赖。仅在本 skill 目录运行自更新入口 `node scripts/update-skill.ts` 时，需满足随包 `package.json` 的 Node 版本与兼容依赖。
已有兼容宿主依赖即可复用；普通运行、导入与检查不自动安装。依赖不可用时，使用随包 manifest 固定的 pnpm 显式执行：

```bash
pnpm --dir "<skill-directory>" install --ignore-workspace --prod --frozen-lockfile --config.node-linker=isolated
```

运行时文件或 manifest/锁文件损坏时，重新获取完整 skill 后再安装并重试。更新覆盖正式包中的同路径文件、保留其余本地文件。源码更新成功不证明依赖兼容；需要时按新包锁文件显式安装。
