# Test Design

## 目标

选择经得起举证的关键、必要、低成本测试。保留是准入结果，不是存量测试的默认状态；现有测试、Case 声明和历史覆盖率均不授予保留资格。

新增与存量共同通过有效性、保护价值、当前形态与开销三项门槛。重要契约也可以不自动化；不承担自动检查，契约本身仍然有效。

## 任务入口与读取

| 任务 | 入口 |
| --- | --- |
| 新增测试 | 从行为、消费者与独立确认的缺陷形成最小候选方案，再举证准入 |
| 存量审查 | 盘点范围内现有测试，全部作为待审候选；通过举证者才进入最终保留集合 |

设计交付方案；只读审查保持被评估材料不变；实施按授权处置测试、fixture 和入口。删除、动态验证、生产改动、依赖安装及外部调用服从当前授权。

1. 读取项目测试约定、行为 owner、消费者、相关实现和测试；核对当前 diff、范围及明确的自动化要求。
2. 举证前读取[易错判断集](references/judgment-pitfalls.md)，校准准入、职责与误删边界。
3. 形成、比较或改进候选时，按需读取[设计与实现要点](references/test-patterns.md#设计与实现要点)及矩阵、恢复等范式；方法比较可以先于准入，详细实现只投入已选方案。

## 主流程

### 1. 恢复候选及其依据

说明候选保护什么、使用何种输入和观察，核对独立行为依据及已有设计和检查。存量以实际测试体为准；新增方案须足以比较价值、可行性和成本。

每条测试只在自身职责内举证，不要求包办调用链或下游副作用。交互本身值得保护时，将交互另作候选目标。

契约由行为 owner 确定；区分契约、当前行为与假设。源码、名称及 Case 自述用于恢复现状，不能自证正确或必要；只有当前输出依据时，明确其行为刻画范围。

### 2. 举证准入

每个候选须同时证明：

1. **有效性**：关键输入、独立预期及实际观察如何识别目标错误，失败能否传到运行器；保持契约的合理实现替换仍能通过。断言或替身只复述实现不成立。
2. **保护价值**：谁依赖该行为，错误影响和现实风险是什么；相对实际适用的设计约束与最终保留检查，增加什么值得自动拦截的保护。模块重要或可构造错误不足以成立。
3. **当前形态与开销**：证明这些场景、断言、规模、准备和执行边界为何需要保留；比较现实可行方案的准备、运行、理解、变更、环境与不稳定性总成本。有效且有价值，也不能豁免当前形态的举证。

三项依据须落到具体候选。判断一致时可成组说明，有争议时拆到场景或断言；重要大类不能授予整组资格。静态举证对照实际测试体，关键有效性仍存疑时再作[针对性验证](references/test-patterns.md#针对性变异与回归敏感性)或列出具体缺失事实。

### 3. 按准入结果处置

| 结果 | 处置 |
| --- | --- |
| 准入：三项均成立 | 当前形态可保留；新方案可建立 |
| 不准入：已核对事实，任一项不成立 | 当前形态不保留；提出删除、精简、降级或退出自动化的处置 |
| 未决：必要事实未核对，或准入所需决定超出授权 | 明确缺失事实或所需决定，不计入已证明应保留，也不按完成审核结项 |

事实查清却缺少依据，判不准入，不以“待确认”保留。不准入可直接退出；修复、精简、降级或替代方案都是新候选，须独立通过三项门槛，不能继承旧资格或称为“保留待修复”。

无等价替代也可退出，说明失去的保护并在授权内接受风险；人工检查等按需选择，不自动产生补测任务。硬性自动化要求交 owner 决定处置，不自行绕过，也不当作已通过准入。

实现边界影响准入时，按需进入[设计反馈与重新裁决](#设计反馈与重新裁决)。

### 4. 复核、验证并交付

处置前复核误删：测试失败可能反映真实产品缺陷，缺少职责外观察不构成缺陷，相似输出可能属于不同责任。核对最终保留项，避免以待删项声称保护已承接；复核不要求保护总量不减少。

实施仅执行获授权的处置，运行目标、受影响的邻近测试及项目检查；核对 runner 实际选择、报告的节点、意外 skip 和异步工作。修改后的候选重新核对准入，产品缺陷与测试缺陷分别交付，首次失败须解释。

交付以最终准入集合为主：

- **保留或拟建立项**：定位候选及三项依据，分别标明方案准入、实际实现与执行验证状态。
- **不准入与未决项**：说明依据、删除或降级等处置、失去的保护、接受的风险及具体未决事实。
- **证据范围**：分别说明读取、裁决与执行范围，以及实现反馈和实际变化；静态判断、已有运行记录与本轮验证分别报告。

**结项自检**：每个保留结论均有三项准入依据，缺陷清单或总体指标不能替代；依据可成组说明，不设删除比例或逐条长证明要求。

测试账本、覆盖率政策与 Gate 由项目 owner 管理。采用 `test-evidence-review` 时，以最终入口、实际证明范围及保护变化交接；本 skill 不自行新增账本或管理流程。

## 设计反馈与重新裁决

当候选准备过重、职责混杂、边界难观察，且调整实现可能改变准入结果时，比较保留现状、调整测试、退出自动化与有限实现调整。

1. 区分测试范围、价值不足、实现职责问题与固有复杂性；难测不自动证明设计有错。
2. 比较实现与测试的整体成本、行为与兼容性变化、新增状态或失败风险。行为或实现 owner 决定方案，生产改动按授权实施；契约变化先确认，再改预期。
3. 实际变化后，仅对受影响范围回到候选与准入门槛：旧测试可以退出、降级或重设计，新风险同样举证。未落地方案只支持条件处置，不能计作已有保障。

只读审查交付当前结论与条件方案；不自动扩成架构审查、全面纯函数化或逐层补测。

## 自更新

本 skill 的指令使用不需要安装依赖。仅在本 skill 目录运行自更新入口 `node scripts/update-skill.ts` 时，需满足随包 `package.json` 的 Node 版本与兼容依赖。
已有兼容宿主依赖即可复用；普通运行、导入与检查不自动安装。依赖不可用时，使用随包 manifest 固定的 pnpm 显式执行：

```bash
pnpm --dir "<skill-directory>" install --ignore-workspace --prod --frozen-lockfile --config.node-linker=isolated
```

运行时文件或 manifest/锁文件损坏时，重新获取完整 skill 后再安装并重试。更新覆盖正式包中的同路径文件、保留其余本地文件。源码更新成功不证明依赖兼容；需要时按新包锁文件显式安装。
