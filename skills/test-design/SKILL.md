# Test Design

## 目标

让测试识别目标错误、容忍保持契约的实现替换，并以必要的运行与维护成本持续提供证据。范围限于当前请求的一条或一组测试。

## 任务与读取

先按请求确定工作方式：

- **设计**：形成可实施的测试方案与验收方法。
- **编写或改进**：在授权范围内实现测试、fixture 和必要入口调整，并验证结果。
- **只读审查**：保持被评估材料不变，交付问题、依据和建议；动态验证按当前授权决定。

先读项目测试约定、行为 owner、相关实现与测试及邻近证据；有待评估改动时再读对应 diff。产品契约由对应 owner 确定；生产重构、依赖安装和外部服务调用需要相应授权，不因改测试自动获准。

普通任务使用下方主流程。需要进一步细化[边界矩阵](references/test-patterns.md#规则与边界矩阵)或[准备复用](references/test-patterns.md#准备复用与独立执行)时，选读对应章节；其他专门问题按[测试范式](references/test-patterns.md)标题定位。

## 主流程

### 1. 明确行为与场景

用一句话连接前提、应有行为和一个可能违反它的实现。区分已确认契约、既有行为与假设；歧义会改变预期时，先向行为 owner 确认。

- 从契约选择能区分目标错误的正常、边界或失败场景；同一行为等价类先选代表，新增样例用于补足已有样例的辨错缺口。
- 邻近测试已有充分证据时复用或补强。移除重复测试前指出仍保留的入口与有效观察，避免互相指向待删除项；相似代码、底层调用或结果不等于相同证明责任。
- 重点证明项目自己的规则、配置、结果映射和消费接线；第三方通用机制仅在具体兼容风险或上游 Bug 需要保护时补测。没有独立价值的测试优先在授权范围内移除。

### 2. 选择最小充分边界

选择能保留必要观察、总成本较小的现有入口，并回答：**再降一层会失去什么？**

| 待证明的责任 | 默认边界 |
| --- | --- |
| 规则、计算、解析与组合矩阵 | 纯函数或领域 API |
| 文件内容、路径身份、权限与恢复 | 必要的真实文件系统 |
| Git index、历史、锁或跨进程语义 | 隔离的真实 Git／进程 |
| 参数解析、输出、诊断与退出结果的接线 | CLI；参数矩阵可在等价入口下沉 |
| 制品启动、模块解析及安装位置 | 真实制品和目标运行时的代表性 smoke |

替身用于控制非目标依赖，目标行为仍须实际执行；替身假设应由真实边界证据或依赖契约支持。降层保留原有证明责任，缺少等价入口时保留原测试或说明缺口；所需生产结构调整另行提出。

### 3. 组织输入、动作、预期与观察

让测试现场能恢复以下四项：

| 要素 | 设计要求 |
| --- | --- |
| 输入与初态 | 满足目标路径前提，以最少数据区分错误：排序有乱序，过滤有命中与干扰，消歧有冲突。规模由功能边界决定。 |
| 动作 | 从选定入口执行目标行为，等待实际完成；步骤之间的状态保留应有明确意图。 |
| 独立预期 | 来自契约、独立算例、审核过的 fixture 或独立模型，而非被测函数、同一生产常量或算法。配置值透传比较只证明接线。 |
| 观察 | 检查目标值、身份、内容、顺序及必要副作用；精确度与契约一致，只有存在性或数量确为目标时才以其作为充分证据。 |

- 纯领域测试可直接构造合法值；来源、身份或接线属于目标时经过真实入口。非法内部状态仅用于该层承担的防御责任。
- 负向场景从可信健康基线改变目标因素，检查具体失败原因和受保护状态。确认应存在的观察对象、分支或回调实际出现；合法空结果按其语义验证。
- helper 可复用构造、机械操作和语义明确的断言，场景输入、预期与失败位置保持可追踪。一组断言可共同证明一个行为，独立意图按框架原生节点组织。
- 核对测试名称承诺的行为与关键条件是否被实际输入、执行和断言支撑。名称夸大时收窄；必要契约缺少证据时补强测试，不以改名掩盖缺口。名称与失败消息应支持定位。
- 控制与目标无关的环境变量、工作目录、配置、时钟和随机源；被测环境差异保留独立场景。测试私有化可变资源，共享只读材料；等待可观察事件，确保异步完成、局部替换恢复和资源回收。随机反例应可复现且不泄露敏感数据。

### 4. 校准辨错与重构兼容性

- **目标错误**：漏过滤、边界偏一、返回旧值或遗漏回滚时，哪项观察会让测试运行器报告失败？
- **合理替换**：保持契约而更换实现后，测试是否仍应通过？

前者不清楚时补强输入或观察；后者不成立时检查实现耦合。内部顺序、精确调用次数、源码文本与私有形状，仅在承接稳定协议、资源预算或安全等契约时锁定。

断言失败必须能传到运行器。被测对象会捕获或转换 callback、getter 或 hook 异常时，记录实际观察并在外层断言，或以精确结算保证内部断言失败会导致测试失败；详见 [回调与失败传播](references/test-patterns.md#回调与失败传播)。

### 5. 按任务验证并交付

- **设计或只读审查**：交付场景、推荐边界、必要观察及证据缺口；区分静态推断、已有运行记录与本轮动态验证。未实现方案给出验收方法即可。
- **编写或改进**：运行目标测试，确认 runner 实际发现、选择并报告预期节点，没有意外 skip 或遗漏异步工作，并接入项目要求的聚合入口。移动、拆合、降层或去重后，运行受影响的邻近测试和项目要求的检查。
- Bug 回归和高风险弱证据在授权且可隔离时补做 [针对性变异验证](references/test-patterns.md#针对性变异与回归敏感性)。并发、随机或环境相关改动按风险补充单独、组合或重复运行；报告首次失败及其原因，重试通过不能代替解释。
- 产品缺陷与测试缺陷分别处理；不得靠放宽断言、盲目刷新快照、提高超时或删除失败测试掩盖未解决的产品问题。

沿用当前任务的交付形式，说明方案或改动、保留与移除的证明责任、实际验证和未覆盖边界。测试数量、覆盖率和耗时是辅助信息，不单独作为质量结论。

测试账本、覆盖率政策与 Gate 由项目 owner 管理。项目采用 `test-evidence-review` 时，将最终入口和证明范围交给它；本 skill 可独立使用，不自行创建账本或新增管理流程。

## 自更新

本 skill 的指令使用不需要安装依赖。仅在本 skill 目录运行自更新入口 `node scripts/update-skill.ts` 时，需满足随包 `package.json` 的 Node 版本与兼容依赖。
已有兼容宿主依赖即可复用；普通运行、导入与检查不自动安装。依赖不可用时，使用随包 manifest 固定的 pnpm 显式执行：

```bash
pnpm --dir "<skill-directory>" install --ignore-workspace --prod --frozen-lockfile --config.node-linker=isolated
```

运行时文件或 manifest/锁文件损坏时，重新获取完整 skill 后再安装并重试。更新覆盖正式包中的同路径文件、保留其余本地文件。源码更新成功不证明依赖兼容；需要时按新包锁文件显式安装。
