# Test Design

## 目标

围绕关键行为，以实现与测试的合理总成本选择必要的自动化保护。先裁定投入，再设计测试；遇到影响取舍的实现问题时反馈设计，并按实际变化重新裁决。

新增与存量采用同一标准，已有测试是候选，保留与修复均须有投入依据。重要契约也可以明确不自动化，契约本身仍然有效。

## 任务与读取

用户已明确保护点与投入边界时沿用该决定，只复核会改变取舍的新事实。

设计交付方案；只读审查保持被评估材料不变；实施按授权改进测试、fixture 和入口。删除、动态验证、生产改动、依赖安装及外部调用服从当前授权。

1. 读取项目测试约定、行为 owner、消费者、相关实现与测试，有改动时读 diff；只补读会改变当前判断的材料。
2. 开始取舍前读取[易错判断集](references/judgment-pitfalls.md)，校准投入、职责与证据边界。
3. 决定投入后，再读取[设计与实现要点](references/test-patterns.md#设计与实现要点)，按保护点选读矩阵、恢复、并发等范式。

## 主流程

### 1. 识别行为、已有保障与风险

从行为契约、消费者需求或独立确认的缺陷，确定保护点：行为前提、应有结果、错误影响及现实易错因素。核对当前设计与已有检查提供的保障，按实际适用范围识别剩余风险。

每条测试在自身职责内独立判定成败，不因关联调用扩大证明义务。交互本身值得保护时，将交互作为测试目标；成本比较不改变这一责任范围。

契约由行为 owner 确定；源码、测试名称和 Case 自述帮助恢复现状，不能代替契约依据或投入裁决。区分契约、当前行为与假设；只有当前输出依据时，按行为刻画交付，不冒充正确性证明。

### 2. 裁定是否投入自动化

先于断言修补，为具体保护点比较：

- **收益**：谁依赖该行为、错误影响及现实风险；在当前设计和已有检查之外增加什么保护。契约存在或可构造错误本身不足以证明投入价值。
- **总成本**：准备、运行、理解、变更、环境与不稳定性成本，包括未来持续承担的开销。
- **可行方案**：比较现有测试与更简单的入口，选择有效信号。实现边界影响成本或可行性时，先按[设计反馈与重新裁决](#设计反馈与重新裁决)比较方案。

| 裁决 | 后续路径 |
| --- | --- |
| 收益值得总成本，自动化投入成立 | 进入下一步选择保护方式 |
| 收益不足，或可行自动化仍超出可接受成本 | 不新增；对存量提出移除或退出自动化的处置，说明减少的保护 |
| 影响决定的事实未核对，或风险取舍超出授权 | 标明具体未决事实或所需决定，不按已完成取舍结项 |

事实查清却没有投入依据，属于举证不成立，不是未决；仅投入成立的目标进入测试设计、修复或替换。

不自动化时说明哪些错误不受自动拦截，在授权内接受风险。人工检查等替代方案按需选择，不自动产生补测义务或待办；已有硬性验收要求交对应 owner 决定。

### 3. 为入选目标选择测试

针对已决定投入的保护点，选择有效且总成本较低的方式：

- 已有测试充分且经济：保留，说明其输入与观察如何识别目标错误。
- 同一保护点重复或当前形态过重：选择代表，缩减、合并、下沉或移除重复项；按需比较相关测试，相似输出不等于同一责任。
- 缺少有效且合适的测试：才提出设计、修复或替换方案。

样例与断言只锁定入选保护点，无关约束可退出，无需补等价测试。合并或替换后核对实际保留项与缺口，避免相互以待删除项作依据。

按[设计与实现要点](references/test-patterns.md#设计与实现要点)落实边界、输入、独立预期、有效观察和失败传播。校准两个方向：目标错误应使测试失败，保持契约的合理实现替换应能通过。

若边界或成本改变投入依据，先反馈设计或回到步骤 2 重新裁决。

### 4. 验证裁决并交付

- **裁决**：定位保护点及相关测试、场景或断言，说明投入依据与处置。有设计反馈时补充实现影响、所需决定和条件方案；相同判断可成组说明，不设删除比例或逐条长证明要求。
- **实施**：仅执行已裁定且获授权的处置，运行目标、受影响的邻近测试及项目检查，确认 runner 实际选择并报告预期节点，没有意外 skip 或遗漏异步工作。
- **证据范围**：分别说明裁决、读取、执行范围，以及接受的风险、替代未就绪的缺口和未决事项；区分静态判断、已有运行记录与本轮验证。

存量审查须有具体投入裁决，全部保留也须举证；模块重要、全绿、数量、覆盖率或耗时均不能代替取舍。

产品缺陷与测试缺陷分别交付，删除测试不表示产品缺陷已解决。风险值得额外成本时，再作[回归敏感性验证](references/test-patterns.md#针对性变异与回归敏感性)或其他针对性运行；首次失败仍需解释。

测试账本、覆盖率政策与 Gate 由项目 owner 管理。采用 `test-evidence-review` 时，以最终入口、证明范围及保护变化交接；本 skill 不自行新增账本或管理流程。

## 设计反馈与重新裁决

这是步骤 2、3 的按需分支：准备过重、职责混杂、边界难观察或保护价值存疑，且调整实现可能改变取舍时进入；其余情况继续主流程。

1. **定位原因**：区分测试范围过大、目标不值得投入、实现职责问题与行为固有复杂性。难测是调查信号，不自动证明设计有错。
2. **比较整体得失**：比较保留现状、调整测试、不自动化与有限实现调整，计入实现和测试的变更及维护成本、行为与兼容性影响、新增状态或失败方式。
3. **确认改变边界**：行为或实现 owner 决定设计与契约变化，生产改动按授权实施。区分重构与契约变化，先确认新契约再改预期；未落地方案只支持条件处置，说明前提与期间风险。
4. **重新裁决**：按实际变化，仅对受影响范围回到步骤 1、2。原目标退出或风险被有效约束时可移除、精简或降级；投入仍成立而职责迁移、旧测试失效时重新设计；新风险另作投入裁决。

只读审查交付当前裁决与条件方案；本分支不自动扩成架构审查，也不要求全面纯函数化或逐层补测。

## 自更新

本 skill 的指令使用不需要安装依赖。仅在本 skill 目录运行自更新入口 `node scripts/update-skill.ts` 时，需满足随包 `package.json` 的 Node 版本与兼容依赖。
已有兼容宿主依赖即可复用；普通运行、导入与检查不自动安装。依赖不可用时，使用随包 manifest 固定的 pnpm 显式执行：

```bash
pnpm --dir "<skill-directory>" install --ignore-workspace --prod --frozen-lockfile --config.node-linker=isolated
```

运行时文件或 manifest/锁文件损坏时，重新获取完整 skill 后再安装并重试。更新覆盖正式包中的同路径文件、保留其余本地文件。源码更新成功不证明依赖兼容；需要时按新包锁文件显式安装。
