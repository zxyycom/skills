# Test Design

## 目标

以合理总成本选择值得承担的自动化保护：先决定测不测，再决定怎么测。新增与存量采用同一投入标准；已有测试是候选方案，发现其缺陷不自动产生修复任务。

契约是否重要与是否值得自动化分别判断。不自动化可以是正式结论，契约本身仍然有效。

## 任务与读取

审查测试默认先裁定保留必要性，再评价入选项的实现质量。用户已明确保护点与投入边界时沿用该决定，只核对会改变取舍的新事实。

设计交付方案；只读审查提出取舍、保持被评估材料不变；实施按授权改进测试、fixture 和入口。实际删除、动态验证、生产重构、依赖安装及外部调用均服从当前授权。

1. 读取项目测试约定、行为 owner、消费者、相关实现与测试，有改动时读 diff；只补读会改变当前判断的材料。
2. 开始取舍前读取[易错判断集](references/judgment-pitfalls.md)，校准投入、职责与证据边界。
3. 决定投入后，再读取[设计与实现要点](references/test-patterns.md#设计与实现要点)，按保护点选读矩阵、恢复、并发等范式。

产品契约由行为 owner 确定；测试名称、Case 自述和当前实现只帮助恢复现状，不自行构成自动化投入依据。

## 主流程

### 1. 识别行为与风险

从行为契约、消费者需求或独立确认的缺陷，恢复当前范围内的具体保护点：行为前提、应有结果、错误影响及现实易错因素。先说明希望防范什么，再将旧测试视为候选。

每条测试在自身职责内独立判定成败，不因关联调用扩大证明义务。交互本身值得保护时，将交互作为测试目标；成本比较不改变这一责任范围。

区分契约、当前行为和假设。源码用于理解职责和可达场景，不从现有分支反推正确预期；只有当前输出依据时，明确行为刻画范围，不能据此证明正确性。

### 2. 裁定是否投入自动化

先于断言修补，为具体保护点比较：

- **收益**：谁依赖该行为、错误的影响与现实风险，自动拦截能带来什么价值。契约存在、条款数量或可构造错误本身不足以成立。
- **总成本**：准备、运行、理解、变更、环境与不稳定性成本，包括未来持续承担的开销。
- **可行方案**：能否以可接受成本取得有效信号，是否已有更简单的入口或足够的现有测试。

| 裁决 | 后续路径 |
| --- | --- |
| 收益值得总成本，自动化投入成立 | 进入下一步选择保护方式 |
| 收益不足，或可行自动化仍超出可接受成本 | 不新增；对存量提出移除或退出自动化的处置，说明减少的保护 |
| 影响决定的事实未核对，或风险取舍超出授权 | 标明具体未决事实或所需决定，不按已完成取舍结项 |

事实已查清却没有投入依据，属于举证不成立，而不是未决。只有投入成立的目标才能进入测试设计、修复或替换。

不自动化时明确契约仍有效、哪些错误不受自动拦截，并在授权内接受相应风险。人工检查等替代方案按需选择，不自动产生补测义务或待办；已有硬性验收要求交对应 owner 决定，不能自行绕过。

### 3. 只为入选目标选择与改进测试

针对已决定投入的保护点，选择有效且总成本较低的方式：

- 已有测试充分且经济：保留，说明其输入与观察如何识别目标错误。
- 同一保护点重复或当前形态过重：选择代表，缩减、合并、下沉或移除重复项；按需比较相关测试，相似输出不等于同一责任。
- 缺少有效且合适的测试：才提出设计、修复或替换方案。

样例与断言围绕入选保护点收敛，无关约束可退出，无需补等价测试。合并或替换后核对实际保留项，避免互相以待删除项作依据；替代未就绪时明确缺口，不虚称保护已承接。

按[设计与实现要点](references/test-patterns.md#设计与实现要点)落实边界、输入、独立预期、有效观察和失败传播。校准两个方向：目标错误应使测试失败，保持契约的合理实现替换应能通过。

### 4. 验证裁决并交付

- **设计或只读审查**：交付投入或不投入的裁决、价值与成本依据，再交付入选项的保留或改进方案。定位到具体保护点及相关测试、场景或断言；相同判断可成组说明，不设删除比例或逐条长证明要求。
- **实施**：仅执行已裁定且获授权的处置，运行目标、受影响的邻近测试及项目检查，确认 runner 实际选择并报告预期节点，没有意外 skip 或遗漏异步工作。
- **证据范围**：分别说明已完成取舍、实际读取和执行的范围，以及不自动化后接受的风险、替代未就绪的缺口和未决事项；区分静态判断、已有运行记录与本轮验证。

存量审查以具体保护点的投入裁决结项，缺少裁决即未完成。全部保留也须有相应依据；模块重要、测试全绿及数量、覆盖率、耗时不能代替取舍。

已知产品缺陷与测试缺陷分别交付，移除测试不表示产品缺陷已解决。风险值得额外验证成本时，再补充[回归敏感性验证](references/test-patterns.md#针对性变异与回归敏感性)或并发、随机及环境相关的针对性运行；首次失败仍需解释。

测试账本、覆盖率政策与 Gate 由项目 owner 管理。采用 `test-evidence-review` 时，以最终测试入口、实际证明范围及接受的保护变化交接；本 skill 不自行创建账本或新增管理流程。

## 自更新

本 skill 的指令使用不需要安装依赖。仅在本 skill 目录运行自更新入口 `node scripts/update-skill.ts` 时，需满足随包 `package.json` 的 Node 版本与兼容依赖。
已有兼容宿主依赖即可复用；普通运行、导入与检查不自动安装。依赖不可用时，使用随包 manifest 固定的 pnpm 显式执行：

```bash
pnpm --dir "<skill-directory>" install --ignore-workspace --prod --frozen-lockfile --config.node-linker=isolated
```

运行时文件或 manifest/锁文件损坏时，重新获取完整 skill 后再安装并重试。更新覆盖正式包中的同路径文件、保留其余本地文件。源码更新成功不证明依赖兼容；需要时按新包锁文件显式安装。
