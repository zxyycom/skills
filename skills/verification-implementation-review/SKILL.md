# Verification Implementation Review

## 目标与使用边界

审查测试与工程校验实现，先确定它是项目拥有的独立验证入口，还是另一个入口内部的实现环节，再判断证据是否可靠并维护 case。核心映射固定为：

```text
一个保留的独立验证入口 <-> 一个 case
```

以下任务使用本 skill：

1. 新增、修改、删除或审查测试与工程校验实现。
2. 查询、整理或修复已经登记的验证 case。

验证实现分为：

1. `test`：安排输入、状态或交互，并断言可观察结果。
2. `check`：对代码、schema、生成物、依赖或工程状态应用规则，主要产物是可复核的通过、失败或诊断结论。

主要产物是业务行为、运行时防御、转换结果或构建产物的实现不是 check，即使命令可能失败。普通业务代码修改、只运行既有测试、lint、类型检查或构建、只修复被检查对象，以及业务运行时输入校验不触发本 skill；任务同时修改验证实现时，由验证实现部分触发。

审查、查询和评估请求保持只读。只有修改请求才更新验证实现、行为 owner、case 目录、配置或派生索引。

## 核心判断：独立入口还是内部环节

独立验证入口是项目明确采用的稳定选择或调用单元。维护者能够直接把它作为验证目标，它的执行会产生可归属于该入口的最终判定。入口可以表现为测试入口、文件、规则 ID、package script、task、CLI 命令、CI job 或其他项目拥有的稳定目标。

按以下结果处理：

| 判断结果 | 判断标准 | Case 动作 |
| --- | --- | --- |
| 保留的独立入口 | 项目把它作为稳定验证目标，并接收它自身的最终判定 | 必须恰好登记一个 case |
| 保留的内部环节 | 只在父入口内执行，结果只用于组成父入口的判定 | 归入明确的父 case，不单独登记 |
| 不保留的实现 | 没有新增证明价值、信号不可靠，或维护成本明显高于价值 | 删除或不新增，不登记 case |
| 归属待确认 | 无法判断是否为稳定目标、最终判定属于谁，或父入口未知 | 报告缺口；不能以未登记状态完成修改任务 |

项目直接配置为提交、CI 或发布 gate 的验证目标是独立入口。项目直接采用的聚合命令或 CI job 也是独立入口，即使它只编排其他验证；只通过该入口执行的子步骤归入父 case。子步骤同时被项目作为稳定验证目标使用时，再为它建立自己的 case。

技术上能够 import、直接调用或被 runner 临时筛选，不足以证明项目把它作为独立入口。入口身份以项目脚本、CI、规则配置、测试策略或其他当前项目事实为准。

同一 case 可以有多个 `Entry:` locator，但它们必须是同一逻辑入口的不同定位方式。内部辅助实现不写入 `Entry:`；内部环节后来成为项目独立目标时，从父 case 拆出自己的 case。

## 内容 owner 与读取路径

1. 本文件承接触发判断、入口归属、证据评估、处置流程、写入授权和完成标准。
2. [catalog-contract.md](references/catalog-contract.md) 承接 case 字段、派生索引、配置、CLI 和机器接口的固定契约。
3. `scripts/verification-catalog.mjs` 只校验、同步和查询显式 case。它不发现入口、不执行 Entry、不修改 case 正文，也不判断入口身份、父子归属或证明价值。
4. [migrate-from-test-evidence-review.md](references/migrate-from-test-evidence-review.md) 只在工作区仍使用旧名称、旧配置、旧 CLI、源码 marker 或旧 case 字段时读取。
5. 项目行为 owner 承接需要长期保持的产品、接口、schema、安全或工程规则；case 的 `Contract:` 只压缩当前验证入口必须证明的背景，不取代这些 owner。

按任务读取：

1. **查询或整理 case**：先使用 `list --query <text>` 搜索 case ID、标题、Contract、Proves 和 Entry；主题不明确时使用无查询的 `list` 获取有界概览，再用 `show` 展开目标 case。只有需要核对语义时才读取对应验证实现和行为 owner。
2. **审查或修改验证实现**：先读取项目指令、测试或校验策略、当前 diff、目标实现及其项目入口，再搜索相关 case。
3. **写入或结构修复**：完整读取固定目录契约；纯查询和语义审查不需要预先加载全部机器字段。
4. **旧格式迁移**：遇到 `.test-evidence.json`、`test-evidence-ledger.mjs`、`test-entry-regex.mjs`、`@test-evidence` 或 `Verification: automated|review|exempt` 时读取迁移文档。

持久化索引缺失、损坏或陈旧时，`list` 和 `show` 使用当前合法 Markdown 的只读内存投影并报告 warning，不写回文件。目录不存在时，查询任务报告没有可查询目录；修改任务只有在决定保留至少一个独立入口后才初始化目录。

## 证据评估

确定入口归属后，评估该入口或内部环节产生的证据：

1. **契约背景**：能够指出产品规则、接口行为、schema、安全边界、错误语义或明确工程不变量。
2. **证明信号**：失败能够指出哪项契约不再成立，而不只是实现文本发生变化。
3. **可观察性**：test 断言可观察结果或当前层拥有的不变量；check 判断可复核的工程状态。
4. **可靠性**：输入、环境、fixture、规则和结果足够确定，不依赖偶然顺序、未声明环境或自证循环。
5. **证据独立性**：验证不直接复述被验证实现，也不只确认自己的 mock、fixture、快照或生成逻辑。
6. **重复与成本**：没有被既有入口等价覆盖，执行、维护和故障定位成本与新增证明价值相称。

验证器自身的测试与运行该验证器通常证明不同契约；二者分别成为项目独立入口时分别登记。只能由人工流程、运行时监控或发布治理承接的风险交给对应 owner，不创建伪验证 case。

## 执行流程

1. **界定范围**：列出本次查询或改动涉及的验证实现、项目入口和预期契约。
2. **搜索目录**：按入口、契约、输入、错误、输出和规则名查找已有 case，先确认同一逻辑入口是否已经登记。
3. **判断归属**：依据“核心判断”把每项实现归为独立入口、内部环节、不保留或归属待确认；内部环节写明父入口。
4. **评估证据**：检查契约、信号、可观察性、可靠性、证据独立性、重复和成本。
5. **实施处置**：
   - 保留的独立入口新建或更新唯一 case。
   - 保留的内部环节按需更新父 case 的 Contract 或 Proves；只有父入口自身的定位变化时才更新 Entry。
   - 不保留的实现删除或不新增。
   - 只能由其他机制承接的风险交给对应 owner。
6. **同步索引**：case 内容变化后运行 `sync-index --write`；索引是可重建查询副本，不手工编辑。
7. **验证结果**：运行直接证明验证实现行为的最小项目命令，再运行目录 `check`；按项目要求补充类型检查、lint、构建或更大范围测试。

## Case 与索引

每个 case 使用 `Verification: test|check`、`Entry:`、`Contract:` 和 `Proves:`。同一入口内的多个函数、规则、断言、分支和连续检查点由一个 case 承接；不同独立入口即使共享契约、fixture 或执行链路也分别登记。精确格式以固定目录契约为准。

Markdown 目录是权威源。派生索引提供按 case ID、标题、全部 Contract、全部 Proves、全部 Entry 和 `test|check` 类型的低上下文查询；`show` 从 Markdown 展开完整原文。

入口和父子归属由 agent 根据项目事实判断。目录工具不扫描源码、不要求 marker、不统计未登记函数，也不自动创建或修复 case。

## CLI

从 skill 目录运行，或使用脚本绝对路径：

```text
node scripts/verification-catalog.mjs list --query "<contract or entry>" --root <workspace-root>
node scripts/verification-catalog.mjs show <case-id> --root <workspace-root>
node scripts/verification-catalog.mjs sync-index --write --root <workspace-root>
node scripts/verification-catalog.mjs check --root <workspace-root>
```

`list` 可组合 `--query`、`--verification test|check`、`--limit` 和 `--offset`；`show` 只展开一个 case。两者优先使用当前持久化索引，索引不可用时只读解析当前目录。`sync-index` 默认只检查，增加 `--write` 才重建索引；`check` 严格校验配置、目录结构和索引新鲜度。需要机器输出时增加 `--json`，精确字段和退出状态以固定目录契约为准。

## 完成标准

### 只读任务

1. 先给总体判断；对每个需要动作的实现说明位置、独立入口或内部环节归属、处置、契约、证明信号和成本依据。
2. 没有越过只读授权；拟登记 case、未运行环境和结论边界已经说明。

### 修改任务

1. 本次范围内每个保留的独立验证入口都恰好由一个 case 承接；项目直接配置的提交、CI 或发布 gate 没有漏登记。
2. 每个 case 都对应已存在的 test 或 check 入口，所有 `Entry:` locator 指向同一逻辑入口，并具有可独立理解的 Contract 和可观察 Proves。
3. 本次范围内的内部环节已经归入明确父入口，没有为内部函数、断言、规则或子步骤单独建立 case。
4. 没有把计划、人工风险、普通业务实现、运行时输入校验或发现豁免登记为验证实现。
5. 派生索引已从合法目录同步；已运行最小相关项目命令和目录 `check`，或明确报告无法运行的边界与残余风险。

### 通用交付

报告实际改动、项目验证、目录校验、未执行环境和残余风险，并区分验证实现失败、被验证对象失败与目录结构失败。
