# 复杂 Bug 调查与报告

本文是本仓库识别复杂 Bug、推进调查与修复，并把关键认识形成调查报告的 owner。`AGENTS.md` 将 Bug 任务路由到本文；本文定义仓库级调查主线、自动触发条件和复杂 Bug 证据要求。

[Investigation Report](../skills/investigation-report/SKILL.md) 继续拥有报告结构、关系、资源和维护事务。代码、配置、测试和领域文档拥有当前事实；本文负责让复杂 Bug 的调查证据正确进入这些 owner 和调查报告。

## 选择调查载体

按下表从上到下判断，匹配一项后停止：

| 当前条件 | 处理结果 |
| --- | --- |
| 当前用户明确排除调查报告、长期文档写入，或给出更窄的写入范围 | 在用户范围内完成排查、修复和验证。 |
| 当前用户明确要求记录、沉淀、创建或更新调查报告 | 按用户要求使用调查报告。 |
| 当前用户没有明确选择，且“结构性复杂度”和“独立复核价值”同时成立 | 自动使用调查报告。 |
| 其他情况 | 作为普通 Bug 在当前任务内完成；后续收到明确要求时再形成报告。 |

## 自动触发条件

自动使用调查报告需要同时满足以下两个条件。

### 结构性复杂度

至少存在一个会实质改变调查方法、修复边界或验证责任的条件：

1. 问题间歇出现，或结果依赖并发、时序、环境、版本、持久状态、历史数据或外部系统。
2. 多个候选根因均有现实依据，需要通过受控实验、对照或逐项排除才能收敛。
3. 完整解释需要跨越多个责任 owner、模块、进程、持久化边界或外部依赖。
4. 问题重复发生、既有修复已经失效，或局部症状指向更深的共同机制。
5. 修复涉及数据完整性、安全、兼容性、并发语义、恢复能力或较大范围的消费者，需要显式证明影响面、回退和验证边界。

分类以问题结构和证据责任为依据。耗时、命令数量、改动文件数量和代码阅读难度只是工作量信号；最小调查已经定位到责任清楚的局部缺口时，按普通 Bug 处理。

### 独立复核价值

至少满足一项：

1. 报告需要补足最终代码差异和测试之外的关键环境条件、因果证据、假设排除过程或修复边界依据。
2. 后续维护者需要在另一任务、另一时点或问题复发时接续本轮认识。
3. 修复完成后仍需保留适用条件、未覆盖范围、恢复路径或重新调查条件。

无法立即分类时，先在当前任务中完成能够改变判断的最小调查。自动报告从首个可独立复核的认识检查点开始；此前的工作假设和临时输出留在当前任务。

## 复杂 Bug 调查主线

1. **建立问题框架**：分别写清观察结果、预期结果、影响、环境与版本、相关状态、复现输入与频率、已知事实、假设、未知和操作约束。
2. **建立候选根因**：每个候选都要连接现实机制或已观察证据，并写明它成立时应出现什么、哪项结果能够排除它，以及涉及的 owner 和边界。
3. **取得区分性证据**：优先执行能够区分多个候选的最小复现、单变量对照或定向观测；记录实际输入、版本、时点、命令或方法和观察结果，使结论可重复核对。
4. **闭合因果解释**：把症状、关键状态变化、组件行为、被破坏的契约和责任 owner 连成证据支持的因果链。相关性观察、临时绕过或尚未闭合的环节按实际强度保存为部分结果。
5. **在正确 owner 修复**：根据根因选择直接修复、约束收窄、恢复处理或其他最小动作，并明确影响面、兼容要求、数据处理和回退路径。实际写入继续服从当前任务授权。
6. **验证目标结果**：先用原复现证明旧症状得到处理，再验证受影响契约、相邻条件、回归范围和必要的实际运行环境；分别记录命令成功、测试通过和环境行为生效。

调查在证据足以解释结果、支持修复边界并完成风险相称的验证时结束。剩余未知若会改变根因、修复或适用范围，应继续调查或明确交接条件。

## 形成和演进报告

1. 需要使用报告时，按 `investigation-report` 的读取路径定位相关报告并读取固定契约。
2. 每个报告保存一个可独立汇报的认识检查点。检查点可以是已经确认的根因与修复结果，也可以是适合跨任务交接的实质收窄结果；正文明确它已经确认什么、依据是什么和仍缺什么。
3. 报告从调查过程提炼关键输入、实验设计、观察、对照、排除依据、因果解释和验证结果。大段日志、生成文件或原始数据仅在复核需要且内容非敏感时作为最小资源保存。
4. 新证据、不同条件下的复查或根因解释发生实质变化时建立新的完整报告，并按契约声明直接关系。形成时记录错误通过原地修正恢复准确内容。
5. 已自动触发的报告属于复杂 Bug 的交付物；同一任务内完成修复时仍形成报告，当前用户明确限制写入范围时服从该范围。

固定核心与复杂 Bug 证据的对应关系如下：

| 固定核心 | 复杂 Bug 证据 |
| --- | --- |
| 形成时背景 | 症状、影响、环境或版本、复现条件与频率、已知事实、初始未知和操作约束。 |
| 调查目的 | 本轮准备回答的根因、影响面、修复或验证问题，以及停止调查的条件。 |
| 调查范围与依据 | 实际检查的 owner 和代码路径、运行版本、最小复现、实验与对照、日志或度量、候选根因及其保留或排除依据、未覆盖范围。 |
| 调查结果与边界 | 已确认根因及机制、事实与推断的区分、实际修复、验证结果、剩余风险、未知项、回退或恢复边界，以及重新调查条件。 |

“现象与复现”“假设排除”“根因机制”“修复与验证”等可选小节用于组织具体证据；四项固定核心共同保持完整。

## Owner 交接

1. 调查报告拥有一轮形成时认识、证据基础和适用边界。
2. 代码、配置、测试和领域文档拥有当前行为与稳定事实，并与实际验证共同证明修复生效。
3. Change 或 task 在工作需要规划、依赖、租约或交接时建立，各自继续拥有实施或协调状态。
4. 修复形成会持续约束未来行为、责任边界、兼容性、风险处理或验收方式的判断时，按 Decision Records 的门槛另行记录。
5. 各载体通过单向引用连接；规范、进度和测试账本保持在各自 owner。

## 完成标准

1. 自动创建报告的两个条件均有实际依据，普通 Bug 已在当前任务内完成。
2. 调查已经形成从症状到根因机制和责任 owner 的证据链，部分结论与未知项保持实际强度。
3. 修复已进入正确的当前事实 owner，验证区分了命令成功、测试通过和环境行为生效。
4. 报告能够让未参与原任务的读者恢复条件、候选根因、区分性证据、实际修复、验证和剩余边界。
5. 长期材料只保留复核所需的非敏感内容；调查索引已经同步，完整调查检查和本次改动要求的仓库检查均已通过。

常用仓库入口：

```bash
bun run investigation-report -- check --id <investigation-id>
bun run investigation-report -- sync-index
bun run investigation-report -- check
bun run check
```
