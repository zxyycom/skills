## 目的

- 让 agent 和工具能够明确区分任务要做什么、已经显式声明什么，以及当前拓扑推导出什么。
- 让任务内容保持紧凑，复杂状态可以独立扩展而不把一个条目退化为难以辨认的平铺字段集合。
- 防止 `ready`、`waiting`、阻塞原因和继承来源等派生结果与显式关系发生新鲜度漂移。

## 背景

- 一个任务的内容通常只包含目标结果、完成条件、少量上下文、引用和结果摘要。
- 调度状态同时涉及人工控制、实际执行、父子继承、依赖满足、并发排斥、租约和时间，复杂度明显高于内容。
- 同一个 `status` 枚举无法可靠区分显式等待、依赖阻塞、正在执行和父级状态继承。
- 把派生有效状态重新写回权威条目，会要求每次拓扑变化同步更新多个任务并形成冗余事实。

## 决策

- 采用: 每个 task entry 顶层保存稳定身份与作用域，并分别使用 `content` 和 `state` 承接任务语义与显式运行事实。
- 采用: `content` 只保存目标结果、完成条件、必要上下文、外部引用和紧凑结果；它不保存调度状态、阻塞原因或关系投影。
- 采用: `state` 至少区分人工控制、实际执行、显式关系和生命周期时间；执行租约属于实际执行状态，不能与任务内容混写。
- 采用: 控制状态表达候选、排队、显式等待、暂停或继承，执行状态表达空闲、运行、完成、失败或取消；两者不压缩为单一枚举。
- 采用: `ready`、依赖造成的 `waiting`、有效控制状态、继承来源、阻塞列表、子任务和反向依赖只由工具根据当前完整索引查询生成，不持久写回 task entry。
