## 目的

- 让一个长期可发现的运行时容器稳定保存当前仍有调度价值的短期任务，并支持低成本查询和事务更新。
- 让每个任务用一个紧凑 JSON 对象承载完成当前调度和交接所需的全部本地上下文。
- 让任务完成后的清理成为正常生命周期，而不是把短期执行对象永久积累为项目历史。

## 背景

- 短期任务通常只需要目标结果、完成条件、少量上下文、显式状态、关系和结果摘要，不需要长篇设计或过程记录。
- 为每个任务创建 Markdown，再从这些文件派生索引，会增加文件发现、同步、新鲜度和双重 owner 的维护成本。
- 决策、调查和 change 需要长期理由或完整交接，因此适合独立文档；task 的价值主要存在于当前调度窗口。
- 长期存在的是索引协议、schema 和运行时容器，而不是其中每一条任务记录。

## 决策

- 采用: 使用一个受工具管理的 JSON task index 作为任务身份、内容、显式状态和拓扑关系的唯一运行时事实源；它不是从逐任务文件生成的派生索引。
- 采用: 每个任务直接作为索引中的短期 JSON 条目存在，不创建 task Markdown、物理归档目录或默认事件历史。
- 采用: 终态任务在没有活动租约、存活子任务或存活引用，且结果不再需要下游消费后，由受控清理从索引移除；任务 ID 不复用。
- 采用: 任务需要大量背景、长期理由、正式审阅或跨阶段交接时，把完整内容交给对应稳定 owner，task 条目只保留紧凑摘要和引用，不扩展为长期记录格式。
- 采用: 索引的精确运行位置、作用域标识和清理触发方式由实现 change 在不改变上述责任边界的前提下确定。
