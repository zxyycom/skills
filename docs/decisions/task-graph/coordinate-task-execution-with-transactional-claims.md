## 目的

- 让多个 agent 能够共享同一任务索引，并在并发读取和写入时保持单一任务所有权与排斥约束。
- 让任务执行者异常退出、超时或交接后拥有显式恢复路径，不把永久 `running` 状态留给后续 agent 猜测。
- 让所有状态和关系修改以完整、可验证的索引事务结束，避免部分写入破坏任务图。

## 背景

- 多个执行者可能同时查询到同一个 `ready` 任务，或分别查询到彼此排斥的任务；普通读后写无法阻止重复领取。
- 单个长期索引会被多个短期任务频繁修改，需要显式 revision、并发冲突和失败恢复语义。
- 只有任务 ID 和执行者名称不足以证明后续完成操作仍属于原领取者，也无法安全回收失联执行者的状态。
- 自动选择最优任务集合属于调度策略；保证一个具体领取动作合法属于状态工具必须兑现的确定性边界。

## 决策

- 采用: task index 只通过专用工具修改；agent 不直接编辑 JSON，也不在索引外维护另一份权威运行状态。
- 采用: `claim` 在一个事务中读取当前 revision，计算任务有效状态，验证依赖、祖先约束和正在运行的排斥任务，再写入带唯一租约的运行状态；任一条件变化都使领取失败而不接受陈旧写入。
- 采用: 完成、失败、释放和暂停运行任务必须匹配当前租约；工具提供受控的租约过期与恢复路径，不能由另一个 agent 静默覆盖活动执行者。
- 采用: 所有改变状态、层级、依赖或排斥的命令先验证候选完整图，再原子替换权威索引；验证、冲突或写入失败不保留部分结果。
- 采用: 工具可以返回 runnable 集合和阻塞原因，但不根据未记录偏好自动替 agent 选择业务优先级；精确锁、时钟、续租和恢复机制由实现 change 在上述事务语义内确定。
