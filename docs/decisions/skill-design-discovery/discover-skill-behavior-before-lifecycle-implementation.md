## 目的
- 在新建、显著扩展或重大重构 skill 前恢复真正决定行为质量的工作流、判断、约束、权限和验证义务。
- 让设计发现与 skill 生命周期实现各自拥有稳定触发、行为边界和完成标准。

## 背景
- Skill 生命周期维护需要处理能力归属、组成、结构、metadata、分发和交付，但这些责任不能代替对隐性领域经验和现实案例的恢复。
- 用户说明、规范材料、现有实现、现实案例和运行结果具有不同证据强度，若不区分就容易把历史 workaround、环境限制或启发式经验写成硬契约。
- 局部结构或文字维护通常已经有明确目标与验收，把完整深度发现强制加入会产生过度访谈和一次性设计产物。
- 能力建立阶段保留的上游原始材料可以辅助维护取证，但其存留、许可和分发状态不决定普通设计发现的行为身份。

## 决策
- 采用: 将 skill 设计发现作为独立行为，只在新建、显著扩展或重大重构前仍有关键流程、判断、约束、权限或验证方式隐含、冲突时触发；目标、边界和验收已经清楚的局部维护不进入深度发现。
- 采用: 同时使用用户说明、规范材料、现实案例、现有实现和可用运行证据，并区分已确认目标、规范性约束、观察行为、当前实现、用户经验、推断和未知项。
- 采用: 设计契约恢复端到端流程、决策信号与例外、约束类型和来源、人类权限、资源 owner 候选、完成证据、交接条件、失败处理和验证义务，不以步骤列表或当前文字代替判断模型。
- 采用: 根据复杂度选择轻量或深度路径；深度路径使用 Workflow Map 组织完整流程，但不把落盘或整图确认设为固定门禁。设计默认可以在对话交付，只有复杂交接或当前环境要求时才写入文件。
- 采用: 验证义务从当前触发、流程、判断、依赖、权限、owner 和行为差异即时推导；已观察运行行为、事后自述与尚未执行的验证分别表达，不把计划当作通过证据。
- 采用: 本行为不拥有目录结构校验、metadata、打包、安装、更新或发布；请求包含实现时把设计契约交给当前环境的实现或维护入口，发现到的判断也只有达到对应长期 owner 门槛后才持久化。
- 采用: 分发后的行为入口不把相邻 skill 或建立阶段的上游参考材料作为隐含运行依赖；上游快照、eval、许可证和 NOTICE 的当前存留由分发与维护事实 owner 承接，不作为本行为决策的组成部分。
