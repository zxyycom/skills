## 目的

- 让 Change 的内容承诺随工作成熟度逐步增加，避免在方向尚未稳定时过早固化无意义的细节。
- 防止搁置后的旧计划未经复核就直接进入实施。

## 背景

- 起草时主要是在建立任务或方向记录，细节尚未经过执行准备，持续修改是正常行为。
- 准备开始实施时才需要把范围、方案、任务、依赖和验收等执行细节固化到足以行动。
- 计划完成后可能因外部条件、优先级或资源变化而未开始实施；这种搁置通常不能在起草或计划时预先确定。
- 搁置期间事实、依赖和约束可能变化，原计划在恢复时不一定仍然有效。

## 决策

- 采用: 活动 Change 的标准推进路径是 `起草 -> 计划 -> 实施`；发生搁置时使用 `计划 -> 搁置 -> 计划`，不允许 `搁置 -> 实施`。
- 采用: `起草` 只要求建立可识别的任务或方向及其必要背景，允许持续改写，不把尚无执行价值的细节设为完成门槛。
- 采用: `计划` 表示已经准备进入实施，应固化可执行范围、设计取舍、任务顺序、依赖、风险和验收条件。
- 采用: `实施` 只接收具有当前有效计划的 Change，并按已固化计划推进。
- 采用: `搁置` 是按实际事件出现的可选阶段，不是每个 Change 的必经阶段，也不在起草或计划时预设。只有计划已经形成、实施尚未开始且工作实际暂停时才进入，并在发生后显式记录。
- 采用: 搁置后的 Change 恢复时先回到计划阶段，重新核对目标、当前事实、依赖、风险和任务细节，更新过时内容后再决定是否实施。
- 采用: 本决策只定义活动 Change 的工作阶段；何时归档及归档门禁继续由既有终态契约承接。阶段的持久化结构、CLI 命令和具体门禁由 [change-plan 固定契约](../../../skills/change-plan/references/change-plan-contract.md)承接。
