## 目的

- 为仓库发现、`revision`、`pending`、工作区读取和受控 `pending` 写入建立唯一、可维护的责任边界。
- 让调用方只表达版本快照、字面路径范围、目标文件集合和一致性要求，不依赖底层版本系统的专属信息。
- 将写入语义、错误映射、失败恢复和底层实现变化集中在共享版本管理 owner。

## 背景

- 共享版本管理层已经集中承接仓库发现、已提交修订、待提交快照、工作区内容和路径变化读取；Git 是已有实现。
- 一个现实领域消费者需要完整替换字面路径范围内的待提交文件集合，同时保留范围外内容，并在失败后恢复原范围。
- 如果领域消费者自行调用 Git 完成写入，Git index、对象 ID、文件模式、锁和原始错误解析会扩散到业务边界。
- 没有同时兼容多种版本管理系统的现实消费者；隔离底层实现不等于承诺多后端兼容。

## 决策

- 采用: 共享版本管理层集中承接仓库发现、`revision`、`pending` 与工作区读取，并提供完整替换一个字面仓库相对路径范围内 `pending` 文件集合的受控写入操作。
- 采用: 写入操作接收目标范围、目标文件集合和必要的一致性前提；范围内未出现在目标集合的文件视为删除，范围外 `pending` 内容保持不变。
- 采用: 共享层校验输入、应用完整目标并读回核对，不把部分范围更新作为成功；对可处理失败恢复写入前的目标范围，恢复不完整时停止并明确报告恢复边界。
- 采用: 公共类型、结果和错误只表达修订、待提交快照、路径、内容、冲突与恢复。本决策不要求 Git 以外的实现，Git 命令、index、对象 ID、文件模式、锁和第三方库对象不得越过共享层。
- 采用: 共享操作不可用时，领域消费者通过稳定失败停止，不直接回退到底层命令。公共边界的隔离只限制依赖方向，不承诺多后端兼容，也不要求预建 provider 注册或能力协商框架。
