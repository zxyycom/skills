## 目的

- 让 agent 从权威任务图恢复当前仍需协调的候选、阻塞、父子、依赖、排斥和执行归属。
- 让任务是否保留取决于协调价值，而不是创建时间、经过时长或是否跨越多个上下文。
- 让任务协调保持执行机制中立，不把可选的执行者或协作方式写成 task-graph 的使用前提。

## 背景

- 线性计划不能稳定表达同时存在的候选任务、父子结构、前置依赖和并发排斥；只把关系留在对话中又会在上下文压缩或动态追加后丢失。
- 有些任务会很快完成，有些任务会跨越较长工作周期；只要它们仍参与选择、阻塞、交接或执行协调，任务图就仍有保存价值。
- Task entry 的临时性限制内容职责：它不替代长期需求、设计理由、测试证据或历史记录；这与 task 必须短时间消失不是同一判断。
- 执行者的选择、配置和结果审计会随调用环境变化。Task graph 只需提供同一组协调事实和状态契约，不需要指定由哪个 skill 或执行机制消费。

## 决策

- 采用: `task-graph` 维护当前工作中仍有协调价值的任务发现、显式关系、状态查询、领取、完成和清理流程；经过时间本身不改变 task 的有效性，也不触发清理。
- 采用: `task-graph` skill 与兑现其行为所需的专用状态工具属于同一分发单元；工具提供确定性状态与拓扑操作，skill 负责触发、判断、权限、交接和完成条件。
- 采用: Task entry 只承接执行协调所需的任务内容、关系、状态、结果摘要和稳定引用；长期知识、正式 change 和历史证据继续由对应 owner 承接。
- 采用: 调用方选择实际执行者和执行方式。`task-graph` 不创建、配置或审计执行者，具体选择也不进入 task-graph 的行为契约。
- 采用: 执行者从 task graph 获取目标、完成提示、约束、关系、当前状态和 lease 边界，并遵守同一套 claim、renew 与终态收敛契约；执行机制的差异不进入任务图。
- 采用: 只有任务不再承担协调价值、结果已经交付且显式清理门禁满足时才删除；任务可以按实际需要跨上下文或长期保留。
