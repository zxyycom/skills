## 目的

- 让已建立决策的常规查询稳定消费最近一次成功维护的持久索引，不在每次读取时重建完整来源集合。
- 让正式记录的完整正文和索引外候选都能从各自权威边界读取，而不把两类生命周期混入同一查询路径。

## 背景

- 持久索引保存已建立决策的身份、位置、摘要、状态和关系投影，适合承担日常发现、过滤与演进追踪。
- `show` 需要返回索引没有完整保存的 Markdown 正文，因此必须先用索引确认正式身份和目标位置，再读取该目标源码；这不同于扫描源码发现正式成员。
- 候选在建立前有意不进入正式索引，仍需通过源码扫描发现；单条非法候选不应遮蔽其他合法候选，但集合结构损坏不能局部忽略。

## 决策

- 采用: `list` 和 `trace` 从持久索引查询已建立决策；`show` 先从同一索引定位唯一正式记录，再读取该路径对应的 Markdown 正文，不通过全量源码扫描发现目标。
- 采用: `candidates` 和 `show-candidate` 只从决策 Markdown 源发现候选，不从正式索引或 Git 历史补造候选身份。
- 采用: 候选查询逐文件容错，跳过单条结构、状态或关系非法的非目标源码并报告 warning；显式请求的目标非法、目标不存在或集合级结构非法时失败。
- 采用: 常规正式查询不逐次重建索引、比较全部 source revision 或在索引陈旧时静默回退到源码发现；怀疑漂移时通过严格 `check` 诊断，并由显式同步维护索引。
- 采用: 严格 `check` 继续从源码验证完整集合及其索引一致性；合法候选留在正式索引外不构成缺失，非法候选和正式集合漂移仍阻断验收。
- 不采用: 把候选混入正式查询，或把 `show` 读取目标正文误写成正式成员由源码扫描确定。
