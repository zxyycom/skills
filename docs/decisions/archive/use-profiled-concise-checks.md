## 目的
- 让日常 `bun run check` 在保留必要工程门禁的同时快速完成，并让成功输出保持可扫描。
- 让维护者和 CI 能显式选择全部检查，不让耗时集成测试延长默认反馈路径。
- 让单项失败提供完整诊断，同时继续收集其余独立检查结果，并以可靠的最终退出状态阻止错误打包。

## 背景
- 部分行为测试会创建多个临时 Git 仓库并启动大量子进程，完整检查的主要等待时间集中在少数集成套件。
- Bun 会把成功测试明细写入 stderr；保留成功任务的 stderr 会产生大量噪音，并在输出收集器中造成摘要与明细错序。
- 现有 warning 默认虽然能继续执行其他任务，但会让存在前置失败的命令仍退出 `0`，调用方不能只依赖最终状态判断检查是否通过。
- 完整检查仍需要保守控制顶层资源占用，且打包只能建立在本次所选检查全部通过的基础上。

## 决策
- 采用: `bun run check` 默认使用 `quick` 档，只执行必要且快速的检查；计划中的耗时检查必须显式标记为 `full`，默认运行时逐项输出 `skipped`。形成时的任务映射由项目检查计划显式维护并接受测试。
- 采用: `bun run check --full` 执行 quick 与 full 的全部任务；CI 和发布门禁使用 full 档。`--verbose` 可以与任一档位组合，并显式展开每个已执行任务的完整捕获日志。
- 采用: 成功任务默认只输出名称、`passed` 和耗时；失败任务始终完整展开自身日志并输出 `failed`，但不会阻止其他已选择的独立检查继续领取和执行。
- 采用: 任一已选择前置检查失败都会使最终状态失败并跳过 `pack:skills`；跳过打包必须显式输出。全部已选择前置检查通过后才执行打包，打包失败同样决定最终失败。
- 采用: 最终摘要显式给出档位、总数、passed、skipped、failed 和总耗时；quick 档因 full 任务被显式跳过仍可成功，不把跳过误报为 warning 或 failure。
- 采用: 顶层任务默认最多并发两个，并继续允许 `CHECK_CONCURRENCY` 以正整数显式覆盖；通过减少默认任务和优先调度 full 档慢任务改善等待时间，不默认提高资源压力。
- 不采用: 将前置失败降级为最终退出 `0` 的 warning，也不在成功路径默认打印测试明细。
