## 目的

- 让决策方向的内容起草、语义审核和正式建立拥有清楚且可恢复的生命周期边界。
- 让已经完整但尚未确认的方向能够跨任务等待、继续收敛或安全删除，而不约束当前工作。
- 保持正式索引和正式关系图只表达已经确认进入当前决策集合的记录。

## 背景

- 一条记录可以已经完整到值得审核，但是否建立、成为当前基线还是未来方向，仍需要独立判断。
- 用活动状态、预选 alignment 或 Git 提交隐式表达候选，会在审核前制造已经生效的假象。
- 候选需要与正式记录使用同等结构和语义完整性，半成品则应继续留在对话、change 或其他草稿 owner。
- Git `pending` 只表达下一版本快照，Git `HEAD` 只表达历史，二者都不决定决策生命周期。

## 决策

- 采用: 新候选使用稳定新身份、完整摘要与正文、完整预期关系、`status: candidate`、`alignment: null` 和 `createdAt: null`；不接受占位字段或半成品。
- 采用: 候选尚未建立和生效，不进入正式索引或正式关系图，也不使用 Git `pending` 表达生命周期。
- 采用: 合法候选可以在审核前原地收敛或跨任务等待；候选关系只接受前瞻性审核，建立事务再确认最终关系、前序生命周期和索引组合。
- 采用: `activate` 或统一演进事务是审核与建立边界；建立时为候选选择 `aligned` 或 `unaligned`，写入不可变建立时间并将其加入正式集合。
- 采用: 不再需要且没有被引用的候选可以通过 `discard` 删除工作区文件；是否已经进入 Git `HEAD` 不影响候选删除，已建立记录和 Git 历史不由此改写。
- 不采用: 用 `active` 加空建立时间、预先选择的 alignment、Git commit 或 pending 状态隐式识别候选。
