## 目的

- 让后续 agent 能根据可复核的维护压力判断是否应创建领域谱系升级 change。
- 为 Decision Records 保留可恢复的升级方向，使领域边界变化真正产生维护压力时不必重新发现问题。
- 将升级范围限定为决策分类领域的身份与谱系，不替代各 skill 或项目文档对当前领域事实的承接。

## 背景

- 当前 `decision-domains.json` 只定义领域 ID 和责任描述，决策路径第一段同时表达唯一领域归属和稳定身份。
- 现有契约把领域改名、拆分和归并作为结构迁移处理，能够恢复当前分类，却不能直接恢复领域之间的历史谱系和责任去向。
- 仓库已经出现能力从一个 skill 转移到另一个 skill 的领域边界变化；现有决策记录与当前事实 owner 仍足以解释该案例，尚未证明需要立即建设通用领域演进系统。
- 领域演进频率低但影响范围大，适合用明确证据控制升级时机，并让触发案例提供实现约束和验收依据。

## 决策

- 采用: 将决策领域的生命周期和谱系支持确认为尚未成为当前能力的未来方向；该方向不自行产生实施、排期或 change。
- 采用: 触发前继续使用受控领域目录、唯一领域路径和人工结构迁移作为当前基线；普通领域描述修正或单次可闭合迁移不扩大为新能力。
- 采用: 只有出现至少一项可复核维护压力时才创建 change：无法同时恢复历史与当前领域归属，无法证明拆分、归并或责任重划已经闭合，人工迁移路径与关系的风险不可接受，或多个项目需要同类查询与维护行为。
- 采用: 升级后的领域需要具备稳定身份、显式生命周期和直接演进关系；退役领域与历史决策仍可恢复，当前查询视图能够区分现行领域与历史归属，领域重划不通过改写历史决策语义完成。
- 采用: Decision Records 只承接用于决策归类的领域身份、谱系和查询契约；各领域当前负责什么仍由对应 skill、代码、规范或项目文档承接。
- 采用: 触发案例必须为 change 提供实施范围、兼容边界和验收标准；字段、关系名称、索引版本、CLI、迁移事务和是否需要独立 skill 由该 change 确定，部分实现不能把本决策标记为已对齐。
- 不采用: 现在创建领域演进 change、专用工具或独立 skill。原因是当前缺少足以约束实现协议的重复维护压力，提前建设会让低频能力持续占用维护成本。
