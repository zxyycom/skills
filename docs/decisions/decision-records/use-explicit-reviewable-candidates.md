## 目的

- 让决策记录的创建、内容收敛与正式审核建立拥有清楚边界。
- 让尚未建立的候选可以跨任务保留、主动发现和安全删除，而不会冒充当前决策。
- 保持正式索引只表达已经确认的决策集合，同时避免索引外候选成为不可见的悬空内容。

## 背景

- 一条记录可以已经写完整并值得审核，但是否进入当前决策集合、应当对齐还是未对齐，仍需要独立判断。
- 旧候选依赖 `status: active`、预先选择的 `alignment` 和空 `createdAt` 组合隐式识别，把尚未确认的记录提前表达成活动状态。
- 常规查询采用索引优先模型；候选不进入正式索引时，`list`、`show` 和 `trace` 无法主动发现它们。
- 候选可以等待审核，不应仅因其合法存在就让严格检查失败；结构不完整或状态非法的文件仍需要阻断维护。

## 决策

- 采用: 新候选使用稳定新身份、完整决策结构、`status: candidate`、`alignment: null` 和 `createdAt: null`；候选与已建立记录使用相同的摘要、正文和关系结构校验，不接受半成品。
- 采用: 候选尚未建立和生效，不进入正式索引，也不使用 Git `pending` 表达；`pending` 继续只属于版本快照。
- 采用: `candidates` 和 `show-candidate` 直接从 Markdown 源发现并读取合法候选；`list`、`show` 和 `trace` 继续只读取正式索引。
- 采用: 严格 `check` 从源码发现并计数合法候选，候选未进入索引本身不构成失败；不完整、状态组合非法、身份冲突或关系无效的候选继续阻断检查。
- 采用: `activate` 是审核与建立边界，为显式目标选择 `aligned` 或 `unaligned`、写入建立时间并加入正式索引；候选中的 `alignment` 不提前表达审核结论。
- 采用: 合法候选可以在审核前原地收敛或跨任务等待，不再需要且没有被引用时可以通过 `discard` 安全删除；已建立记录不能用候选删除路径改写历史。
- 采用: 候选不作为正式关系目标或正式关系图成员；演进和拆分事务在建立后继时确认最终关系，并与前序生命周期和索引变化一起验证。
