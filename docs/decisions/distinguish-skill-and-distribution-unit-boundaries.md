## 目的

- 让每个 skill 的发现入口和触发后行为拥有清楚 owner，同时让真实共同交付的成员能够按一个分发单元验收。
- 阻止仓库布局或主题关系被误当成安装保证，并让跨单元依赖在缺少外部能力时仍有明确结果。

## 背景

- Skill 的 name、description、正文和按需资源共同形成可触发的行为单元。
- 安装、更新、版本兼容、成员完整性和交付验收可能只覆盖一个 skill，也可能由明确声明的一组成员共同承担。
- 若只按目录判断分发单元，会把同仓、相邻阶段或偶尔协作误作共同安装；若强迫所有真实组合拆成单 skill，又会破坏合法的单元内依赖。

## 决策

- 采用: Skill 是行为单元，每个 skill 拥有独立发现入口和触发后行为契约；distribution unit 是安装、更新、版本兼容、成员完整性和交付验收的边界。
- 采用: 分发单元可以包含一个或多个 skill 及兑现整体承诺所需资源，其边界从用户说明和当前环境显式的安装、更新、metadata、打包或发布契约恢复。
- 采用: 同一分发单元内的成员可以显式调用、依赖和交接，但必须写清触发条件、输入和完成状态；单元验收证明成员、共享资源与兼容约束完整。
- 采用: 跨分发单元的能力不能作为未声明前提；确有依赖时表达前置条件，并定义依赖缺失时的失败或降级路径。
- 不采用: 仅因 skills 位于同一仓库、主题相近、名称相关或组成一条概念工作流，就推断它们属于同一分发单元。
