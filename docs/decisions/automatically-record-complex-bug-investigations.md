## 目的

- 让复杂 Bug 排查中形成的症状条件、候选根因、排除依据、根因机制、实际修复、验证结果和剩余边界在脱离原任务后仍可复核。
- 让普通局部 Bug 在当前任务中完成，使持久化成本与问题复杂度和后续价值相称。

## 背景

- 复杂 Bug 的最终代码差异和回归测试通常只证明当前修复的一部分结果；完整复核还需要假设排除、环境与状态条件、因果解释和修复边界。
- `investigation-report` 已能保存一轮形成时认识、证据与适用边界，并用直接关系表达后续复查、修正或推翻；仓库级规则可以直接复用这套报告契约。
- 普通局部 Bug 可以在当前任务中直接定位、修复和验证，其持久化需求由用户明确选择。

## 决策

- 采用: 由 [`docs/complex-bug-investigation.md`](../complex-bug-investigation.md) 统一拥有本仓库的自动触发条件、报告形成流程、复杂 Bug 证据要求和 owner 交接。
- 采用: 问题同时具有结构性复杂度和脱离当前任务后的独立复核价值时，自动建立调查报告；分类依据是问题结构和证据责任。
- 采用: `AGENTS.md` 将仓库内 Bug 任务路由到项目规则；`skills/investigation-report/` 继续拥有可分发报告能力的行为与契约。
- 采用: 普通 Bug 在当前任务中完成，用户明确要求记录、沉淀、创建或更新调查报告时再使用该载体。
- 采用: 报告保存形成时认识和证据链；代码、配置、测试与领域文档拥有当前事实，Change、task 和 Decision 分别在自身门槛成立时建立。
- 采用: 报告以可复核的认识检查点组织调查证据，自动分类以问题结构和证据价值为依据。
