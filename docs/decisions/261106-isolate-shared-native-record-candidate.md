## 目的

- 让决策与调查工具的原生迁移共同维护索引、文件安全及事务证明，同时继续按各自领域规则演进。
- 让原生交付以完整命令、程序化结果、平台与制品证据为依据，不把语言替换或局部实验等同上线。

## 背景

- 两域的记录格式和演进规则不同，但已共享索引及记录操作底座。分别迁移会增加共同安全契约漂移和跨域验收遗漏的风险。
- 仓库盘点可核实维护 CLI 的调用及状态、诊断和范围需求，不能穷尽外部安装与私有脚本。用户本次对主要使用者的检查表明，直接导入多用于简化 CLI，少数深入使用关注精确的程序化输出。基于这两类依据，保留信息粒度比重建深层 SDK 更贴合当前需求；CLI 参数与 JSON 因此成为候选兼容边界，内部 library 仅服务两个入口。
- 原生二进制需要按平台构建、绑定身份并验证安装恢复，也不能继续提供 TS 源码就地修改的同一种定制方式。现有 [TS 分发判断](distribute-editable-typescript-runtimes.md)继续约束其他适用 skill；两域转为独立原生交付。

## 决策

- 采用: 在 `tools/record-cli/` 的独立 Cargo package 中维护两个原生 CLI，共同层承接已经共享的索引、来源安全、Git 与事务不变量；领域层分别拥有解析、身份、关系、生命周期及输出适配。内部共享不形成公开 Rust SDK、插件接口或另一个通用命令框架。
- 采用: 以现有领域规则和持久格式为兼容基线，通过参数调用及具名 JSON 保留程序化信息粒度；既有 trace 成功结果继续遵守各域格式。兼容性差异由对应契约明确记录和验证，不由实现自行缩窄。
- 采用: 两域以原生 CLI 为唯一业务入口；平台、来源、版本和资产 hash 以实际证据核验。私有验收不等于发布或用户安装。
- 采用: Rust 工具链和原生平台验证使用明确入口，公共 quick 保持不依赖 Rust。Node 只承担安装更新和仓库轻量调度；旧领域 TS SDK 不保留。
- 采用: 共享内存索引及跨命令批量调用保持独立设计边界，只有出现真实需求时再评价；本方案不以它们作为性能或功能验收前提。
