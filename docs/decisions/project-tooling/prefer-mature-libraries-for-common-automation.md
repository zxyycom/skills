## 目的

- 让仓库自动化把维护投入用于项目领域规则，而不是重复实现成熟生态已经覆盖的通用底层能力。
- 以明确选择标准控制依赖质量，同时不把当前依赖名称冻结为长期架构约束。

## 背景

- 手写目录发现、frontmatter 解析、ZIP header、CRC 或压缩拼装会增加边界缺陷、类型维护和测试负担。
- 主仓库脚本服务本地校验、打包和 CI，不进入 skill zip；在该边界内，可读性、正确性和类型体验通常比少量依赖体积更重要。
- 具体库可能因维护状态、兼容性或更合适替代品而变化，这类当前映射可以从 package 与源码直接恢复。

## 决策

- 采用: 常见格式、协议、文件发现、解析、压缩和归档能力优先使用成熟外部库，不因为代码属于辅助脚本就手写底层实现。
- 采用: 选择依赖时综合维护活跃度、使用成熟度、API 聚焦程度、类型支持、ESM、Node.js 与 Bun 兼容性，以及依赖复杂度。
- 采用: 项目特有领域规则继续由仓库直接实现；依赖通过根 package manifest 与锁文件统一维护，脚本入口保持简单。
- 采用: 具体库名和调用点属于当前实现与依赖事实，除非出现需要长期回放的独立兼容或责任取舍，否则不固化为决策。
- 不采用: 为减少依赖数量继续维护通用目录遍历、格式解析、归档 header、CRC 或 deflate 拼装实现。
