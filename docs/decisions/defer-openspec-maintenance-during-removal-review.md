## 目的

- 避免在 OpenSpec skills 可能整体退出仓库时继续扩大行为、文档、决策和分发维护面。
- 让维护者区分“当前仍然存在并可使用”“普通维护已经延期”和“已经获得删除授权”三种状态。

## 背景

- `openspec-explore`、`openspec-propose`、`openspec-apply-change` 和 `openspec-archive-change` 当前仍位于 `skills/`，现有行为与分发关系没有因观察而失效。
- 项目已经进入是否整体删除这组 skill 的观察阶段；在去留结论形成前继续处理普通文案、体验、功能或决策细化，可能产生不会长期保留的维护成本。
- 观察阶段只改变维护优先级，不等于已经决定或执行删除，也不能代替删除对仓库入口、分发、引用和使用者影响的单独核对。

## 决策

- 采用: OpenSpec 四个 skill 在去留观察期继续保留现有入口、行为和当前分发关系；已经适用的行为决策在实际删除前仍作为当前基线。
- 采用: 观察期内发现的普通问题、措辞优化、体验改进、功能扩展和非阻断决策细化默认延期，不自动建立 Task、Change 或实施工作。
- 采用: 只有用户或产品 owner 明确重新选择维护，或者问题会阻断安全使用、去留评估或受控删除时，才按届时事实重新确定处理范围；本记录不保存问题 backlog。
- 采用: 若观察结论是继续保留，先重新核对届时需求和现有行为，再选择是否处理此前发现的问题，不自动恢复全部历史设想。
- 采用: 若观察结论是删除，必须通过独立且明确授权的工作同步移除 skill 本体、项目入口、分发与引用；本记录本身不授权删除文件或改变当前制品。
- 不采用: 把“正在观察删除”表述为已经弃用、已经删除或现有行为立即失效，也不为可能删除的能力继续进行常规优化。
