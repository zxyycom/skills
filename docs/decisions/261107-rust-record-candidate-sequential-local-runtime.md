## 目的

- 在不丢失领域业务事实和可解释结果的前提下，降低两域 Rust 候选的运行时、恢复与验证维护面。

## 背景

- 原有合作锁、文件身份与跨阶段证明、恢复材料和 Git 暂存保护复杂，仍无法实现非合作进程的跨文件隔离；本地单用户顺序操作可接受更简单的失败边界。
- 正文、IR 发布身份和成员、未选 Git 暂存及操作结果仍具有独立价值。Git pending 是提交快照而非工作区备份，跨文件操作失败可能部分完成。
- 此判断完整替代前序文件保障取舍；两域共用候选与隔离生产接线的独立方向仍有效。

## 决策

- 采用: Rust 候选面向合作型本地单用户顺序操作，保留基本工作区路径范围和必要领域校验；已有文件用成熟库原子替换保护旧内容，新建用 `create_new` 不覆盖已有目标，但初始化失败可能留下部分新文件，按已知和未知事实及写入诊断报告，不承诺新文件完整内容的原子发布；取消主动权限策略、跨阶段身份与全范围回读证明、CLI 集合锁、普遍备份和自动恢复证明。资源在普通冲突检查后目录 rename，再顺序更新引用与索引；允许部分失败，以已完成和未知事实协助人工对账，不声称跨文件原子性或回滚。
- 采用: 保留 IR 发布身份和成员等无法从正文猜测的业务事实；预检不交接执行凭据，正式调用重新读取准备一次。机器结果保留业务信息、实际提交及失败步骤和路径，不把计划或未验证事实表述为成功。
- 采用: Git 暂存对所选记录合成同 JSON 内容，保留未选暂存；以 Git 的对象写入和一次 index 更新，由 Git 自身管理锁，不维持 CLI 手持真实锁、备用 index 或 HEAD/pending CAS。
- 采用: 范围仅限 `tools/record-cli/` 两域 Rust 候选；生产 TypeScript、分发与 updater 的既有契约不随之变化。候选、平台证据和生产切换分别判断，不以目标编译宣称原生运行资格。
