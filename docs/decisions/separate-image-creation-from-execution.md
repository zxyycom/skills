## 目的

让 `image-creation`（`skills/image-creation/`）持续以用户所求图像及其用途为验收对象，同时能独立演进视觉需求、参考输入和看图迭代的工作方式，而不承担不断变化的生成服务调用协议。

## 背景

图像生成工具可以成功返回文件，但这不证明用户想要的状态、角色身份、局部设计或非目标保留已经落实。参考图的文字描述也不证明生成器收到了该位图；局部样稿可读，不等于全图回填成功。只优化提示词会遗失这些验收义务。

生成工具或宿主执行 skill 已经拥有附件、模型参数、输出位置及调用失败处理等约定。将这些细节再内置到视觉流程会形成重复 owner，也容易把旧模型语法和历史经验误用为当前能力。反过来，让单个执行协议拥有全部视觉任务判断，又会使通用工作流与某个生成入口绑定。

## 决策

- 采用：建立独立的 `image-creation`，以“意图与当前状态 → 实际参考审计 → 路线与提示 → 获授权的生成／编辑 → 看图诊断与保留回归 → 交图”为主线。用户只要提示词或诊断时止于该交付；简单任务不强制问卷或完整记录。
- 该 skill 拥有视觉任务、参考职责、生成／编辑路线判断和结果验收；实际调用由当前工具及其执行 skill（例如环境提供的 `imagegen`）承接。不存在默认必装的跨 skill 组合，也不内置另一套 API、模型安装或收费回退。
- 共同规则围绕可见关系、输入事实和验收组织；分支知识按缺口读取。模型专属语法、数值与版本限制在执行时向当前 owner 核对，不将教程配方、固定参考数量或个案比例升级为通用契约。
- 缺执行能力时可交付提示及输入说明，但必须标明尚未成图；局部成功、代理暂选与用户认可分别解释。该选择不承诺跨模型收益或像素级保留，实际质量需要获授权的输入—调用—输出验证。
