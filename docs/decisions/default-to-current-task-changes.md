## 目的
- 让多个会话、人员或自动化共享一个 Git 工作区时，简短的提交指令只提交当前任务结果，不消费其他来源的工作区或暂存区内容。

## 背景
- Git 能展示 staged、unstaged 和 untracked 状态，但不会记录每处工作区改动由哪个会话或人员产生。
- 用户在一个任务完成后说“提交”或“提交 Git”，通常是在授权提交该任务结果，不是在授权接管当前仓库内所有并行改动。
- 仅按路径、修改时间、内容相关性或 staged 状态推断归属，仍可能把任务开始前已有内容、其他会话并发写入或混合同一文件的改动带入提交。

## 决策
- 采用: 将未指定范围的提交指令解释为提交可由当前任务要求、用户指定范围、agent 已执行编辑和已知初始状态可靠归因的改动，不解释为提交整个工作区。
- 采用: 任务开始前已有、执行期间由其他来源产生或无法说明来源的改动默认保留；用户明确要求指定范围或全部改动时才扩大授权，并继续复核实际 diff 与提交粒度。
- 采用: staged 状态不代表当前任务拥有该内容；使用显式路径、精确局部暂存或经过完整 diff 复核的 path-limited commit 隔离提交，不改写或消费其他来源的 staged 内容。
- 采用: 同一路径混有多个来源、暂存快照无法安全隔离或提交前出现无法归因的范围变化时，在创建提交前停止并请求用户选择。
- 不采用: 不把 Git 状态、文件时间、目录邻近或内容相似度单独作为改动归属证明。
