## 目的
- 让所有项目决定保留的独立 test/check 入口都能从显式目录中找到，包括阻断提交、CI 或发布的 gate。
- 用稳定的入口身份区分“自身就是验证入口”和“只是其他证明的一环”，避免 case 漏登记或按函数、断言、规则和子步骤膨胀。
- 保留低上下文索引、只读查询和显式维护，同时不重新引入源码扫描、marker、自动采集或自动注册。

## 背景
- “值得长期找回的独立证明单元”需要再次判断登记价值，可能让已经作为项目 gate 的 test/check 在保留实现后仍没有 case。
- 共享契约、fixture 或执行链路可以降低实现成本，却不能说明多个能够独立选择并产生各自判定的入口应被合并为一个 case。
- 技术上能够 import、直接调用或被 runner 临时筛选，不代表项目把该实现作为稳定验证目标；反过来，聚合命令即使只编排子检查，也可能是项目实际采用的独立 gate。
- `Entry:` 允许多个 locator，如果不限定它们必须定位同一逻辑入口，就会重新模糊 case 与入口的对应关系。
- 入口身份和父子归属需要结合项目脚本、CI、规则配置和维护约定判断，目录解析器无法仅凭 locator 文本可靠推断。

## 决策
- 采用: `verification-implementation-review` 只在新增、修改、删除或审查测试与工程校验实现，或者显式查询和整理其 case 时启用；普通业务修改、仅运行既有检查、只修复被检查对象和业务运行时输入校验不启用。
- 采用: `test` 通过安排输入、状态或交互并断言可观察结果产生判定；`check` 对代码、schema、生成物、依赖或工程状态应用规则，主要产物是可复核的通过、失败或诊断结论。
- 采用: 独立验证入口是项目明确拥有的稳定选择或调用单元，能够直接作为验证目标并产生可归属于自身的最终判定。仅能被 import、调用或临时筛选的内部实现不是独立入口；其结果只用于组成父入口判定时，归入父入口。
- 采用: 每个已经存在、决定保留的独立验证入口各有且只有一个 case。阻断提交、CI 或发布的 test/check 必须登记；非阻断入口只要被项目作为独立验证目标保留，也使用同一规则。可靠性或维护成本不足的入口应被删除或修复，不能以不登记掩盖。
- 采用: 项目采用的聚合 gate、CI job 或项目级检查命令本身是独立入口，即使只编排其他验证也要登记。子步骤只通过父入口执行时不另建 case；同时被项目作为独立验证目标时，再拥有自己的 case。
- 采用: 一个 case 的全部 `Entry:` locator 必须定位同一逻辑入口，可以同时记录入口定义文件、规则 ID、task 和规范调用命令；不得把多个独立入口或仅在入口内部执行的辅助实现收进同一 Entry 列表。
- 采用: case 继续记录 `Verification: test|check`、`Entry:`、`Contract:` 和 `Proves:`。同一入口内的多个函数、断言、规则、分支和连续检查点由一个 case 承接；planned、review、exempt、人工风险和普通业务实现不进入目录。
- 采用: 入口身份、父子归属和证据质量由 agent 根据项目事实进行语义判断。工具不扫描源码、不发现入口、不统计未登记函数、不要求 marker、不执行 Entry，也不自动创建或修复 case。
- 采用: Markdown 目录继续作为权威源；派生索引的搜索覆盖 case ID、标题、全部 `Contract:`、全部 `Proves:` 和全部 `Entry:`。`list` 与 `show` 在持久化索引不可用时从当前合法目录建立只读内存投影，`check` 与 `sync-index` 仍严格要求持久化索引新鲜。
