## 目的

- 让未来的正式测试结果能够证明其来源和语义资格，同时避免把尚无近期计划的探索误作实施承诺。

## 背景

- 现行门禁主要消费测试进程的聚合退出码，无法直接区分可追溯的行为失败、未绑定测试和结果协议故障。
- 完整接入会同时影响测试实体身份、runner 结果生产、test-evidence 消费、项目检查和 CI；在真实身份模型与 runner 证据尚未稳定时冻结细节，容易形成错误约束。
- 当前没有近期实施需求或排期，因此只保留未来方向与重启条件，不把探索细节维护成当前实施规格。

## 决策

- 采用: 若未来为正式测试建立资格门禁，各 runner 在生产边缘输出统一、版本化的 JSON 结果；结果以 Test ID 标识测试实体，test-evidence 消费方先报告有问题的测试实体，再从权威账本关系派生关联 Case ID。
- 采用: 缺少有效身份、无法关联 Case 或协议不合格的正式测试结果应阻断为测试完整性问题，不把它解释成有资格约束实现的行为回归。
- 采用: 该方向作为长期未对齐方向保留。重新启动前不修改现行测试、test-evidence、check 或 CI 行为，也不把现有 draft change 当作路线图或待执行清单。
- 采用: 只有在 Test 身份与关系模型已经可用、出现真实阻断需求和优先级、至少一个 runner 有可核对的生产证据，并获得明确实施授权后，才重新评估实施；届时重新决定 JSON Schema、结果状态、传输、runner 接入、迁移和加固边界。
- 不采用: 现在冻结字段、runner 映射或迁移顺序，或因相关依赖完成而自动启动实现。
