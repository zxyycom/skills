## 目的
- 让每个 case 继续对应 runner 能稳定选择、单独报告且测试意图完整的最小原生节点。
- 让增长中的账本能够按稳定测试责任定点维护，不要求加载或修改一份全量 Markdown。
- 保持一个统一查询入口，并能从索引准确返回 case 所在的权威主题原文。

## 背景
- 测试文件、suite、脚本、runner 和 CI job 可以聚合多个可分别归因的测试结果，不能因自身可执行就成为一个合并 case。
- 单个 Markdown 在 case 较少时可以工作，但补齐历史测试后目录已经跨越多个工具域；继续集中会让无关主题共享同一写入热点。
- 主题文件适合承接维护与定位边界，但测试证据身份仍来自最小原生入口和全局唯一 case ID，不能按文件重新聚合。
- 派生索引已经能够统一查询多个权威源；只要 state 保存源路径和行范围，拆分正文不需要引入手写总表、源码扫描或自动注册。

## 决策
- 采用: case 的登记单元仍是最小原生测试入口；框架不限，节点必须能够稳定选择、单独报告最终结果且拥有一项完整测试意图。
- 采用: fixture、helper、mock、断言和步骤只作为入口内部环节；测试文件、suite、目录、package script、runner 命令和 CI job 只要聚合更小原生节点，就只作为容器。
- 采用: 自定义测试程序只有在确实不存在更小可归因节点且测试意图单一时才能整体登记；混合多个独立意图的入口先拆测试。
- 采用: `catalogPath` 指向主题目录，直接子级 Markdown 按稳定测试责任拆分并各自至少承接一个 case；case ID 在全部主题文件中保持唯一。
- 采用: 全部主题 Markdown 共同组成权威源；统一派生索引保存 `sourcePath` 和行范围，跨文件提供查询，并让 `show` 只展开目标 case 的主题原文。
- 采用: 目录和 case 继续由测试改动显式维护；工具只发现配置目录中的主题 Markdown，不扫描测试源码、不执行 Entry，也不自动收集、注册或生成 case。
- 不采用: 把全部责任域重新集中到单个 Markdown、按主题合并多个原生节点，或为拆分主题恢复 marker、入口采集和自动注册。
