# 项目验证模型

本文帮助维护者理解项目要证明什么、证据如何形成，以及如何选择验收路径。实际命令、范围和预算由[项目工具链](gate-execution.md#权威-vibe-门禁)承接；运行结果与失败诊断见 [Gate 运行结果与诊断](gate-runtime.md)，新增或修改 Check 见 [Gate Check 编写与接入](gate-check-authoring.md)。

## 谁负责证明什么

- **主仓库**证明维护的结构、共享工具、生成状态和制品满足项目契约。
- **单个 skill 的行为 owner**决定其目标行为需要哪些现实案例和回归证据。同仓本身不产生跨 skill 的行为验证责任；显式共同工作流才需要相应组合验证。
- **测试与环境证据**只覆盖实际断言的对象和执行环境。例如，源码测试通过不等于生成制品、真实媒体或其他平台已验收。测试设计和证据维护从[仓库导航](navigation.md)进入。

## 从改动到验收

1. **选范围**：日常先用公共 quick 基线，按本任务的改动 owner 和风险显式追加能力组或直接测试；quick 不包含代码质量命令或 skill/仓库结构校验。领域检查沿用实际订阅与成功前置，文件/函数指标读取所选领域的维护代码投影，二者来自同一份领域声明。多个 `--scope` 分别求自身文件集合后取并集，某组的排除不压制其他组的包含；检查共享输入不自动扩大指标领域。重复检测保持独立的完整代码范围与既有订阅。其他人的工作区变更不自动扩大选择。影响不明或需要全工作区变更结论时才用 changed/all 兜底；单个 skill 和发布例外按 [AGENTS](../AGENTS.md#验证与交付)执行。
2. **检查前置并结算**：环境可信后，各 Check 按自身责任检查材料或执行命令；成功前置未通过时，依赖项不启动。failed、unavailable、意外不适用或运行失败不能当作通过。直接命令、整轮结果和性能预算分别构成证据。
3. **检查生成状态**：需要可信分发产物的验证先证明实际消费的 skill 与源码一致；显式模式按这些消费者的完整生成闭包校验，自动 changed、full 和 release 保留全量生成前置。程序类型有效本身不证明生成一致。
4. **交付证据**：分别报告实际运行与结果、未覆盖的环境及剩余风险。一次命令通过不等于发布已执行或远端保护已生效。

## 何时可以复用成功证明

receipt 是某项 Check 在完整输入身份下通过的历史证明；它与本轮实际执行的结果分别报告。

quick 和显式 scope 直接执行选定检查，不采集全工作区输入指纹，也不读取或发布项目 receipt。原生检查的计算缓存和调度历史仍可使用，但不作为通过证明。

changed 可以复用完整输入、契约和工具链身份精确匹配的 receipt，也只有它可以发布 receipt：整轮成功、所有本次实际执行项通过，重新采集后输入和工具链无漂移才发布。输入未知、未闭合、不可读取或必要探测失败时，在 changed 的有效范围保守执行，不发布部分证明。full、CI 和 release 全执行，不复用或发布 receipt。具体选择与失败处理见[权威 Vibe 门禁](gate-execution.md#权威-vibe-门禁)。

## 制品与发布边界

普通工作树验证与版本管理的 pending 快照是不同输入。release 从一次快照进行版本授权，并对同一快照打包；未暂存的 skill 变更不能因此视为已打包。

聚合发布需要 Linux 完整 release Gate 和 Windows 对同次 Linux 视频 zip 的验收均成功；远端合并保护还须实际配置并核对。平台 fixture 不证明未覆盖的真实媒体、网站或客户端行为。具体工作流与授权边界见 [CI 与发布](tooling.md#ci-与发布)。
