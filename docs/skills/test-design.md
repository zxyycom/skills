# Test Design

`test-design` 先处理“哪些行为值得投入自动化”，再处理“怎样测试”。新增与存量采用同一标准，已有测试是候选方案，不因存在或发现缺陷就默认保留、修复。

收益看消费者依赖、错误影响和现实风险；成本包括准备、运行、理解、变更、环境与不稳定性。关键契约也可能不值得承担自动化成本，此时明确接受未被自动拦截的风险，契约仍然有效；不自动追加人工检查或补测待办。

## 使用方式

适用于功能与 Bug 回归测试设计、存量测试审查和精简。可以提出“给这个行为设计测试”“审核这些测试是否值得保留”或“评估这项 GUI 测试是否值得自动化”。只运行测试、维护账本或调整 Gate 调度交给相应入口。

流程是：

1. 从行为和风险识别保护点，不从旧断言反推测试义务。
2. 裁定投入、不自动化或事实未决；先有取舍，再有修补。
3. 仅为入选目标选择有效、低成本的测试，保留合适项，精简重复或过重项，必要时才设计、修复或替换。
4. 交付裁决依据、实际保护变化及验证范围；只有缺陷清单不算完成必要性审查。

每条测试只承担自身职责，不要求包办调用链。[易错判断集](../../skills/test-design/references/judgment-pitfalls.md)集中校准关键性与投入、有效性与必要性、重复与职责差异；设计方法按入选目标读取，不设删除配额或逐条长证明。

## 与测试证据账本的分工

本 skill 负责自动化取舍及入选测试的设计质量；[Test Evidence Review](test-evidence-review.md) 负责实际证据、Case 与引用。两者独立选用，项目同时采用时以最终入口、证明范围和保护变化交接。

## 验证边界

结构和链接检查证明文本可读取，不证明取舍有效。实际效果使用未收录的代表性材料验证：是否先作投入裁决，允许明确不自动化，保留有价值的保护，并只修补入选目标；同时核对独立预期、实际执行和授权边界。
