# Test Design

`test-design` 处理“如何写好测试”：让测试识别目标错误、容忍保持契约的实现替换，并兼顾运行与维护成本。

适用于设计测试方案、补充行为与 Bug 回归测试，以及审查或改进断言无效、重复验证、入口过重、fixture 失真、实现耦合和环境不稳定的测试。仅运行既有测试、维护账本或调整 Gate 调度交给相应项目入口。

## 使用方式

可以提出“给这个行为设计测试”“审查这些测试能否抓住 Bug”或“降低这组测试成本，同时保留必要的 Git 和 CLI 证据”。

流程先区分设计、实施和只读审查，再从行为与场景出发，选择边界，组织输入、动作、独立预期与观察，最后按任务验证和交付。贯穿其中的两个问题是：

- 目标错误出现时，哪项观察会让测试运行器报告失败？
- 保持契约而替换实现后，测试是否仍应通过？

真实集成边界、替身和语义明确的断言 helper 都按证明责任选择。矩阵、准备复用、回调断言、恢复、并发、性质、快照、性能及变异验证按需展开。

## 与测试证据账本的分工

本 skill 负责设计与实现质量；[Test Evidence Review](test-evidence-review.md) 负责审查实际证据、维护 Case 与引用。两者独立选用，项目同时采用时以最终入口及其证明范围交接。

## 验证边界

结构、链接和分发检查证明 skill 可读取、可交付。实际行为仍需通过代表性任务验证，包括设计与只读路径、必要真实边界、独立预期、断言失败传播，以及降层或去重后的证明保留；这些结果与账本有效或测试运行通过分别判断。

实际 skill 位于 [`skills/test-design/`](../../skills/test-design/)。
