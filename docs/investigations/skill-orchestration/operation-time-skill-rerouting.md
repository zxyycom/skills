# 长任务跨阶段 Skill 重路由调查

## 调查信息
- 核心问题: 长任务从一个工作阶段进入具体副作用动作时，怎样重新发现并进入适用的领域 Skill，而不让通用执行 Skill 硬编码其他 Skill 的领域内容？
- 状态: 暂停
- 最新报告时间: 2026-08-12T05:39:41+00:00

## 调查报告

### 首次发现改进没有覆盖动作时重路由
- 形成时间: 2026-08-12T05:39:41+00:00

#### 形成时背景

本仓库曾因工作区经常同时存在多组改动，让 `decision-records` 等领域 Skill 原生提供分段暂存能力。后来发现这些能力在提交任务中不易首次触发，于是扩展了 Skill description，使“多个决策变化同时存在时单独暂存所选变化”成为可发现的使用时机。

新的真实案例表明，首次发现不是唯一问题：agent 在任务前期已经读取并使用 `decision-records`，后期进入 Git 暂存与提交阶段后却把当前动作重新归类为通用工作区隔离，只进入 `git-commit-organizer`，没有再次读取领域 Skill。通用 Git 手段能够继续工作，因此没有失败信号迫使 agent 返回专用能力；直到用户提醒后，agent 才重新读取 `decision-records` 并发现 `stage`。

同一案例还暴露了 `stage` 不能原子处理“新领域及其首批决策”的独立能力缺口；该事项当时另由 `changes/stage-new-decision-domains-with-initial-records/` Draft Change 记录。本调查不把该工具边界当作漏用专用能力的原因，也不负责确定其实现方案。

针对漏用问题，曾提出在 `git-commit-organizer` 中识别决策路径、强制重新读取 `decision-records` 并优先调用 `stage`。用户指出，这会让通用 Git Skill 混入其他 Skill 的具体内容，而且需要类似交接的领域和动作不只这一种，不能用逐个硬编码特例解决。

#### 调查目的

本轮调查要区分首次 Skill 发现、长任务中的跨阶段重路由、领域专用能力缺口和通用执行能力的责任边界，判断当前材料能够支持哪些结论，并保存后续选择机制前必须继续回答的问题。

本轮不选择最终机制，不修改 Skill、全局提示词、项目协作规则或工具实现，也不把一次案例直接推广成尚未验证的平台契约。

#### 调查范围与依据

调查以 Git `HEAD` `8e04a90d4b031245808fd8f79a5da5baf2e58690` 和 2026-08-12T05:39:41+00:00 的工作区状态为基线；当时只有未跟踪的 `changes/stage-new-decision-domains-with-initial-records/`，它不改变本调查核对的既有 Skill 与历史记录。

实际核对了以下材料：

- `skills/decision-records/SKILL.md` 的 description、主动读取策略和“构造待提交决策快照”流程，确认当前入口已经明确覆盖多个决策变化的独立暂存。
- `skills/git-commit-organizer/SKILL.md` 的范围恢复、快照隔离和提交工作流，确认它只提供通用 Git 手段，没有领域 owner 的重新解析协议。
- `docs/decisions/make-independent-decision-staging-discoverable.md`、Task Graph 中已成功的 `task-000023` 及其引用的集成提交 `8ee1eecc2aaa2b4d89b46187ff831e88531b7f17`。该提交只修改了 `decision-records` description、Skill 版本、决策对齐状态和派生索引；没有修改 `git-commit-organizer` 或建立其他运行时交接入口。
- `skills/skill-maintainer/SKILL.md` 的 Skill 发现、真实依赖与缺失路径要求，以及 `skills/ai-ready-docs/` 对 AI 实际获得文本、owner 归位和外部召回缺口的原则。
- 用户对本次实际执行路径、漏用时点以及硬编码跨 Skill 内容不可扩展的说明。

本轮没有检查 Codex 平台内部 Skill dispatcher 或上下文装配实现，没有运行多轮模型触发实验，也没有收集其他领域的完整失败案例。因此，材料可以证明现有仓库契约没有覆盖本次动作时重新进入，但不能单独证明某一种提示词、交接协议、注册表或机械门禁足以普遍解决问题。

#### 调查结果与边界

已确认事实：

1. 现有 `decision-records` description 已经表达独立暂存使用时机，本次漏用不能再单纯归因于发现文案缺失。
2. 先前的发现入口集成只留下了任务开始或重新匹配 Skill 时可消费的 description，没有留下能够证明长任务后期会重新匹配、重读或交接领域能力的仓库契约与验证证据。`task-000023` 的既有结果可以证明发现入口已经集成，不能证明动作时重路由已经成立。
3. 本次执行路径支持一个更窄的诊断：当任务阶段从领域维护转为通用副作用操作时，Skill 选择可能没有重新执行；此前读过的领域能力随后依赖模型注意力保持。通用手段能够成功时，这个缺口不会自然产生工具失败信号。
4. 新领域拒绝与动作时漏路由是两个独立问题。正确的专用命令可能在重路由后仍因真实能力边界失败，但该失败不能解释为何命令最初没有被尝试。
5. 把 `decision-records` 的路径、命令和失败规则直接写入 `git-commit-organizer` 只能解决单个组合，并让可独立分发的通用 Skill 逐渐依赖多个可选领域 Skill；随着领域和副作用动作增加，这会形成多对多硬编码，不是可扩展的 owner 边界。

当前仍未决定的问题：

- 重路由策略应由始终可见的全局 agent 指令、通用执行 Skill 的领域 owner 解析协议、独立协调能力、机器可读的能力声明，还是这些机制的组合承接。
- 哪些阶段变化或副作用动作足以触发重新匹配，怎样避免每个普通步骤都重复加载 Skill。
- 已经读取过的 Skill 再次命中时，应重读完整入口、特定动作章节，还是由 Skill 声明可恢复的重入点。
- 通用执行 Skill 怎样发现当前安装或可用的领域 owner，同时保持领域 Skill 可选、缺失时有明确路径，并避免维护第二份集中路由真相。
- 提示词级重路由能够提供多强的保证，哪些聚合索引、发布、归档或外部写入还需要机械门禁；门禁负责阻止错误结果时，怎样避免反向成为另一套领域路由器。
- 后续验收需要哪些跨领域真实案例，才能证明机制解决的是“动作时重路由”而不是再次优化某一对 Skill。

基于当前证据，可以排除“继续只加长领域 Skill 正文”和“在 Git Skill 中逐项硬编码其他 Skill”作为完整方案；不能据此直接采用全局重匹配、通用交接或机器注册机制中的任意一种。本主题暂停，等待用户或后续维护者明确希望继续调查的机制范围与保证层级；恢复时应至少选择多个不同领域与不同副作用阶段的代表性任务进行验证，再决定是否建立 Change 或长期决策。
