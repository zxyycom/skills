## 形成时背景

上一轮区分了表达极性、规范作用、目标参照方向和描述层级，并提出应检查一个从补集形成的概念何时已经成为目标侧原语。用户用安全规则给出了更具体的修正：一份安全文档虽然包含大量负向描述，其主线仍然可以是“安全”；只是在“安全”难以从正面完整展开、正向措辞容易保持模糊时，文档选择用具体的不得发生事件来表达和收紧这条主线。负向描述在这里不一定是主线之外的附属提醒，反而可能是安全主线最具体、最可执行的内容。

这也直接修正了上一轮“禁止契约中负向描述可能就是主线”的粗略分类。更准确的问题不是文档究竟以安全还是禁止项为主线，而是抽象目标名称与具体规则怎样共同组成一条主线：`安全` 提供组织概念，禁止项提供成员判定、违规见证或实现约束。两者位于不同抽象层，不需要争夺唯一主线身份。

## 调查目的

本轮要判断安全类文档怎样验证“正向描述并非总是占优”，并区分高层正向目标名称、负向规格、目标定义、必要条件和验证证据。重点是解释：负向规则为什么可能比“保持安全”这类正向概括更直接、更精确，同时避免把列出若干禁止项夸大成已经完整证明系统安全。

本轮不把所有安全问题都还原为禁止项，不判断安全天然是纯负向属性，也不修改 `ai-ready-docs` skill。安全只作为结构清楚的反例，用于检验正向描述优势的适用条件。

## 调查范围与依据

本轮依据包括用户对安全主线与具体禁止项关系的分析、本主题前述目标投影、补集表达、认知压缩和正负层级讨论，以及安全属性的一手形式化资料。Schneider 的 [Enforceable Security Policies](https://www.cs.virginia.edu/~soffa/cs851/p30-schneider.pdf) 说明一类可由执行监控机制实施的安全策略可以通过有限的坏前缀刻画；Clarkson 与 Schneider 的 [Hyperproperties](https://www.cs.cornell.edu/fbs/publications/Hyperproperties.pdf) 则说明安全策略还包括不能只用单条执行轨迹属性表达的信息流等超属性，并区分禁止坏事的 safety 与要求好事发生的 liveness。

这些资料支持某些安全属性天然适合由违规事件或坏前缀刻画，也支持“安全不等于一组普通禁止句”的边界；它们没有检验自然语言文档中哪种表达更容易被 LLM 遵循。本轮没有运行模型实验，也没有建立正负写法的信息量指标。仓库基线仍为 Git commit `75c8b5edefe768ace29c7f960a163016218486c0`；工作区既有 skill 与决策阶段性改动保持原状。

## 调查结果与边界

用户的判断成立，并提供了比“禁止契约是例外”更准确的解释：**正向目标名称可以承担概念组织，负向规则可以承担该目标的具体规格；当正向名称无法给出可判断内容，而违规条件能够被清楚识别时，负向规格会比继续增加正向概括更有用。**

例如，“系统必须安全”虽然在目标参照方向上清楚，却几乎没有告诉执行者哪些行为满足安全、怎样发现违规或怎样验收。若改为“未经授权不得读取”“秘密不得进入日志”“高权限操作不得绕过审计”，这些规则以被禁止事件为参照，却为安全增加了可执行区分。此时负向内容不是离开安全主线去介绍错误道路，而是在把抽象的安全投影成可检查的局部条件。

因此，一条主线可以具有纵向结构：

`深层价值：避免不应由相关方承担的损失`

`目标概念：安全`

`属性或策略：机密性、完整性、授权、可审计性等`

`具体规则：不得发生的访问、泄露、篡改或绕过事件`

越靠上越能解释为什么这些规则属于同一目标，越靠下越能支持判断和执行。把高层“安全”称为正向主线、把所有具体禁止项称为附属边界，会低估后者的语义责任；反过来，只保存禁止项而不说明它们共同保护什么，也可能让规则碎片化、难以处理冲突和未见场景。更准确的组织不是正向主线加负向附录，而是**目标名称与正负规格共同展开主承诺**。

这个例子确实验证了正向描述并非总是占优，但需要说明比较对象。负向规则胜过的是“保持安全”“采用安全方案”这类信息不足的正向概括；它未必胜过一份同样精确、可判定的正向规格，例如“只有通过授权检查的主体可以读取资源”可能与“未经授权不得读取资源”承载接近的契约。哪一种更好仍取决于规则的自然判定单位、默认行为、验证入口和错误后果，而不是语法极性本身。

负向规格的优势至少有三种来源：

1. **违规见证更具体**：某些属性只要出现一个有限坏前缀就已确定失败，指出坏事件比描述全部合法执行更紧凑。
2. **高层正向概念欠指定**：`安全`、`可靠`、`合规`等词能够组织目标，却不能独自恢复成员条件；负向规则补上实际区分。
3. **错误后果不对称**：高后果场景关心的是确保特定失败绝不发生，直接保存禁止项更便于审计、监控和追责。

但“用负向描述来证明安全”需要收窄。某条禁止规则可以定义一个安全属性，实际检查可以证明系统满足该属性；然而若“安全”仍是开放的深层目标，列出已知禁止项只证明这些属性得到覆盖，不能证明所有未知攻击、信息流关系、可用性目标或未来情境都安全。部分信息流策略甚至需要比较多条执行轨迹，无法由一串独立坏事件完整表达。因此更准确的说法是：**负向规格使安全的某些组成属性可定义、可证伪或可验证，而不是仅凭具体就自动证明整体安全。**

这一轮也改变了“目标侧原语”的后续问题。`安全`可以是成熟的目标侧概念，却仍必须由大量负向条件展开；概念已经成熟不意味着负向规格可以被压缩掉。真正需要讨论的是：**高层目标名称与具体负向规则之间是什么关系——后者是在完整定义目标、给出必要条件、提供可观测违规见证，还是只覆盖当前已知风险？** 只有区分这些关系，AI-ready 文档才能既利用负向描述的精确性，又不把有限禁止项误作完整目标。
