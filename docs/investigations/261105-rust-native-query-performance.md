## 形成时背景

用户希望在接受原生二进制分发后，判断 Rust 能带来多少实际优化。用户对主要使用者的盘点显示，直接导入多用于简化 CLI 调用，深入使用主要需要精确的程序化输出，因此迁移候选是全面 CLI＋JSON；批量优先接口和 SDK 退出留到采用决策后设计。

本轮以 Decision Records 查询为性能试点，生产入口、TS SDK、生成物与分发流程保持不变。Cargo 的正式测试账本与 CI 接入属于后续迁移范围。

## 调查目的

以相同行为任务分别回答：新进程 CLI、常驻 Node 直接导入改为原生子进程，以及 npm／本地安装入口的耗时、CPU 和内存变化。以有限匹配负载支持继续或停止的判断，不将微基准、原型通过或单个倍数当作完整迁移证明。

## 调查范围与依据

- **基线与候选**：生产 revision `098d64ad53ccfcd64c4d78b3a72782c0e2b6b6ae`，Node v26.8.2、Bun 1.4.4；Rust/Cargo 1.98.1，锁定依赖的 release 构建。Linux x86_64，AMD Ryzen AI 7 H 450。候选 SHA-256 为 `863e91862111f68e7a54505d14369a8d2afcdb2f37aac371f0a0f5099676e788`。
- **输入**：固定 revision 的真实快照 419 条（153 active、266 archived）；确定性 100／1,000／10,000 条合成输入通过现有同步与检查。基础合成图无边，复杂关系使用真实快照，另有合法 Unicode 长行、四种故意损坏来源和两种合法来源的字节超限变体。
- **行为证据**：21 个原生节点通过，另以行为 owner 独立预期核对关键边界。业务输入差分 66 个单元匹配，npm／本地安装各重复 17 个单元，共保存 100 个对照；独立验证重跑规模、真实图、Unicode、安全和预算组。`list/search` 本轮仍为现有文本，仅 `trace` 提供 JSON。
- **计量**：在查看配对结果前选定 20 个主单元；每单元分无插桩 wall 与资源 profile，再分 CLI／宿主路径，各 10 对交替样本及首轮预热。共 40 份记录、1,600 个正式调用样本、160 个预热调用。测量期间本任务的编译、Gate 和其他验证已暂停，并非整机隔离或冷文件缓存实验。
- **调用边界**：CLI 计从启动至完整输出；宿主比较公开 `runDecisionRecordsCli` 捕获输出与同类宿主启动原生子进程，trace 双方含 JSON 解析。模块首次加载单列，监督进程 IPC 另记。这里不是所有 SDK 导出或外部客户端的实测回放。
- **证据边界**：驱动执行前后指纹比对并在漂移时失败，但原始 JSON 未保存逐次两份实际哈希，不能称具备这类独立记录。npm 驱动锁定启动器，安装树的版本、二进制及文件指纹由独立 smoke 和归档补充，不宣称逐请求锁定完整 npm 树。

实验源码、测试及制品不作为长期产物保留，留存材料不保证完整重跑。正式迁移需另建源码、测试及 CI，并重新验证和测量。

版本续接：本报告数值继续对应上述旧冻结制品；后续 trace 查重优化及 TS／旧 Rust／新 Rust 的有关系图比较见[独立调查](./261105-rust-trace-aligned-graph-performance.md)。后续优化版本不能代入本报告的旧版本结果。

## 调查结果与边界

### 1. 直接原生路径有明确收益，常驻调用需单独评价

下表是各单元独立配对样本的无插桩墙钟中位数，单位毫秒。不同单元独立执行，不能将跨单元差异作为纯规模因果。

| 输入／操作 | Node CLI → Rust CLI | TS 导入 → Rust 子进程 |
| --- | --- | --- |
| 100 条分页 | 711.5 → 3.4 | 17.3 → 10.3 |
| 1,000 条分页 | 602.6 → 6.2 | 57.0 → 10.2 |
| 10,000 条分页 | 1,135.0 → 46.0 | 532.8 → 52.3 |
| 10,000 条 metadata 零命中 | 1,203.3 → 52.8 | 544.2 → 63.8 |
| 10,000 条 content 全扫描零命中 | 21,455.2 → 595.7 | 14,980.1 → 436.6 |
| 10,000 条 content 密集命中早停 | 1,452.0 → 44.5 | 533.1 → 45.6 |
| 真实快照列表 | 445.6 → 4.8 | 49.1 → 10.6 |
| 真实快照重划 trace JSON | 509.7 → 6.1 | 32.2 → 8.9 |
| Unicode 预览预算 | 509.7 → 9.5 | 146.6 → 12.0 |

例如一万条全文件扫描，直接 CLI 耗时约降至 1/36，宿主调用约降至 1/34。小规模分页的宿主收益则只有约 6.9 ms；高倍数的冷启动收益不能替代实际使用路径的绝对延迟判断。

### 2. npm 启动器存在明确反例

100 条 metadata 零命中的安装入口各自配对结果：本地安装组 Node CLI 413.9 → 原生 2.4 ms，宿主 8.0 → 4.7 ms；npm 组 Node CLI 409.7 → 启动器 44.5 ms，但宿主从 TS 导入 9.4 → npm 启动器 51.6 ms，耗时增至约 5.46 倍（+446%）。这些基线来自各自单元，不能将其差值当作统一安装器净开销。

因此，不能把裸二进制收益直接外推到 npm。若继续迁移，需要把常驻调用与实际安装入口共同列为验收对象，优先验证能保留收益的原生调用路径。

同一候选经直接、离线 npm tar 和本地安装三路运行 list／trace JSON／无效命令，输出与退出码一致。单次安装 wall 为 npm 0.457 秒、本地安装 0.054 秒；它们不是分布、网络下载或冷缓存结论。

### 3. CPU 与进程内存也下降，但不是应用总内存承诺

一万条全扫描资源组中，查询进程 CPU 中位数 Node 14.273 → Rust 0.429 秒；wait4 子进程峰值 RSS 中位数 223,120 → 21,968 KiB（约 217.9 → 21.5 MiB）。这是分开插桩采样的资源结果，其墙钟不用于上表。

宿主 TS CPU 中位数为 16.740 秒，Rust 分支宿主＋helper＋child 为 0.462 秒；helper 在写统计前取样，属于近似下界。两分支共用已加载 TS 模块的 Node 宿主：Rust 的宿主 RSS 仍含该模块，不能推论卸载 SDK 后的应用内存。宿主累计峰值、约 2 ms 采样下界和子进程峰值必须分列，不能相加为同时峰值。

### 4. 结论与采用缺口

**建议继续 Rust 原生 CLI 的受控迁移设计，但不直接替换生产。** 本轮已经证明受测只读负载有量级收益，也证明 npm 常驻调用可能退化。收益属于这次实现、数据布局、调用方式与运行环境的整体组合，未用同策略 TS 改写隔离纯语言贡献。

需要保留的边界：多个图错误同时存在时，Rust 只返回首条，而 TS 聚合诊断；该边界不等价，未作为合格性能单元。完整参数错误交互、所有 YAML／Unicode 版本组合和受控并发文件替换未穷尽；写入事务、其他 skill、十万条、大规模复杂图和其他平台未测。本轮 21 个专项原生节点及其 Contract／Proves 不代表正式 Case 账本或 CI 接入。后续全面 JSON、SDK 退出、批量优先协议和发布供应链仍需独立设计与验收。

首次交付验证因私有目录缺少 package.json，npm 意外选择 `/tmp` 上级包树；代理回报增加 2、移除 239 个包，原先 manifest／lock／node_modules 内容未知。本轮保留现场，未擅自恢复；仓库生产依赖未因此纳入改动。后续验证已使用新私有根、显式 prefix／cache，并修复启动器向父目录解析平台包的行为。该副作用不是性能数据；若其他工作依赖这棵共享临时包树，需要由其 owner 按已知依赖清单恢复。

本轮未切换生产入口或发布原生包。二进制、工具版本、算法、安装入口或输入分布变化后，应重新测量，而不是沿用本轮倍数。
