# 同一变更内决策演进保留边界调查

## 调查信息
- 核心问题: 已激活决策在进入版本基线前被同一变更中的新决策修订时，是否应保留为长期演进历史，以及版本控制证据能否支持安全折叠？
- 状态: 已结束
- 最新报告时间: 2026-08-03T10:45:21+08:00

## 调查报告

### 版本基线可发现同一变更内的决策演进候选
- 形成时间: 2026-07-28T16:39:03+08:00

#### 形成时背景
当前决策记录契约允许先把已经确认但尚未落实的长期判断激活为 `active + unaligned`，在完整目标与当前事实核对后再标记为 `aligned`。首次激活即建立记录，Git 暂存、提交和历史不参与建立状态；已建立记录发生语义变化时，需要新增完整决策并通过演进关系承接前序。

由此出现一个潜在问题场景：在同一轮尚未提交的工作中，agent 先建立并落实决策 A，随后用户进一步澄清或调整长期判断，agent 又建立决策 B 来修订 A。若 A 和 B 相对最后一个已提交修订都是新增文件，最终改动会同时包含一个刚建立便归档的 A 和当前活动的 B。A 从未进入已提交版本基线，却会作为长期历史永久保留，可能把同一变更内部的收敛过程保存成决策演进。

本轮形成时尚不确定：该场景是否必须依靠人工判断；Git 或项目版本控制 owner 是否已经提供足够证据机械识别其中一部分；以及版本基线应只参与交付前历史整理，还是反向改变决策“激活即建立”的现行语义。

本报告把“版本基线”作为一个尚待选定的已提交修订，把“同一变更内”限定为决策 A 和决策 B 都不存在于该修订、但都出现在本次准备交付的变更集合中；该集合可能由 pending、未暂存工作区变化或两者共同形成。这个定义只用于描述待调查对象，不预先决定应选择 `HEAD`、准备提交内容的父修订或其他修订作为正式基线。

#### 调查目的
本轮调查准备回答：

1. 现行决策契约和 CLI 会如何处理上述场景。
2. 已提交版本基线能否提供一个不依赖对话语义的充分条件，用于识别同一变更内新增并被修订的中间决策。
3. 哪些折叠动作可以由机械检查支持，哪些关系结构仍需 agent 或维护者判断。
4. 这项认识目前只是潜在问题、候选规则还是已经具备实施与采用依据。

本轮不决定是否修改 `decision-records`，不实现检查或折叠命令，也不把未验证的自动修复方案写成当前生命周期规则。

#### 调查范围与依据
本轮以提交 `090c1bc4db13b23e2241530f610363f87aee53a1` 的干净工作区为事实基线，检查了以下材料：

- [`decision-records` 行为入口](../../../skills/decision-records/SKILL.md)及其[领域契约](../../../skills/decision-records/references/decision-record-rules.md)，用于确认候选、激活、对齐、归档、丢弃和语义修订的现行边界。
- [将对齐状态定义为单向基线](../../decisions/archive/use-monotonic-alignment-baseline.md)，用于确认 `active` 已经生效、`aligned` 不可退回以及长期方向改变时应形成新决策。
- [`decision-lifecycle-service.ts`](../../../tools/decision-records/src/decision-lifecycle-service.ts)，用于确认当前 `activate`、`evolve`、`archive`、`discard` 和 `mark-aligned` 的生命周期入口，以及演进时归档直接前序并激活新候选的事务行为。
- [集中版本管理责任](../../decisions/archive/centralize-version-control-responsibility.md)和[`VersionControlRepository` 接口](../../../tools/shared/src/version-control/types.ts)，用于确认项目已经区分已提交修订、pending 快照和工作区变化，并能查询修订中的路径或文件。

本轮只做文档、决策和实现结构审阅，没有构造临时仓库复现生命周期事务，没有验证部分暂存、多 worktree、并行 agent 或非 Git 工作区，也没有测试关系折叠算法。场景本身来自设计讨论，并非当前工作区已经存在的故障样本。

#### 调查结果与边界
已确认的现行事实：

1. 决策 A 一旦首次 `activate`，便获得建立时间并成为已建立记录；即使仍是 `unaligned` 或尚未 Git 提交，也不能使用只面向候选的 `discard`。标记为 `aligned` 后也不能退回 `unaligned`。
2. 已建立记录只能原地进行不改变目的、范围、关键背景、采用方向、核心理由和关系语义的编辑性修正。用户后来改变长期判断时，现行正式路径是建立决策 B，以“修订”“替代”“判定无效”或“归并”关系承接 A。
3. 当前 `evolve` 实现根据显式关系归档活动直接前序并激活新候选，但不查询版本控制状态。因此，A 和 B 是否都只存在于当前未提交改动，不会改变生命周期事务或最终记录集合。
4. 项目版本控制接口已经能够取得当前修订、列出修订中的文件、读取指定修订文件，并分别查询 pending 与工作区变化。判断“路径 A 是否存在于已提交基线”不需要从提交日志文本或对话语义推断。

基于这些事实形成的推断：

- 若基线修订中不存在 A 和 B，而当前改动包含已归档 A、活动 B 以及从 B 指向 A 的演进关系，则可以机械证明 A 与 B 都是在同一未提交版本区间内形成。这个证据不能证明用户是否曾真正确认 A，却足以证明 A 从未成为已提交版本基线的一部分。
- 决策记录的目标是保存可长期回放的判断，而不是任务进度或同一交付内部的收敛过程。在没有其他历史需求的简单链路中，永久保留 A 的回放价值存疑；把当前完整判断 B 作为本次变更唯一新增决策，更符合这一内容边界。
- Git 或其他版本控制基线不必参与“当前工作区中哪项决策已经生效”。它可以只作为交付前历史规范化的证据：激活仍立即约束当前工作，版本基线只帮助判断中间演进是否已经跨越需要保留的持久边界。

目前较稳妥的候选规则是：交付前检查新增决策关系；如果后继决策 B 和它指向的前序决策 A 都不存在于选定的已提交基线，则报告“同一变更内决策演进”。若 A 只有 B 这一个新增后继、没有其他入站引用，且 A 不承接任何已提交直接前序，可以把它列为简单折叠候选；存在多前序、分叉、关系类型组合、直接引用或更早已提交前序时，只提供诊断，由 agent 重新判断最终决策应承接的直接关系。

如果后续采用该规则，`decision-records` 继续拥有“何时允许折叠以及折叠后保留什么关系”的语义判断；版本控制 owner 只提供基线、路径存在性和变更集合证据。提交整理流程可以触发检查，但不拥有决策生命周期规则。

该候选规则尚未达到采用或实施状态，主要边界包括：

- 尚未确定“版本基线”固定使用当前 `HEAD`、准备提交内容的父修订，还是由调用方显式选择；三者在部分暂存、分支整理和提交重写时可能不同。
- “修订的两端都是新增文件”是可靠的发现条件，但不是所有关系都能机械合成。删除中间记录后，新记录是否应直接修订、替代或判定无效某个更早前序，仍可能需要语义判断。
- 尚未决定检查只产生 warning、在严格模式阻断，还是提供显式折叠命令。自动删除已激活记录会改变现行“已建立记录默认保留”的不变量，不能只作为实现细节加入。
- `decision-records` 可以在没有 Git 的目录中使用。若引入版本控制辅助，它需要显式前置条件和缺失时的保守路径，不能把项目内部的版本控制实现变成未声明的分发依赖。
- 尚未验证其他 agent、外部工具或未提交工作树消费者是否可能已经把 A 当作共享基线；“没有进入 Git 历史”不等于“从未被任何读取方观察”。

因此，本轮确认的是一个具备机械发现依据的潜在问题，而不是已经确定的 bug 修复：现行模型可能把同一未提交变更内部的中间判断保存为长期历史；版本基线足以收窄需要审阅的候选集合，但最终折叠规则、依赖边界和安全动作仍需后续设计与验证。

### 采用事前警告与显式单前序折叠
- 形成时间: 2026-08-03T10:45:21+08:00

#### 形成时背景
前一份报告已经确认：Git 路径存在性足以发现一部分同一未提交变更内的演进候选，但不能证明中间判断是否有长期价值，也不能替调用者合成删除中间节点后的关系。本轮讨论进一步比较了单独删除命令、复用 `discard`、扩展 `evolve`，以及事前或事后 warning 的调用成本。

用户最终确认采用事前 warning，并以扩展 `evolve` 的方式承接简单折叠；归档类动作也应在未提交决策退出活动状态前提醒，避免无意义演进。`discard` 的候选边界保持不变，不新增通用删除命令。

#### 调查目的
本轮把原候选规则收敛为可实施契约，回答：

1. 哪些命令需要在写入前检查 Git 基线。
2. 首次警告后如何显式选择保留或折叠，且不增加第三次调用。
3. 折叠中间记录时，哪些关系仍能机械校验，哪些必须由调用者决定。
4. 非 Git 集合、复杂关系图和既有 `discard` 应保持什么边界。

#### 调查范围与依据
本轮复核了当前 decision-records 生命周期服务、可恢复事务、CLI 参数解析、共享 `VersionControlRepository`、skill 行为入口和领域契约，并通过 change `guard-unrecorded-decision-evolution` 实施已确认方向。

实现证据包括：

- `tools/decision-records/src/decision-history-baseline.ts` 从决策根发现 Git 工作树并读取当前 `HEAD` 中的决策路径；非 Git 或决策根在工作树外时返回无基线。
- `tools/decision-records/src/decision-lifecycle-service.ts` 在事务前产生可区分的暂停结果，并在显式折叠时校验目标状态、`HEAD` 路径、其他引用和最终关系边界。
- `tools/decision-records/tests/unrecorded-history.test.ts` 集中覆盖 warning 无写入、显式保留、非法上游拒绝、成功折叠和 archive 门禁。
- 完整 decision-records 测试入口共 36 个原生测试节点通过，生成 CLI 已从工具源码同步。

本轮没有尝试支持自定义基线、一次折叠多个中间记录、自动关系合成、部分暂存或提交重写。

#### 调查结果与边界
已采用并实现的结论如下：

1. Git `HEAD` 只提供归档前发现证据。它不参与候选、建立、生效、对齐或索引成员判断，`createdAt` 的生命周期语义保持不变。
2. `evolve`、带关系的 `activate` 和 `archive` 即将归档一个不在 `HEAD` 的已建立记录时，首次调用返回“命令已暂停”的 warning 和退出码 1，且不修改决策 Markdown 或派生索引。
3. 调用者确认中间记录仍有长期价值时，以 `--keep-unrecorded-history` 重试。该选项只承接本次显式判断，不放宽其他生命周期、关系或事务校验。
4. 调用者判断中间记录没有长期价值时，以 `evolve --collapse-unrecorded <decision-path>` 重试。该动作只折叠一个活动、已建立且不在 `HEAD` 的前序，并把零个或多个 `--relation` 视为后继的完整最终关系集合。
5. CLI 不组合关系类型，也不默认继承上游。最终关系中的活动目标按普通演进归档；已经归档的目标只有在它原本就是被折叠记录的直接前序时才允许。调用者可以明确选择不再连接某个上游。
6. 折叠删除、活动最终前序归档、后继建立和索引重建使用同一个可恢复事务。已进入 `HEAD`、目标非活动、目标仍被其他记录引用或最终归档目标越过直接前序边界时，命令拒绝且不写入。
7. 非 Git 决策集合继续执行原有生命周期命令；缺少版本证据时不能使用 `--collapse-unrecorded`。Git 仓库已发现但基线读取失败时停止维护，不静默跳过预检。
8. `discard` 仍只删除未激活候选。复杂分叉、多层中间链、多个折叠目标或最终直接关系不清楚时，不提供简单断链或通用删除，由维护者保留现场并设计真实演进。

事前与事后 warning 在需要显式选择时都至少需要两次调用；事前 warning 的优势是第一次调用保证无写入。扩展 `evolve` 后，保留与简单折叠都能在第二次调用完成，不需要先 `discard` 再第三次激活。

当前实现固定使用当前 `HEAD`，因此只能识别尚未进入当前提交基线的记录。已经分多次提交但仍属于一个更大逻辑变更的历史、自定义比较基线和部分暂存视图不在本轮结论内。

#### 后续复核条件
本调查已经形成长期决策、实施计划、行为实现和测试证据，因此结束。出现以下任一情况时另开或追加调查：

1. 需要让调用方选择非 `HEAD` 的版本基线，或把部分暂存内容作为交付边界。
2. 获得真实的多层未提交链、分叉或多后继样本，需要判断是否值得扩展折叠能力。
3. 发现当前单前序关系门禁仍允许错误的直接关系，或阻止了具有明确语义的安全折叠。
4. 非 Git 环境需要等价的可验证持久基线，而不再接受保守保留历史。
