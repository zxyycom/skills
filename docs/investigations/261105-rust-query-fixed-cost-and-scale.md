## 形成时背景

[原性能调查](./261105-rust-native-query-performance.md)发现 Rust 原生 CLI 相对现有 Node CLI 在受测只读负载下明显更快，但三组规模依次运行，未回答“每项代价小会不会使压力规模仍被固定开销掩盖”。本轮沿用原调查的实现和输入，另在新时段交错比较规模；这里考察的是该实现和调用路径的总耗时，不把语言、算法与启动成本分离。

## 调查目的

判断已测规模是否出现可观察的增长、何时增长相对小规模足够明显，以及现有样本能否识别固定成本与复杂度阶。补测关注分页和 metadata 零命中；全文件扫描、密集命中、常驻宿主和 npm 分发沿用前序报告的边界，不将本轮结果外推到它们。

## 调查范围与依据

- 前序调查保留的无插桩 wall 样本为 100、1,000、10,000 条，每操作和每调用边界各 10 对，按规模分单元顺序运行；每个单元内语言交替，不同规模并非同轮交替。合成输入无关系，内容密集命中达到结果上限时提前停扫。具体覆盖、机器及原数据见前序报告。
- 2026-11-05 北京时间 16:18:50–16:20:12（UTC+08）新增补测：同一机器使用原三个合法 fixture 和 SHA-256 为 `863e91862111f68e7a54505d14369a8d2afcdb2f37aac371f0a0f5099676e788` 的冻结 Rust 可执行文件。生产路径使用仓库公开的 `bun run --silent decision-records`，该脚本调用 Node 分发 CLI；计时包含 Bun runner、Node 进程启动及完整输出，与旧调查直接启动 Node 的数值不能视为相同边界。Rust 路径直接运行二进制。两条命令均为新进程，未模拟常驻宿主。
- 分页和 metadata 零命中各以 100、1,000、10,000 条在同轮轮换并反转规模次序；每单元语言顺序也交替，共 2 轮预热、12 轮正式，分别为 24 和 144 次调用。每个规模及操作中有 8 次某语言先、4 次另一语言先，并非完全平衡；规模顺序六种排列各出现两次。同一任务的编译、Gate 和计数工作暂停，但未隔离整机或控制其他负载，也不是冷缓存实验。
- 每次保存顺序、完整命令、耗时、退出码以及规范化输出摘要，逐次与前序冻结差分的退出码和 stdout/stderr 精确核对；全部匹配。执行前后 Rust 二进制、当时的原型源码、生产 CLI 分发树、输入树及 package.json 指纹相同；未在每次调用间重新计算输入指纹。资源中的原始 JSONL、汇总程序与汇总结果保留样本与处理方式。

## 调查结果与边界

### 1. 一万条已出现明显增长，不能笼统说固定开销仍主导

下表为交错补测的正式样本中位数，单位毫秒；每格 12 次。Node 列含 Bun runner 的额外调用边界。

| 操作与路径 | 100 条 | 1,000 条 | 10,000 条 | 1,000 → 10,000 增长 |
| --- | ---: | ---: | ---: | ---: |
| 分页 Rust CLI | 2.78 | 7.21 | 51.12 | 7.09 倍 |
| metadata 零命中 Rust CLI | 3.11 | 7.83 | 62.03 | 7.92 倍 |
| 分页 Bun → Node CLI | 563.71 | 647.37 | 1,325.37 | 2.05 倍 |
| metadata 零命中 Bun → Node CLI | 587.61 | 623.13 | 1,517.21 | 2.43 倍 |

Rust 在 100 到 1,000 条即增长约 2.5 倍，在 10,000 条进一步增长至数十毫秒；因此该场景已能观察到规模相关工作，并不是整个现有范围都被固定开销遮蔽。Node 小规模的相对差异较小，与较大的进程及调用固定项相容，但此实验没有单独测出启动成本，不能把差异全部归因于它。Rust 单项更快是实现、输入和机器的总体观察，并非分离出的语言成本。

波动仍有实际影响：Rust 10,000 条 metadata 样本范围 47.29–93.01 ms；Node 同单元为 1,102.77–2,890.60 ms。交错减轻了规模与时间完全绑定，却没有排除调度、缓存和其他进程影响；12 次也不足以推断尾延迟或一般化到其他机器。旧调查中分页 Rust CLI 为 3.36／6.22／46.00 ms，趋势一致，数值不必相同。

### 2. 固定项、每项系数和复杂度不能由三点唯一识别

用户提出的机制成立：在简化模型 `T(N)=c+a·f(N)` 中，若固定成本 c 不变，每项系数 a 越小，就需要更大的 f(N) 才能超过 c；较快实现确实可能在小规模下掩盖增长。但更换运行时也改变 c，不能先验认定 Rust 的可见增长阈值必然更高。这里的 c 包括进程与调用固定项，并不等同于算法的常数系数 a。

两点连线的截距也不是独立测得的启动成本：旧数据的规模与时间绑定，输入处理不一定严格线性，而中位数与真实单次成本结构不是同一个模型。更稳妥的经验结论是，在本轮输入与机器上，1,000 条相对 100 条已有可见增长，10,000 条增长更明显；不能据此声称某精确记录数以后进入某渐近区间。

对三个规模拟合 `c+aN` 或 `c+bNlogN`，两者各含两个自由参数，单一剩余自由度又受跨单元波动影响；不同操作的拟合优劣还会反转，因此不能由拟合选出复杂度阶。每千条归一化亦包含固定成本，且输入字节数及内部工作并非固定不变；不能将其直接称为单条实际成本或算法操作次数。需要结合源码的循环、排序和图结构分析，并在控制变量后观察操作计数；更大 N 也只能增加有限实测范围，不能单独证明渐近阶。

原数据的 content 零命中确实读取全扫描负载，Rust CLI 在 100／1,000／10,000 条的中位数为 11.09／55.09／595.75 ms，但一万条的 10 次范围 422–1,868 ms；这支持“规模相关工作可见”，不支持精确斜率。content 密集命中则在 `matched>=21`、返回 20 时受 `max-records` 限制停止，数据集 N 不等于被扫描文件数，不能用总条数归一化推断全扫描成本。内容扫描还有文件和累计字节预算，本轮未突破这些限制。

本轮未修改生产实现、发布原生入口或证明所有负载的性能；更换二进制、输入分布、执行入口或环境须重新验证。需要识别固定项时，应增加专门的空工作／阶段计时并说明是否包含启动；需要验证图算法增长时，应固定节点数、分别控制边数及深度，记录算法操作计数，而非把本次计时外推。[算法复杂度调查](./261105-rust-query-algorithmic-complexity.md)已确认合法星形图的局部平方查重；无边输入即使扩大 N 也不会触发该路径，不能将“万条增长可见”理解为所有渐近风险均已暴露。

随附脚本、样本和汇总用于审阅当时的方法与结果，不是现行运行入口；实验源码和制品不作为长期产物保留，材料不保证完整重跑。
