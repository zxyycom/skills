# Skills 仓库编码规范

本文档是 `scripts/` 与 `tools/` 下实现代码通用质量规则的 owner，供修改或审阅这些实现代码的 agent 和维护者使用。

项目级协作和内容归属由 [`AGENTS.md`](../AGENTS.md) 定义，各 skill 的行为契约由对应的 `skills/<skill-name>/SKILL.md` 及其引用文件定义，脚本目录、依赖、命令、生成、打包和发布规则由 [项目工具链](tooling.md) 定义。本文件不复制这些规则，只约束实现代码应保持的性质。

核心目标：代码显式呈现职责、领域含义、数据流、状态与失败边界；具体语法和抽象形式服从这些信息的准确表达。

使用结果：实现者能够定位行为规则与实现归属，选择贴合问题的实现模型，显式处理受影响边界，并形成与风险匹配的验证证据；reviewer 能够区分阻断问题、推荐调整和只需复核的信号，并指出判断依据、受影响边界和所需动作。

## 1. 适用范围与使用方式

本规范直接约束 `scripts/` 与 `tools/` 下维护的 TypeScript、JavaScript、测试、声明源和生成器。由构建或同步入口写入 skill 的 MJS、类型声明和 source map 是生成产物，不是直接实现入口；修改其行为或公共类型时，必须修改 [项目工具链](tooling.md) 指定的源码、声明源或生成器，再通过对应入口同步。

修改或审阅实现前，必须按以下顺序建立判断上下文：

1. 从相关 `SKILL.md`、项目文档或工具链文档确认本次行为的规则 owner。
2. 确认承载逻辑的现有脚本、模块或生成器；没有明确归属时先澄清职责。
3. 列出改动跨过的输入、文件、进程和输出边界。
4. 选择能证明这些边界仍成立的验证。

本规范使用三种规则强度：

| 强度 | 本规范中的识别方式 | 审查结论 |
| --- | --- | --- |
| 阻断性要求 | 使用“必须”“只能”“不得”“不能”“不要”“不用”或“只有……才……”等明确约束，或列为“通过标准” | 未满足时不能接受当前实现；修复实现，或由对应 owner 显式改变发生冲突的契约 |
| 推荐路径 | 使用“默认”“优先”等表达，或在问题形态表中列为优先模型 | 满足全部阻断性要求和对应章节“通过标准”时，可以采用其他方案，并说明使该方案更符合当前约束的依据 |
| 审查触发信号 | 使用“重新判断”“阅读信号”等表达，或列出需要复核的代码形态 | 只触发边界复核，不单独证明违规，也不自动要求重构 |

每节的“通过标准”收束阻断结论，其他正文提供定义、推荐路径和审查信号。审查反馈必须说明规则强度、对应依据、受影响边界和所需动作；审查信号需要补充责任或证据复核后才能形成整改要求。

整改以本次变更及其直接影响边界为闭合范围。只有范围外代码使受影响边界无法成立或无法验证时，才把对应部分纳入本次整改。

## 2. 规则与实现各有 owner

具体行为 owner 定义“系统做什么、什么结果与失败合法”，本规范定义“实现代码保持什么性质”，项目工具链定义“源码、命令、依赖、生成和交付怎样组织”。具体行为或组件契约可以细化本规范的推荐路径；涉及阻断性要求的冲突必须先同步相应 owner。

先确认谁定义规则、谁实现规则、谁消费结果、谁负责失败反馈。稳定规则只能有一个权威 owner；代码和测试负责实现或验证规则。规则缺失、冲突或过期时，必须以稳定 owner 为基线，再按影响面同步 owner、代码、测试、fixture 和生成材料；既有实现和测试只作为当前行为证据。

新增逻辑进入最接近其职责的现有实现归属。入口负责组合流程、映射结果和对外反馈；解析、校验、文件操作或领域判断进入负责该职责的模块。跨模块协作使用显式参数、类型和返回结果，不在调用方重复解释下游拥有的领域值。

共享层承接多个调用方共同依赖的不变量、数据结构、错误映射，或项目明确选定且具有独立契约的基础实现原语。准入依据是共同责任和独立契约；调用位置相似、实现代码短或未来可能复用不构成共享责任。

可分发工具的依赖方向与共享层位置以[项目工具链的“源码与依赖边界”](tooling.md#源码与依赖边界)为准。

通过标准：reviewer 能回答“哪份规则定义行为、哪段代码负责实现、谁消费结果、谁负责失败反馈”。

## 3. 在边界完成解析和错误映射

CLI 参数、环境变量、配置、路径、文件系统、Git、子进程、Markdown、frontmatter、JSON、scanner 或其他依赖输出、归档文件和网络响应都属于外部边界。每个外部表述进入其责任边界时按同一方向流动：

1. 以未经信任的外部值进入边界。
2. 在边界完成解析、校验和归一化。
3. 以领域对象进入内部逻辑。
4. 领域对象再次进入文件、进程、网络或其他外部表述时，按新边界的输出契约转换；从外部重新进入时，新边界重新承担自己的校验。
5. 在对外入口把最终结果或失败映射为稳定输出、诊断和退出状态。

同一个原始表述只在所属边界转换为领域对象；新的信任边界或表示转换形成新的校验责任，各边界分别验证自己的契约。

可预期失败使用明确返回结果或具有稳定语义的错误传递，由入口统一转换为调用方可行动的反馈。验证失败应指出文件、字段或规则及原因；机器输出与诊断输出保持各自通道职责。

失败必须保留可区分的语义并形成调用方可行动的反馈；缺失、格式错误、读取失败、进程失败或依赖不可用不得映射为合法空结果或成功结果。默认值、格式推断、跳过、降级和恢复策略只有在行为 owner 明确定义时才使用，并保留足够的定位证据。

通过标准：内部领域逻辑只接收已经由当前边界验证的领域对象；调用方能够区分合法空结果与边界失败，并从失败结果定位责任和下一步动作。

## 4. 用类型表达领域含义

1. JSON、YAML、frontmatter 等无法由 TypeScript 证明结构的外部数据先以 `unknown` 接收并完成运行时校验和收窄，不得用 `any` 或未经证明的类型断言绕过边界。
2. 原始输入、领域对象、对外输出模型和只服务实现内部的参数使用不同类型或清楚的局部类型边界；领域逻辑只接收已经校验的值，不重复解析原始输入。
3. 跨模块传递的配置、解析结果、执行结果和生成状态使用显式类型；生命周期由提供方管理的输入和领域结构默认使用只读字段或只读集合，把状态变化收敛到负责其生命周期的单元。
4. 有限状态和互斥分支优先使用判别联合、字符串字面量联合或等价结构，使非法组合不能轻易进入内部逻辑。
5. 普通、可预期失败优先通过 `Result`、判别联合或其他明确返回类型表达；错误类别和对外映射继续遵循本规范的边界规则。
6. 稳定字段、错误类别和跨函数复用的固定值由职责内类型或常量表达，并与负责其语义的模块共同维护。

当多个字符串、通用 JSON 值或元组承载不同领域含义时，使用对象或专用类型区分；测试 fixture 和单一局部作用域可以保持简单。类型声明不得代替边界运行时校验，稳定规则和错误映射不得散落为魔法值。

通过标准：函数签名能区分原始输入、外部格式、领域对象、内部参数、执行结果和可预期失败，并直接表达值的验证状态与修改责任。

## 5. 按问题形态选择实现模型

行为 owner 或组件契约已经明确实现模型时按其约定执行；没有更具体约定时，识别当前职责的主导问题形态，并优先采用相应模型。一个任务包含多种问题形态时，在清楚的职责边界内组合不同模型；相同职责保持稳定的表达方式。实现模型以直接表达当前不变量为选择目标，各类范式没有统一优先级。下表是非穷尽的推荐映射，问题形态可以组合；第三方库的采用另由实际抽象需求决定。

| 问题形态 | 优先实现模型 | 主要价值与期待方向 |
| --- | --- | --- |
| 无状态计算和数据转换 | 纯函数与组合 | 数据流直接，推理范围局部，计算易于组合和独立验证 |
| 有明确先后顺序、副作用和失败恢复的工作流 | 结构化过程或事务脚本 | 执行顺序和失败路径连续可见，流程便于追踪和调整 |
| 有稳定身份、生命周期或必须持续成立的不变量 | 对象或 class 封装 | 状态与行为聚合到同一责任边界，不变量有稳定的维护位置 |
| 取值和分支集合封闭，结果只取决于当前值 | 判别联合与穷尽分支 | 合法取值和对应处理显式，分支变化能够在整体范围内检查 |
| 行为取决于当前状态和事件，合法转移需要约束 | 状态机 | 状态、事件和转移关系显式，流程演进能够按合法路径检查 |
| 行为需要持续扩展或替换 | 接口、策略对象或多态 | 消费契约保持稳定，行为差异集中在独立实现中 |
| 大量同构规则、字段或映射 | Schema、表驱动或声明式定义 | 规则以统一结构集中呈现，扩展主要落在数据定义中 |
| 数据经过多个职责稳定的连续处理阶段 | 流水线 | 阶段职责和组合顺序清楚，各阶段可以独立理解和验证 |
| 独立参与方围绕事件发生和时序关系协作 | 事件驱动或消息驱动 | 协作契约显式，参与方能够围绕事件边界独立演进 |
| 数据关系、访问模式或批处理成本占主导 | 数据导向设计 | 数据组织贴合主要工作负载，性能取舍具有清楚依据 |

项目当前通过 [`package.json`](../package.json) 和共享源码提供以下实现能力。本节定义它们在编码规范中的适用角色；实际可用性、版本和源码归属分别以项目依赖与共享源码 owner 为准。实现者先根据问题形态选择模型，并以模型是否确实需要相应抽象作为采用依据。

- `Valibot` 用于 Schema、外部数据解析和运行时收窄。
- `neverthrow` 用于可预期失败及其同步、异步组合；[`Option`](../tools/shared/src/option.ts) 用于表达值存在或缺失，并可在边界转换为 `Result`。
- `ts-pattern` 用于非平凡封闭分支、判别联合组合和穷尽匹配。
- `Remeda` 用于由连续数据转换主导的集合处理与组合。
- `Mnemonist` 用于访问模式或复杂度确实需要的专用数据结构；普通集合继续使用语言原生结构。

现有能力无法覆盖真实问题时，把缺口及其工作负载交给依赖 owner 评估；采用结果同步到项目依赖集合。

本表确定实现的主导表达及其期待方向。选择和 review 同时检查实现是否兑现第三列的主要价值。具体控制流、数据结构和错误机制由本文件的相邻规则、行为 owner、组件契约和实际约束共同确定。

通过标准：实现者能从问题形态确定主要实现模型，并说明实现如何呈现对应的期待方向；相同职责使用一致表达，不同模型之间具有清楚边界。

## 6. 保持局部可推理并按责任组织代码

### 局部流程

读者从入口和相邻实现中应能恢复主要条件、数据流、状态变化、副作用、执行顺序和失败归属。具名阶段、职责拆分和领域命名必须帮助恢复这些语义；拆分导致读者跨多个无独立责任的 helper 才能重建主流程时，保留更连续的局部结构。

### 文件、目录与抽象

目录归属、依赖选择和生成边界遵循 [项目工具链](tooling.md)。在同一实现归属内，目录层级对应模块 owner 的父子关系，文件名表达模块内的具体职责，文件、模块和函数围绕可独立说明的变化原因组织。入口保持流程可读，具体职责进入可独立命名和验证的单元；只服务一个父模块的 helper、wrapper、常量和小类型留在父模块附近。

新增 helper、class、interface、共享模块、子目录或 barrel 必须承载真实结果、不变量、生命周期、变化原因、边界、稳定消费契约或独立验证责任。语法包装、转发调用、位置相似、代码短或假设复用不构成独立责任；共享代码进入项目已经定义且 owner 明确的共享边界。

### 审查触发信号

文件大小、函数长度、嵌套层数、分支数和复杂度指标都是阅读信号，不是单独的拆分或违规依据。出现以下情况时重新判断边界：

1. 一个单元同时负责多个工具行为、多个外部边界或多个输出阶段。
2. 新增功能需要持续修改无关代码。
3. 解析、领域判断、文件操作、输出和错误映射互相遮蔽。
4. reviewer 无法用一个简短句子说明该单元的主职责。
5. 抽象只转发参数或改写语法，调用方仍需理解其全部实现细节。
6. 子目录或 barrel 只由文件数量、导入长度或个人偏好驱动，不能指出新的父子 owner 或稳定消费边界。

这些信号只要求重新检查责任边界。若拆分不能产生更清楚的 owner、局部数据流或独立验证责任，保留简单的局部实现。

通过标准：文件路径和命名能表达实现归属；读者从局部代码能恢复主要流程和失败责任；每个新增抽象都能说明自己独立承载的现实责任。

## 7. Oxlint 例外保持局部且可审计

`bun run lint` 对 `scripts/` 与 `tools/` 的维护源码默认执行同一套 Oxlint 规则。遇到诊断时，默认路径是修改实现、类型、测试设置或规则表达，使代码符合规则；局部例外只通过本节定义的单行路径进入。

`.oxlintrc.json` 是受校验的统一项目基线，只表达已经确认的项目规则；局部例外由源码紧邻位置承接。需要调整项目级 lint 行为时，先更新本节的规则，再同步配置、前置校验和测试。路径、继承或规则级绕过，以及降低已选质量基线的配置都会被拒绝。

只有同时满足以下条件时，才能保留单点例外：

1. 被报告的结构是明确行为或接口契约不可缺少的一部分，而不是可修复的实现疏漏。
2. 改写以满足规则会弱化、遮蔽或错误表达该契约，或引入更高的实现风险。
3. 例外能收敛到一条源代码；不能以同一理由覆盖文件、目录、规则集合或不相邻的多处代码。

满足门槛时，在受影响代码的紧邻上一行写一条 `oxlint-disable-next-line <rule> -- <reason>`。这是唯一的局部例外路径。`<reason>` 必须说明该规则通常防止的情况为何在这里有意出现，以及当前契约为何要求保留它；只写“误报”“测试需要”或规则名称不构成理由。需要跨行或跨位置停用规则时，先重构或重新判断规则 owner，不扩展为配置豁免。

通过标准：`bun run lint` 通过，且未使用的 disable directive 作为 error 失败；reviewer 只读注释和相邻代码即可恢复具体规则、例外范围与契约理由。该注释只改变 lint 诊断，不替代类型检查、测试或其他受影响边界的验证。

## 8. 验证覆盖受影响风险

验证必须随影响面扩展：

1. 纯计算、解析或映射逻辑用单元测试、fixture 或等价局部验证证明不变量。
2. CLI 和验证入口同时覆盖成功、失败、退出状态以及 stdout/stderr 边界。
3. 文件系统、Git、归档和生成行为覆盖路径边界、确定性、失败恢复和产物漂移。
4. 共享工具链、项目配置或目录结构变化执行项目级检查。
5. 行为或数据契约变化必须同步对应 owner、Schema、示例、fixture、生成材料和验证入口中实际受影响的部分。

具体命令和生成检查入口以 [项目工具链](tooling.md) 为准，最低验证范围遵循 [`AGENTS.md`](../AGENTS.md)。交付时记录实际运行的命令和结果；无法运行时说明原因、未覆盖边界和残余风险。

通过标准：验证证据与本次改动影响的边界、失败行为和输出契约对应；类型检查是其中一类证据。

## 9. 交付前检查

1. 规则 owner、实现归属、消费方和失败反馈责任是否清楚。
2. 每个外部表述是否在负责它的边界完成解析、校验和归一化，领域逻辑是否避免重复解析同一原始输入。
3. 失败、恢复和默认行为是否可追溯到 owner，并向调用方提供行动信息。
4. 类型是否区分原始输入、外部格式、领域对象、内部参数、执行结果和可预期失败，并明确哪些值允许修改。
5. 主要实现模型是否贴合问题形态，同类职责的表达是否一致，不同模型的组合边界是否清楚。
6. 局部代码是否能看出条件、数据流、状态变化、副作用、执行顺序和失败归属。
7. 文件、目录和抽象是否围绕现实责任组织；代码指标、语法形式和复用设想是否只作为审查信号。
8. Oxlint 配置是否仍是受校验的统一项目基线；配置行为变化是否同步本规范、前置校验和测试；诊断是否优先通过实现修复，保留的例外是否满足局部门槛、紧邻单行格式和理由要求。
9. 生成行为是否从源码或生成器修改，并同步受影响产物。
10. 验证是否覆盖受影响边界、错误路径和输出通道；契约变化是否同步直接受影响的 owner、Schema、示例和验证材料。
11. 审查结论是否区分阻断性要求、推荐路径和审查触发信号；整改范围是否闭合在本次变更及其直接影响边界。
12. 受影响材料是否已经同步；每项规则是否仍由唯一 owner 完整解释。
