# Skills 仓库编码规范

本文档是 `scripts/` 与 `tools/` 下实现代码通用质量规则的 owner。它帮助实现者和 reviewer 判断代码应放在哪里、如何处理边界、如何表达领域含义、如何根据问题形态选择实现模型，以及需要什么验证证据。

项目级协作和内容归属由 [`AGENTS.md`](../AGENTS.md) 定义，各 skill 的行为契约由对应的 `skills/<skill-name>/SKILL.md` 及其引用文件定义，脚本目录、依赖、命令、生成、打包和发布规则由 [项目工具链](tooling.md) 定义。本文件不复制这些规则，只约束实现代码应保持的性质。

目标：每项代码变更都能定位规则 owner 和实现归属，选择贴合问题的实现模型，显式处理受影响边界，并用与风险匹配的证据证明行为成立。

## 1. 使用方式

修改 `scripts/` 或 `tools/` 下的 TypeScript 源码、测试或生成器前：

1. 从相关 `SKILL.md`、项目文档或工具链文档确认本次行为的规则 owner。
2. 确认承载逻辑的现有脚本、模块或生成器；没有明确归属时先澄清职责。
3. 列出改动跨过的输入、文件、进程和输出边界。
4. 选择能证明这些边界仍成立的验证。

随 skill 分发的 MJS、TypeScript 声明和 source map 生成文件不作为直接实现入口；需要改变其行为或公共类型时，修改主仓库源码、声明源或生成器，再通过 [项目工具链](tooling.md) 定义的入口同步。

## 2. 规则与实现各有 owner

代码和测试负责实现或验证规则，不成为新的规则来源。实现发现规则缺失、冲突或过期时，先确认稳定 owner，再按影响面同步 owner、代码、测试、fixture 和生成材料。

新增逻辑进入最接近其职责的现有实现归属。入口负责组合流程、映射结果和对外反馈；解析、校验、文件操作或领域判断进入负责该职责的模块。跨模块协作使用显式参数、类型和返回结果，不在调用方重复解释下游拥有的领域值。

共享层承接多个调用方真正共享的不变量、数据结构或错误映射，也可以承接项目明确选定并预置、具有独立契约的基础实现原语。预置原语不扩大其他共享代码的准入范围；只有调用位置相似、实现代码短或未来可能复用，仍不足以形成共享职责。

可分发工具的依赖方向与共享层位置以[项目工具链的“源码与依赖边界”](tooling.md#源码与依赖边界)为准。

通过标准：reviewer 能回答“哪份规则定义行为、哪段代码负责实现、谁消费结果、谁负责失败反馈”。

## 3. 在边界完成解析和错误映射

CLI 参数、环境变量、配置、路径、文件系统、Git、子进程、Markdown、frontmatter、JSON、归档文件和网络响应都属于外部边界。边界数据按同一方向流动：

1. 以未经信任的外部值进入边界。
2. 在边界完成解析、校验和归一化。
3. 以领域对象进入内部逻辑。
4. 在入口把结果或失败映射为稳定输出、诊断和退出状态。

可预期失败使用明确返回结果或具有稳定语义的错误传递，由入口统一转换为调用方可行动的反馈。验证失败应指出文件、字段或规则及原因；机器输出与诊断输出保持各自通道职责。

默认值、格式推断、跳过和恢复策略只有在行为 owner 明确定义时才使用，并保留足够的定位证据。任何失败路径都应让调用方知道下一步该查看、修改或重试什么。

## 4. 用类型表达领域含义

1. JSON、YAML、frontmatter 等无法由 TypeScript 证明结构的外部数据先以 `unknown` 接收并完成运行时校验和收窄，不用 `any` 或未经证明的类型断言绕过边界。
2. 领域逻辑只接收已经校验的值，不重复解析原始输入。
3. 跨模块传递的配置、解析结果、执行结果和生成状态使用显式类型。
4. 有限状态和互斥分支优先使用判别联合、字符串字面量联合或等价结构，使非法组合不能轻易进入内部逻辑。
5. 稳定字段、错误类别和跨函数复用的固定值由职责内类型或常量表达，不建立跨功能的杂物常量池。

当多个字符串、通用 JSON 值或元组承载不同领域含义时，使用对象或专用类型区分；测试 fixture 和单一局部作用域可以保持简单。类型声明不能代替边界运行时校验，稳定规则和错误映射不能散落为魔法值。

通过标准：函数签名能区分原始输入、外部格式、领域对象和执行结果。

## 5. 按问题形态选择实现模型

行为 owner 或组件契约已经明确实现模型时按其约定执行；没有更具体约定时，识别当前职责的主导问题形态，并优先采用相应模型。一个任务包含多种问题形态时，在清楚的职责边界内组合不同模型；相同职责保持稳定的表达方式。

| 问题形态 | 优先实现模型 | 主要价值与期待方向 |
| --- | --- | --- |
| 无状态计算和数据转换 | 纯函数与组合 | 数据流直接，推理范围局部，计算易于组合和独立验证 |
| 有明确先后顺序、副作用和失败恢复的工作流 | 结构化过程或事务脚本 | 执行顺序和失败路径连续可见，流程便于追踪和调整 |
| 有稳定身份、生命周期或必须持续成立的不变量 | 对象或 class 封装 | 状态与行为聚合到同一责任边界，不变量有稳定的维护位置 |
| 取值和分支集合封闭，结果只取决于当前值 | 判别联合与穷尽分支 | 合法取值和对应处理显式，分支变化能够在整体范围内检查 |
| 行为取决于当前状态和事件，合法转移需要约束 | 状态机 | 状态、事件和转移关系显式，流程演进能够按合法路径检查 |
| 行为需要持续扩展或替换 | 接口、策略对象或多态 | 消费契约保持稳定，行为差异集中在独立实现中 |
| 大量同构规则、字段或映射 | Schema、表驱动或声明式定义 | 规则以统一结构集中呈现，扩展主要落在数据定义中 |
| 数据经过多个职责稳定的连续处理阶段 | 流水线 | 阶段职责和组合顺序清楚，各阶段可以独立理解和验证 |
| 独立参与方围绕事件发生和时序关系协作 | 事件驱动或消息驱动 | 协作契约显式，参与方能够围绕事件边界独立演进 |
| 数据关系、访问模式或批处理成本占主导 | 数据导向设计 | 数据组织贴合主要工作负载，性能取舍具有清楚依据 |

项目已经预置以下实现能力。实现者先根据问题形态选择模型，再在模型确实需要相应抽象时直接使用；能力清单由项目依赖与共享源码 owner 统一维护。

- `Valibot` 用于 Schema、外部数据解析和运行时收窄。
- `neverthrow` 用于可预期失败及其同步、异步组合；[`Option`](../tools/shared/src/option.ts) 用于表达值存在或缺失，并可在边界转换为 `Result`。
- `ts-pattern` 用于非平凡封闭分支、判别联合组合和穷尽匹配。
- `Remeda` 用于由连续数据转换主导的集合处理与组合。
- `Mnemonist` 用于访问模式或复杂度确实需要的专用数据结构；普通集合继续使用语言原生结构。

现成能力不能覆盖真实问题时，把缺口及其工作负载交给依赖 owner 评估并更新项目依赖集合，使后续实现仍从已经确认的本地能力开始。

本表确定实现的主导表达及其期待方向。选择和 review 同时检查实现是否兑现第三列的主要价值。具体控制流、数据结构和错误机制由本文件的相邻规则、行为 owner、组件契约和实际约束共同确定。既有源码用于理解当前行为，明确规则与契约用于确定后续实现风格。

通过标准：实现者能从问题形态确定主要实现模型，并说明实现如何呈现对应的期待方向；相同职责使用一致表达，不同模型之间具有清楚边界。

## 6. 按变化原因组织代码

目录归属、依赖选择和生成边界遵循 [项目工具链](tooling.md)。在同一实现归属内，文件、模块和函数围绕一个可独立说明的变化原因组织。

入口保持流程可读，具体职责进入可独立命名和验证的单元。只服务一个父模块的 helper、wrapper、常量和小类型留在父模块附近；共享职责形成后再移动到共享层。

文件大小和函数长度是阅读信号，不是单独的拆分依据。出现以下情况时重新判断边界：

1. 一个单元同时负责多个工具行为、多个外部边界或多个输出阶段。
2. 新增功能需要持续修改无关代码。
3. 解析、领域判断、文件操作、输出和错误映射互相遮蔽。
4. reviewer 无法用一个简短句子说明该单元的主职责。

通过标准：文件路径和命名能表达实现归属，局部改动不要求读者同时理解无关流程。

## 7. Oxlint 例外保持局部且可审计

`bun run lint` 对 `scripts/` 与 `tools/` 的维护源码默认执行同一套 Oxlint 规则。遇到诊断时，默认路径是修改实现、类型、测试设置或规则表达，使代码符合规则；不要用无理由的注释掩盖问题。

`.oxlintrc.json` 是受校验的统一项目基线，不是按位置或用途分配规则的例外入口。配置只能表达已确认的基线；路径、继承或规则级绕过，以及降低已选质量基线的配置都会被拒绝。需要调整 lint 行为时，先更新本节的规则，再同步配置、前置校验和测试；不要用配置承接局部例外。

只有同时满足以下条件时，才能保留单点例外：

1. 被报告的结构是明确行为或接口契约不可缺少的一部分，而不是可修复的实现疏漏。
2. 改写以满足规则会弱化、遮蔽或错误表达该契约，或引入更高的实现风险。
3. 例外能收敛到一条源代码；不能以同一理由覆盖文件、目录、规则集合或不相邻的多处代码。

满足门槛时，在受影响代码的紧邻上一行写一条 `oxlint-disable-next-line <rule> -- <reason>`。这是唯一的局部例外路径。`<reason>` 必须说明该规则通常防止的情况为何在这里有意出现，以及当前契约为何要求保留它；只写“误报”“测试需要”或规则名称不构成理由。需要跨行或跨位置停用规则时，先重构或重新判断规则 owner，不扩展为配置豁免。

通过标准：`bun run lint` 通过，且未使用的 disable directive 作为 error 失败；reviewer 只读注释和相邻代码即可恢复具体规则、例外范围与契约理由。该注释只改变 lint 诊断，不替代类型检查、测试或其他受影响边界的验证。

## 8. 验证覆盖风险，而不只覆盖代码路径

验证随影响面扩展：

1. 纯计算、解析或映射逻辑用单元测试、fixture 或等价局部验证证明不变量。
2. CLI 和验证入口同时覆盖成功、失败、退出状态以及 stdout/stderr 边界。
3. 文件系统、Git、归档和生成行为覆盖路径边界、确定性、失败恢复和产物漂移。
4. 共享工具链、项目配置或目录结构变化执行项目级检查。

具体命令和生成检查入口以 [项目工具链](tooling.md) 为准，最低验证范围遵循 [`AGENTS.md`](../AGENTS.md)。交付时记录实际运行的命令和结果；无法运行时说明原因、未覆盖边界和残余风险。

通过标准：验证证据能证明本次改动影响的边界和失败行为仍成立，而不只是通过类型检查。

## 9. 交付前检查

1. 规则 owner、实现归属、消费方和失败反馈责任是否清楚。
2. 外部输入是否只在边界解析、校验和归一化一次。
3. 失败、恢复和默认行为是否可追溯到 owner，并向调用方提供行动信息。
4. 类型是否区分原始输入、外部格式、领域对象和执行结果。
5. 主要实现模型是否贴合问题形态，同类职责的表达是否一致，不同模型的组合边界是否清楚。
6. 文件和函数是否围绕独立变化原因组织，共享代码是否承接真实共享职责。
7. Oxlint 配置是否仍是受校验的统一项目基线；配置行为变化是否同步本规范、前置校验和测试；诊断是否优先通过实现修复，保留的例外是否满足局部门槛、紧邻单行格式和理由要求。
8. 生成行为是否从源码或生成器修改，并同步受影响产物。
9. 验证是否覆盖受影响边界、错误路径和输出通道。
10. 改动是否只同步受影响材料，没有把规则复制到新的 owner。
